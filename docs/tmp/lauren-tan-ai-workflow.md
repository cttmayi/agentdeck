# 把 AI 当员工：Lauren Tan 的七条工作法，和它背后的工程护栏

B 站 UP 主“苏大讲AI”的这条视频只有四分钟，标题很抓人：马斯克公司的一位工程师，一个人带几十个 AI，90% 的 SpaceX 同事都在抄她的作业。视频把她的方法压成七条，从“先造一个招聘官”到“用语音交代任务，再让 AI 复述”。看起来像效率博主的经验，实际上大部分都能在 pstack 和它的配套工具里找到对应实现。

先把神话部分拿掉。视频里“她以前一行代码都不会写”更像标题党；公开材料里，Lauren Tan（@poteto）是 React Core 团队成员，在 Meta、Netflix、Cursor 工作过，开源了 pstack。“90% 的 SpaceX 同事都在抄”也没有可核对的来源。她的方法值得看，靠的是把“带 AI”拆成了可复用、可验证的工件。

pstack 不是一个模型，也不是一个全能 Agent。它是一组 Agent Skills 和 playbooks：用 `/poteto-mode` 作为入口，按任务类型选择调查、修 bug、性能、重构、功能、原型等流程；用 `/reflect` 从一次成功或失败的轨迹里提炼技能修改；用 `/interrogate` 做多模型对抗评审；再配合 cursor-team-kit 里的 `control-ui`、`control-cli`、`verify-this`，把“我觉得好了”变成可复现的证据。README 里那句话很直白：if you want to go fast, go deep first。

视频的七条，表面是“把 AI 当员工”，底层是把一次性对话变成一套系统：角色、技能、身份、流程、验证。输入是你的意图、上下文、账号和仓库；输出是可复用的岗位卡、技能库、自动化交接和可验证的产物。一个最小场景：研究 Agent 每周抓竞品更新，按固定模板写成简报；验证 Agent 检查来源链接和数字；确认后发到群里。它适合重复、可验证、权限可控的工作；不适合目标模糊、无法验证、或者需要组织承担责任的决策。

## 七条方法，先压成一张表

| # | 视频里的要点 | 对应的工程动作 |
|---|---|---|
| 1 | 第一个 AI 不干活，先当“招聘官” | 角色访谈，生成岗位卡：目标、职责、工具、边界、输出格式 |
| 2 | AI 不在多，在精 | 窄职责专才，一人一个验收标准 |
| 3 | 像带新人一样交代背景 | 注入上下文，允许反问，先对齐再执行 |
| 4 | 把成功的一次对话存成技能 | 轨迹转 `SKILL.md`，进 Git，跨任务复用 |
| 5 | 给 AI 独立账号和身份 | 服务账号、最小权限、独立工作区/分支、审计 |
| 6 | 别再手动搬运信息 | 工具调用、Workflow、Agent 交接，结构化协议 |
| 7 | 用语音输入，让 AI 复述 | 低摩擦输入 + 结构化复述 + 人工确认 |

把七条放回流程，可以串成一个闭环。

图中紫色是 Agentic：角色访谈、幕僚长、专才，它们做判断、拆解、异常处理。蓝色是 Workflow：验证、技能库、复盘，它们做固定步骤和可重复的检查。橙色是 HITL（human in the loop，人工介入）：语音复述确认和不可逆操作前的人工确认。绿色是产物。

注意图里没有向量库。她的长期上下文主要落在技能文件、对话记录和代码仓库里，不是一个“什么都记得”的向量数据库。这个选择很工程：可读、可 diff、可回滚，比“模型记得我”可靠。

## 一、第一个 Agent 不干活，它负责招聘

第一步很反直觉：造出来的第一个 AI 不是干活的，而是坐下来问你几个问题。要不要定时干活，主要跟谁对接，最烦哪些活。问完，它按你的场景生成一个职责清楚的“AI 员工”；问题升级了，再调整。

这一步的产物可以落成一张岗位卡，比一段 prompt 多了几样东西。岗位卡至少写清楚五件事：目标是什么，负责哪些事，能用哪些工具，不能碰什么，输出长什么样。比如“会议纪要助理”：输入是妙记链接，输出分 decisions、owners、deadlines 三段；不替我做决定；缺信息时先问三个问题。这个卡片是可以 review、可以进 Git、可以交给另一个 Agent 的。

为什么先招聘再干活？因为大多数人一上来就写“你是一个资深产品经理”，然后期待它自己补齐组织上下文。招聘官的作用是把“你是谁、你要什么、边界在哪”从你的脑子里挖出来。它问的问题越多，后面返工越少。

但岗位卡是草稿，不是合同。招聘官也会自信地生成一个错误的岗位。你要审一遍，尤其是“不能做什么”这一栏。一个没有边界的岗位，最后一定会长成一个什么都接、什么都做不深的万能助手。

## 二、AI 不在多，在精

第二条很实在：写文案的、做表格的、剪视频的，每个都来一个 AI，最后每个都是半吊子；几个调教好的，顶一支杂牌军。

这句话在工程上对应的是“窄职责 + 独立验收”。从 README 看，pstack 的 playbooks 按任务分，不按职业分：调查、修 bug、性能、运行时取证、trace 取证、功能、重构、原型、视觉对齐、写技能、评测、自主运行、接手会话、安全暂停、多阶段计划。每个 playbook 有自己的步骤，多数最后要落到某种验收。专才不是一个“人设”，是一块清晰的责任边界。

所以“一个人带 50 个 AI”不该当成目标。视频口播说 50 多个，它引用的文章写的是 10 到 20 个执行 Agent，两个数字口径不同，不必当成 KPI。10 到 20 个执行 Agent 是结果：当任务可以拆成互不依赖的片，且每一片都有验证手段，才值得并行。没有验证的并行，只是 50 份低质量产出。

一个最小团队可以先只有三个角色：研究的、构建的、验证的。第四个角色什么时候加？当你能说出它独立的验收标准时。说不出来，就先别加。

## 三、像带新人一样给上下文，也允许它反问

第三条是“先告诉她我是谁、干什么的、每天最烦哪些活”，再反过来问她。她把 AI 比作“能力超强但刚入职五秒的实习生”。

这个比喻只在“上下文”这一层成立。模型有通用能力，但没有你的组织记忆、项目黑话、历史决策和审美偏好。它像一个刚进门的人，能力不差，但不知道你们上周为什么否掉了那个方案。你要补的是这些，不是再写一段“请认真思考”。

“每天最烦哪些活”是一个很好的 elicitation prompt。它逼你列出高频、低价值、可交接的任务，这些通常也是最适合自动化的任务。比“你能帮我做什么”有效得多，因为后者会得到一份泛泛的功能清单。

上下文要可维护。cursor-team-kit 里的 `workflow-from-chats` 会从最近对话里抽取稳定的偏好，判断哪些该进技能、哪些该进规则、哪些只是一次性的；`brainmaxxing` 则把记忆做成一个 Markdown vault，Agent 在会话开始时读，学到东西时写。它们都把高信号的东西沉淀成可读文件，而不是把所有聊天记录塞进上下文窗口。

也要允许它反问。一个上来就执行的 Agent，往往是在猜。先让它问三个问题，再让它复述一遍计划，比你事后纠正五轮便宜。

## 四、把成功的一次对话存成技能

第四条最值钱：每回 AI 干成一件事，就说一句“把刚才这套方法，存成技能”。下次只要说“整理会议纪要”，它就知道按你的格式来。技能还要备份到 GitHub，相当于攒公司资产。

这就是“轨迹转技能”。视频里把它比作“AI 写 AI 的操作手册”，这个说法不夸张：技能就是 Agent 的操作手册。一次成功对话里，可复用的资产是：什么时候触发、先做什么、用哪些工具、输出什么格式、遇到什么情况停下来、怎么验证。把这些写成 `SKILL.md`，放进 Git，设计上可以跨 Agent 复用，前提是目标工具支持同类技能格式。

pstack 和 cursor-team-kit 把这件事做成了流程。`/reflect` 会扫当前会话，找可复用的经验，分给三个 reviewer 从判断、工具、发散三个角度看，再合成一份“接受/拒绝/待办”的清单；它不会自动改技能，要你批准。`/automate-me` 会从你最近的对话里挖出工作习惯，草拟一个属于你的 `-mode` 技能。`workflow-from-chats` 则明确说：不要总结聊天，要抽取可复用的工作流指导。

技能要写成可执行的，不是写成鸡汤。至少包含：触发条件、步骤、工具、输出契约、失败模式、验证方式。只写顺利路径的技能，第一次遇到异常就会露馅。

也别把每一次成功都存成技能。一次性的任务存下来是噪音。判断标准很简单：这个路径下个月还会不会重复？换一个类似任务还能不能用？答案是否，就不要进技能库。

## 五、给 AI 独立账号和身份，产物分开

第五条听起来最像“给 AI 发工牌”：她让 AI 自己去注册工作要用的公司内部平台账号，干完活直接提交；AI 的东西和你的东西分开，出了问题好排查。她甚至说“连工牌都发了”，把自己当成 AI 的调度员和传话的。

这段话容易被读成“让 Agent 无法无天”。实际要抓的是三件事：身份、权限、审计。

身份：不要让 Agent 跑在你的个人会话里。用服务账号，或者一个专门的工作区。产物放在独立的分支、目录或命名空间，和人的东西分开。这样回滚、对比、清理都简单。

权限：最小权限，短期凭证，不可逆操作前停下来。注册账号、接受条款、改生产数据，这些不是 Agent 应该自己决定的事。pstack 的 `poteto-mode` 里也写得很清楚：可逆的外部动作可以直接做，force-push、部署、删数据、给客户发消息必须暂停。

审计：每一次工具调用、每一个产物、每一次人工确认，都要留下记录。视频里的“工牌”是个好比喻，但工牌背后是凭证和审计，不是自治权。给 Agent 发工牌，不等于给它签字权。

## 六、别再手动搬运信息

第六条是一个触发器：只要你还在手动把一段信息从这儿挪到那儿，就反过来问 AI——这一步你怎么帮我解决？要么搭自动流程，要么建技能。

知识工作里有大量时间花在搬运上：从邮件搬到表格，从表格搬到文档，从文档搬到群消息。人做这些事容易错、容易烦、难以审计。Agent 适合做，但要用对形态。

路径固定、规则清楚的，用 Workflow：定时任务、webhook、队列、脚本。路径需要判断的，用 Agentic 交接：上一个 Agent 产出结构化结果，下一个 Agent 读取后决定下一步。视频里的“抓资讯的 AI 再调给创作的 AI”就是后者；放到生产里，两个 Agent 之间最好有 schema、有队列、有重试、有死信，而不是一段自由文本。还有一个更日常的例子：用语音说个回信的大概意思，AI 把邮件写出来，确认后发出去。

工具层要可调用、可观测。CLI 最好支持 `--json`，API 要有明确的错误码，写操作要幂等。pstack 配套的 `control-cli` 和 `control-ui`（在 cursor-team-kit 里）就是干这个的：前者驱动 CLI/TUI，后者通过浏览器/CDP 驱动 Web 或 Electron UI，截屏、读控制台、走用户路径。`verify-this` 再把这些证据变成 baseline 和 treatment 的对比。

自动化没有日志，比手动更糟。手动至少知道是谁点的；自动跑飞了，你连哪一步错了都不知道。每一个交接都要能重放。

## 七、用语音输入，再让 AI 复述

最后一条最轻，但很实用：安排任务直接开语音，三两句把事交代完；全部说完，补一句“用你自己的话，复述一遍”。这样它到底听没听懂、有没有要补充的，你马上就知道；还能一次把来龙去脉喂给 AI，返工也少。

语音降低的是输入摩擦。打字的时候人会不自觉地压缩上下文，说话的时候更容易把背景、例外、担心的事一起说出来。对 Agent 来说，这些“废话”往往决定输出质量。

复述则是廉价的语义检查。让它按固定结构复述：目标、约束、不做什么、验收标准、待确认的问题。你确认一遍，再让它动手。这一步是 HITL，不是形式主义；它把“理解错”从事后返工变成事前拦截。

但复述不是验证。它只证明 Agent 说对了，不证明它做对了。输出验证还是要落到测试、截图、日志、基线对比上。语音转写也有噪音，人名、数字、专有名词容易错；关键参数要让它回读确认，不可逆操作要有书面确认。

## 视频没讲透的部分：验证护栏

七条方法讲的是“怎么带人”，但让这套东西成立的，是“怎么验收”。视频画面里展示的那篇工作坊文章有一句话，大意是：她敢放手，不是因为模型变聪明了，而是因为验证机制和工程护栏先变硬了。

那篇文章把她的编组方式分成三层。第一层是协调层：幕僚长 Agent 不写代码，只负责理解任务、拆解工作、分派角色、跟踪进度；她同时跑十多个协调器，一个盯桌面端性能，一个处理 Bug 报告。第二层是执行层：10 到 20 个专才 Agent，分别负责移动端、桌面端、基础设施、测试框架。第三层是编排指令：`/poteto-mode` 按任务类型选 playbook，再调用 `/loop` 迭代、`/goal` 跟踪长期目标、`/swarm` 并行分片、`/arena` 多方案竞争、`/interrogate` 多模型交叉评审。

这套结构里，Agentic 和 Workflow 的分工很清楚。拆解、定位根因、处理异常，是 Agentic；跑测试、截屏、对比基线、提交 PR，是 Workflow；不可逆操作前停下来，是 HITL。不要让一个 Agentic 循环去干本该由脚本干的确定性步骤，也不要指望一个 Workflow 处理它没见过的异常。

验证工具是具体的。`control-ui` 通过浏览器或 CDP 驱动真实界面，点击、输入、截图、读控制台；`control-cli` 驱动 CLI/TUI；`verify-this` 把 claim（待验证的断言）改写成可证伪的形式，采 baseline 和 treatment（基线/处理组），最后只给三个结论：VERIFIED、NOT VERIFIED、INCONCLUSIVE。`interrogate` 让多个模型各自审同一份 diff，模型之间的一致性是高信号。`arena` 并行跑多个方案，再挑最好的部分。

pstack 的目标不是让 Agent 写更多代码。README 的原话是：write less, but higher quality code。它的原则里有 prove-it-works、fix-root-causes、sequence-verifiable-units、encode-lessons-in-structure。翻译成大白话：先证明，再交付；修根因，不打补丁；把工作切成可验证的小块；同样的错误第二次出现，就写成结构，不要写成提醒。

这也是“一个人带很多 AI”的门槛。不是模型能不能同时跑 50 个，而是你有没有 50 份可验证的验收标准。没有后者，数量只是噪音。

## 两周落地清单

如果你想把七条方法用起来，不要一上来搭“AI 团队”。先做一个任务，跑通一圈。

| 时间 | 做什么 | 产出 |
|---|---|---|
| 第 1 天 | 选一个每周重复、输出清楚、验证便宜的任务 | 一页岗位卡：目标、职责、工具、边界、输出格式 |
| 第 2-3 天 | 用语音交代任务，让它复述，再执行 | 一份任务 brief，一份对话记录 |
| 第 4 天 | 把成功路径写成技能 | `SKILL.md`：触发、步骤、工具、输出契约、失败模式、验证 |
| 第 2 周 | 加一个验证护栏和一个交接自动化 | 测试/截图/日志脚本；一个服务账号或独立工作区 |

衡量指标也换一下。不要看跑了多少个 Agent、用了多少 token、写了多少行代码。看五个数：返工率、首次可用产出时间、验证通过率、技能复用次数、人工接管次数。返工率、首次可用产出时间、人工接管次数应该降；验证通过率、技能复用次数应该升。

三条不要：不要在验证之前扩 Agent 数量；不要让 Agent 用你的个人账号做不可逆操作；不要把一次性的成功当成可复用技能。

## 结论

七条方法之所以好记，是因为它们把人和 AI 的关系从“问工具”改成了“带团队”。视频最后有一句话：你把 AI 当工具，AI 就给你打工；你把 AI 当员工，AI 就给你干事。但团队不是人多就叫团队。没有岗位定义、没有技能沉淀、没有权限边界、没有质量门禁，那只是一群人。

发生变化的是六个东西：prompt 变成岗位卡，一次性对话变成技能，输出变成可验证的产物，个人账号变成受限身份，手动搬运变成工作流，语音输入变成结构化 brief。

“把 AI 当员工”只在你也像管理者一样工作时才成立：定范围、给上下文、设质量门、看结果、承担最后的责任。Agent 可以替你执行，不能替你负责。

如果你明天只做一件事，选一个每周重复、输出可验证的任务，写下它的岗位卡，然后让 AI 用自己的话复述一遍。
