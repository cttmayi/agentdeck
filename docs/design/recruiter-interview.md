# 从要求生成智能体（含 AI 起草的配套技能）+ 访谈官 设计

> 状态：**设计稿，未实作**。配套决策记录：实现时补 D 号（`docs/srs/requirements.md` §16）。
> 需求来源：使用者 2026-11-09 读完《把 AI 当员工：Lauren Tan 的七条工作法》后提出
> 「先设计 招聘官访谈」。文章的七条之一（原文第 1 条）：**第一个 AI 不干活，先当
> "招聘官"**——先问清"你是谁、你要什么、边界在哪"，再生成一张**岗位卡**（目标 /
> 职责 / 工具 / 边界 / 输出格式）；岗位卡是**草稿不是合同**，尤其要审"不能做什么"
> 那一栏。
> 使用者五轮定稿（2026-11-09）：
> ① 两步走、两步无连接；
> ② 第 2 步必须有 AI 起草（"还会通过智能体动态生成智能体吗——我的理解要"）；
> ③ 第 2 步与第 1 步解耦、栏位最少、用户可以直接做第 2 步（"提要求去生成智能体"）；
> ④ 功能 A 独立（"如果需求，我觉得不应该复用现有表单"→ 选「选项 2：独立」）；
> ⑤ **产出仍是智能体，技能不是外挂勾选、是 AI 起草的**："我的意思是还是生成
>    智能体（但智能体内可包括 SKILL，不是外挂的，是 AI 自己起草的）"——生成
>    智能体的同时，AI 把它的配套技能也起草出来，一起审阅、一起确认。

## 1. 背景与目标

现状：新建智能体是**填表**，技能是**勾选挂载已有**的。使用者要的是：**从一段要求
生成智能体**，而且智能体**自带 AI 起草的配套技能**——要求里隐含的可复用做法
（输出格式、处理流程等），由 AI 在起草时一起写出来，不是从技能库里挑现成的挂上。

**最终形态（两个独立功能，互不连接）**：

```
┌─ 功能 A：从要求生成智能体（独立面板）─────────────────────┐
│  写一段要求 → AI 起草 → 审阅 → 确认生成                    │
│  草稿 = 智能体（名称/角色/指令）+ 配套技能草稿（AI 起草）   │
│  确认 = 创建智能体（skillIds 挂新技能）+ 技能沉淀（共享）   │
└──────────────────────────────────────────────────────────┘
┌─ 功能 B：访谈官（可选，独立）───────────────────────────┐
│  聊天页与访谈官对话，理清"目标/职责/边界/输出格式"         │
│  产出「岗位卡方向」仅作参考（想用就抄进功能 A 的要求框）   │
└──────────────────────────────────────────────────────────┘
```

**配套技能的含义**：智能体草稿里带 0..N 条技能草稿，每条都是 AI 从要求里识别出的
可复用做法（如"会议纪要三段格式"）。它们随智能体一起审阅、一起确认——**不是外挂
已有技能，是这次生成的一部分**。技能落库后仍是平台的普通技能（共享资产，
skills-mine + git），任何智能体都能挂；"私有技能"概念 v1 不做（§3.7）。

## 2. 为什么功能 A 独立、不复用新建表单（2026-11 使用者定稿）

1. **生成器 ≠ 保存表单**：功能 A 是"要求 → 草稿 → 审阅 → 确认"的生成流程，
   产出不止一个对象（智能体 + 配套技能）；复用"新建智能体"表单，配套技能无处
   安放（或硬塞进去，把表单搞成四不像）。
2. **独立接口族**（与"接口独立"拍板一致）：面板只管生成这一段，创建动作仍走
   现有端点，不复制逻辑。

## 3. 功能 A：从要求生成智能体（独立面板）

### 3.1 入口与交互

智能体页「新建智能体」旁加「**从要求生成**」入口 → 独立面板（页面内弹层即可）：

```
[ 一段话写你要什么：做什么 / 输出长什么样 / 绝不能碰什么…… ]
[ 由 AI 起草 ]
        ↓ 起草 run
[ 审阅区：智能体部分 + 配套技能部分（0..N 条，AI 起草）] [ 素材摘要 / RunLog ]
[ 确认生成：创建智能体 + 技能沉淀 ]
```

- 要求框纯文本，一两句到一段都行。
- 不满意 → 改要求 → 再「由 AI 起草」：素材更新为新要求，旧草稿覆盖（与沉淀
  "重新起草"同规矩）；起草失败 → RunLog 报错、可重试、不预填草稿。

### 3.2 起草：一次智能体起草 + 按需的配套技能起草

一个 requirement 记录发起两类 run（都在本面板展示，RunLog 常驻）：

1. **agent-draft run**（subject `agent-draft`，`entities.ts` 枚举加值，§4.1.3 已
   预留；执行者 = 内置「岗位卡起草者」`card-drafter`）→ 产出 `agent-draft.md`：
   frontmatter（name/role）+ 正文一段指令（**必须有边界段**，要求没提边界时写
   最小权限缺省段），末尾一节 **「配套技能」清单**（0..N 条：slug / name /
   一句描述——它认为要求里哪些做法值得抽成技能；认为没有就 0 条）。
2. **按清单逐个发起 skill-draft run**（subject `skill-draft`，**现有**机制；执行者 =
   **现有沉淀起草者**，挂 distilly，技能写作规范正好对口）→ 每条产出 `SKILL.md`
   （slug/name/description/body，同沉淀草稿）。素材 = `00-要求.md` +
   agent-draft.md 里那条配套技能的说明（沉淀素材源从 run 扩展到要求文本，§5）。

配套技能**数量由起草者按要求判断**，不是每单必带；用户审阅时可删可改可加。

### 3.3 素材（一条纪律：起草者唯一依据 = 要求文本）

```
requirement-<id>/
  material/
    meta.json     ← 来源（requirement）、创建时间
    00-要求.md    ← 要求框里的那段话（原样落盘）
```

起草者只读 00-要求.md，不许编。要求没说清的部分，草稿相应处标「待补：xxx」并写清
缺什么——与沉淀"不结晶清单"同一纪律。

### 3.4 智能体起草者 = 内置「岗位卡起草者」（三条证据，早前已定稿）

为什么不用沉淀的起草者写智能体：① 其身份在第 191 批**有意**收窄成"只干一件事"
（"把素材写成一条可复用的 skill"），写智能体 = 身份与任务书打架（第 51 批教训）；
② 其挂 `distilly`（SKILL 写作规范）——对智能体草稿是错误注入，而注入不能按
subject 分叉（第二份真相）；③ 仓库内置模式 = "一个岗位一条内置 + 专属 role +
不进业务选择"（memory-tidy 先例）。
配套技能的 skill-draft run 则正好由它干（身份对口）——**两个内置各司其职，
不互相越界**。

### 3.5 审阅（栏位最少，两部分）

- **智能体部分**：名称 / 角色 / 指令（一段，边界在段内，下方提示「草稿不是合同——
  检查『边界』段」，提示不是校验）。
- **配套技能部分**：每条技能一行块（slug / name / description / body，复用沉淀
  草稿审阅骨架），每条顶部一行提示：「此技能草稿来自要求，**未经验证**——建议
  先让智能体干几轮，再用沉淀结晶正式版」（提示不是校验）。可删（不需要这条）、
  可改。
- 已有技能可另勾选挂载（可选，不是主线——主线是 AI 起草的配套技能）。

### 3.6 确认生成（人确认是唯一入口）

- `POST /api/agents`：name/role/instructions，`skillIds` = 配套新技能 + 用户另勾
  的已有技能。动作权限不落智能体（属于组）。
- 每条配套技能走**沉淀 commit** → 落 `skills-mine` + git（共享，可被其他智能体
  挂载）。
- 顺序：先沉淀技能、再建智能体（智能体的 skillIds 要指向已存在的技能）。
- requirement / 草稿记录存着可复查，不自动删，不关联（不加死字段）。

### 3.7 技能是共享资产，不是私有（平台定性，v1 不变）

配套技能落库后和所有技能一样：磁盘 `skillsRoot`、mine 进 `skills-mine` git、
任何智能体都能挂。**不做"仅此智能体可用"的私有技能**：技能是共享资产是平台
定性（文章第 4 条也是"存成 SKILL 进 Git"共享），私有化是新面（新存储 + 新的注入
通道 + git 处理），v1 为"配套技能"付出整个私有面不值。若使用者要私有技能，另起
设计再议。

## 4. 功能 B：访谈官（可选，独立，聊天页找方向）

### 4.1 是什么

平台内置智能体「访谈官（内置）」，角色 `interviewer`。聊天页「新对话」下拉可直接
选它开对话。**独立功能**：聊出的「岗位卡方向」只是参考——想用就抄进功能 A 的要求
框，不想就自己写。没有按钮、没有传递、没有连接。

### 4.2 角色放行（两处小改，都有测试钉住）

聊天目前只接受 `role === 'executor'`。放行 `interviewer` 两处：

| 位置 | 改动 | 钉住 |
|---|---|---|
| `apps/daemon/src/server.ts` conversations POST | 角色判据放行 `interviewer`，WHY 注释："访谈官只访谈不干活，聊天的产出是方向不是判决" | `chat.test.ts` 加一条 |
| `apps/web/src/lib/chat.ts` `executorChoices` | 同款放行 | `chat.test.ts` 对应判据 |

新角色天然被业务选择的等值判断排除（不进组、不进任务），只有聊天这一处放行。

### 4.3 内置纪律（与 memory-tidy 同一套）

启动对账建出来、幂等/自愈/不许删、智能体页可见可编辑可恢复默认、历史版本逐字
冻结升级（第 248/249 批教训）、通用守则（`withConduct`）共用。

### 4.4 指令要点（只问不干）

1. 你是访谈官：帮人把"一个岗位"说清楚，**不干活**；用户派活引导回岗位本身。
2. 按岗位卡五字段追问：目标 → 职责（"每天最烦的活"）→ 输出格式（给例子）→
   **边界（必问，追问到说清为止，"没有"也要明说）** → 背景。
3. 边界为空时给最小权限缺省段，写进方向总结。
4. 问完输出「岗位卡方向」总结（§4.5）——用户表示聊够了之后才给，不主动结束。
5. 方向总结注明"草稿——建之前尤其要审『边界』"。

不用技能、记忆默认关（上一场访谈不污染下一场）。

### 4.5 「岗位卡方向」总结（给用户看的参考）

```markdown
## 岗位卡方向（草稿）
- 岗位名称：会议纪要助理
- 角色：executor
- 目标/职责：…… / 边界（不能碰，必审）：…… / 输出格式：……
- 验收标准：……
- 建议挂载技能：meeting-notes（已有）
```

用户抄进功能 A 的要求框时，原样粘贴或挑重点写——功能 A 只认要求框里的文本。

## 5. 与「沉淀」和「沉淀 Agent」（§4.1.3）的关系

- **配套技能 = 沉淀的"素材源扩展"**：沉淀现在从真实 run 收集素材；功能 A 的配套
  技能把素材源扩成"要求文本"（`00-要求.md` + 配套技能说明），起草/审阅/commit 全部
  复用 skill-draft 骨架，**不复制逻辑**。代价是技能未经验证（§1/§3.5 明说，审阅时
  提示）。
- **智能体 = §4.1.3「沉淀 Agent」的简化落地**：素材源是要求文本而不是对话，产出是
  新建智能体；将来沉淀页把「沉淀技能 / 沉淀智能体」并排时（§4.1.3），agent-draft +
  card-drafter 直接复用。

## 6. 界面改动

- 智能体页：「新建智能体」旁加「从要求生成」入口 → 独立面板（§3.1）。
- 聊天页：「新对话」下拉出现「访谈官（内置）」。
- 智能体页列表：出现「访谈官（内置）」与「岗位卡起草者（内置）」两条（可查看 /
  编辑 / 恢复默认，同 memory-tidy）。
- 审阅区复用沉淀页的草稿审阅骨架（素材摘要 + RunLog 常驻 + 恢复进行中）。

## 7. 测试策略

- **单测 / e2e**（假 AgentBackend，不烧真实 CLI）：
  - `POST /api/conversations` 接受 `interviewer`，仍拒绝 `reviewer`/`drafter`/
    `memory-tidy`（不回归）；`executorChoices` 包含 `interviewer`（`chat.test.ts` 钉住）；
  - **整链**：要求文本 → 素材落盘（原样）→ agent-draft run（fake card-drafter 产
    agent-draft.md，含配套技能清单）→ 配套技能 skill-draft runs（fake 沉淀起草者产
    SKILL.md）→ 审阅（改边界、删一条技能）→ 确认 → 断言 `GET /api/agents` 新智能体
    的 skillIds = 已沉淀技能、技能落 `skills-mine` + git、字段与草稿一致；
  - **配套技能为 0 条**时只建智能体（无技能 run）；
  - **要求没提边界时**智能体草稿含最小权限缺省段；
  - **独立性**：不用访谈也能生成；访谈对话不会自动触发生成；
  - 内置对账（两条新内置）：启动建出来、可恢复默认、历史版本冻结、不进业务选择
    （补进 `agents-create` 判据）。
- **探针**（`probe:layout`）：独立面板（要求块、起草、两段审阅区）；聊天下拉有
  「访谈官」。

## 8. 协议草案（独立接口族，实现时定细节）

| 端点 | 说明 |
|---|---|
| `POST /api/requirements` `{text}` | 建 requirement 记录 + 素材落盘 + 发起 agent-draft run，返回 runId |
| `GET /api/requirements/:id` | 要求 + 各 run 状态 + 智能体草稿 + 配套技能草稿 + RunLog |
| `POST /api/requirements/:id/skills` `{slugs}` | 按配套技能清单发起 skill-draft runs（或 agent-draft run 完成时自动发起，实现时定） |
| `PATCH /api/requirements/:id/draft` | 审阅修改（草稿修订） |
| `POST /api/requirements/:id/commit` `{finalDraft, skillIds}` | 人确认：先沉淀配套技能（复用沉淀 commit），再 `POST /api/agents`（skillIds 挂新技能 + 勾选已有） |

创建动作仍走现有端点（智能体 `POST /api/agents`、技能沉淀 commit），独立接口族只
负责"要求 → 草稿 → 审阅 → 确认"这一段，不复制创建逻辑。

## 9. 边界与风险

1. **配套技能未经验证（拍板取舍）**：AI 从要求起草的技能草稿没有真实 run 背书。
   审阅时明示"未经验证"（提示不是校验）；要正式版走沉淀。写进这里防将来有人
   忘了为什么。
2. **配套技能数量由 AI 判断**：0..N 条；用户可删可改可加。不给"必须带技能"的
   校验——要求没有可复用做法时 0 条是合法的。
3. **token 成本**：一次生成 = 一次 agent-draft run + 按需的 skill-draft runs；访谈
   另算（可选）。
4. **草稿不是合同**：AI 只起草，确认（commit）是唯一入口；"检查边界段 / 未经验证"
   是提示不是校验。
5. **内置角色纪律**：`interviewer` / `card-drafter` 不进业务选择（等值判断天然
   排除）；聊天放行只改 `interviewer` 那两处、各带 WHY 注释；配套技能 run 用现有
   沉淀起草者，不新开。
6. **技能是共享资产**：配套技能落库后任何智能体可挂；私有技能概念 v1 不做（§3.7）。
7. **两个功能独立是拍板行为**：不加任何"访谈 → 生成"的传递。
