# 智能体生成者（聊天页）+ 配套技能 设计

> 状态：**设计稿，未实作**。配套决策记录：实现时补 D 号（`docs/srs/requirements.md` §16）。
> 需求来源：使用者 2026-11-09 读完《把 AI 当员工：Lauren Tan 的七条工作法》后提出
> 「先设计 招聘官访谈」。文章的七条之一（原文第 1 条）：**第一个 AI 不干活，先当
> "招聘官"**——先问清"你是谁、你要什么、边界在哪"，再生成一张**岗位卡**（目标 /
> 职责 / 工具 / 边界 / 输出格式）；岗位卡是**草稿不是合同**，尤其要审"不能做什么"
> 那一栏。
> 使用者七轮定稿（2026-11-09）：
> ①–⑥：两步无连接 → 第 2 步有 AI 起草 → 独立 → 产出智能体 + AI 起草的配套技能
> （不是外挂勾选）→ 全部改到聊天页（工作目录 `agent/` 侦测出按钮）。
> ⑦ **中心是一个「智能体生成者」智能体**："用户在聊天界面聊天，相关的规则都需要
>    在智能体生成者去描述，而不是让用户来描述。智能体生成者可以包括几个你认为
>    重要的市场技能……可以和沉淀起草者一样，动态安装。"

## 1. 背景与目标

**中心形态（第七轮定稿）**：

```
聊天页「新对话」选「智能体生成者（内置）」→ 聊天
  它问（岗位卡五字段），你答
  它自己描述规则（目标/职责/边界/输出格式/验收）——不是让你写规则，你只确认
  它挂几个平台技能（动态安装，同沉淀起草者挂 distilly）
  聊完 → 产出「岗位卡（草稿）」（写进工作目录 agent-draft.md）+ 配套技能草稿
        （skill/<slug>/SKILL.md）
        ↓ 栏头出现「确认生成智能体」按钮
  审阅面板（岗位卡 + 配套技能，边界必审，人可改）→ 确认
        ↓
  先沉淀配套技能（生成者起草的 SKILL.md 直接过审落 mine+git）→ 再创建智能体
  （skillIds 挂新技能）
```

- **规则由生成者描述**：边界、输出格式、职责……是它提出、你确认，不是你在表单
  或目录里写——这最贴文章"招聘官"的形态（它挖，你答）。
- **生成者挂技能**：几个我推荐的平台技能（§4），**动态安装**（与沉淀起草者挂
  `distilly` 同一机制：启动对账时保证技能已安装进 skillsRoot）。
- **取代两个内置**：「访谈官」（只问不干）与「岗位卡起草者」（只写岗位卡）被
  **智能体生成者**吸收合并——它既问又起草，一个内置、一个角色、一个入口。
- **配套技能与岗位卡同一场确认**：生成者按 skill-eligibility 判定、在聊天里起草
  `skill/<slug>/SKILL.md`（§3.4），确认时与岗位卡一起过审、一起沉淀
  （§3.6 v1 拍板：不走 skill-draft run），落 mine+git 共享。

## 2. 为什么合并成「智能体生成者」（2026-11 使用者第七轮定稿）

前六轮把"问"（访谈官）和"写"（岗位卡起草者）拆成两个内置。使用者拍板合并：

1. **问和写是同一个人干的活**：招聘官问完就该出卡——拆成两个角色，中间还得靠
   "岗位卡方向 → 素材 → 起草 run"传递，绕（正是第 ① 轮"太绕"的教训回来找）。
2. **规则由它描述**：拆开时"方向总结"要用户抄/或当素材；合并后生成者在对话里
   直接描述规则，用户只确认，没有传递。
3. **一个智能体一个角色**：仓库内置模式本来就是"一个岗位一条内置 + 专属 role"；
   生成者 = "帮人把岗位说清楚并写下来"，一条内置正好。

**因此删除**：`interviewer` 访谈官、`card-drafter` 岗位卡起草者。**新增**：内置
「智能体生成者」，角色 `agent-maker`（聊天放行 + 业务选择天然排除）。

## 3. 智能体生成者（内置，聊天页）

### 3.1 角色与放行

- 内置智能体「智能体生成者（内置）」，角色 `agent-maker`。
- 聊天页「新对话」下拉可选（与执行者并列）。
- 放行两处（测试钉住，与早前 `interviewer` 放行相同）：

| 位置 | 改动 |
|---|---|
| `apps/daemon/src/server.ts` conversations POST | 角色判据放行 `agent-maker`，WHY 注释："生成者只在聊天里问和起草，不干业务活，聊天的产出是岗位卡" |
| `apps/web/src/lib/chat.ts` `executorChoices` | 同款放行 |

- 业务选择天然排除（`role === 'executor'` / `'reviewer'` 等值判断不认它），不进组、
  不进任务选择器。
- 内置纪律与 memory-tidy 同一套：启动对账建出来、幂等/自愈/不许删、可见可编辑可
  恢复默认、历史版本逐字冻结升级（第 248/249 批教训）、通用守则（`withConduct`）共用。

### 3.2 聊天行为（只问只写，不干活）

1. **你是智能体生成者：帮人把"一个岗位"说清楚并写下来，不干活**。用户派活/
   求产出，引导回岗位本身。
2. **按岗位卡五字段问**：目标（做什么）→ 职责（最常被叫去干的活）→ 输出格式
   （给例子）→ **边界（必问，追问到说清为止，"没有"也要明说）** → 背景。
3. **规则由你描述，不是让用户写**：每个字段你提出草稿（"我建议的目标是……"、
   "我建议的边界是……"），用户确认或修正——**用户只回答、只确认，不写规则**。
4. **边界段必有**：用户没说边界时，给出最小权限缺省段（不触发不可逆操作 /
   拿不准先停下 / 只在工作目录动手），写进岗位卡。"没有边界"也是缺省最小权限，
   不是漏填。
5. 用户表示聊够后，产出「岗位卡（草稿）」（§3.4 写入工作目录）+ **配套技能草稿**
   （0..N 条：它按 skill-eligibility 判定哪些做法值得抽成技能；没有就 0 条——
   **逐条写成 `skill/<slug>/SKILL.md`**，与岗位卡同一份产出、同一场确认）。
6. 岗位卡注明"草稿——确认前尤其要审『边界』"。

### 3.3 挂载技能（动态安装，同沉淀起草者挂 distilly）

智能体生成者挂 **3 个平台内置技能**（§4 推荐），由 `ensureBuiltinAgentMaker`
启动对账时**动态安装**进 `skillsRoot`（与 `DRAFTER_SKILL_SLUG`/distilly 同一机制：
平台技能随仓库分发，ensure 时复制安装，幂等）。生成者聊天/起草时这些技能作为
规范注入。

### 3.4 产出：岗位卡（草稿）+ 配套技能草稿

聊天结束（用户确认规则）后，生成者在工作目录写：

```
conversation-<id>/
  agent-draft.md     ← 岗位卡（草稿），分节：
                       frontmatter: name / role
                       ## 目标 / ## 职责 / ## 边界（不能碰）/ ## 输出格式
                       ## 验收标准
  skill/<slug>/SKILL.md   ← 配套技能草稿（0..N 条，逐条一个子目录；
                           没有就 0 条，不写任何技能文件）
```

岗位卡 = 生成者在对话里已逐条描述并被用户确认的规则，**落盘一份**，确认生成时
平台读它（可复现、可 diff、可重新聊天再写）。配套技能同理：草稿落盘在
`skill/<slug>/SKILL.md`，确认时与岗位卡一起过审一起沉淀（§3.6）。

### 3.5 素材（可选）：工作目录 `agent/` 目录

用户可以在工作目录放一个 `agent/` 目录（资料 / 示例 / 参考文档），生成者聊天时
会读它（第六轮的侦测保留：工作目录顶层有 `agent/` 时生成者引用；没有也行——规则
由生成者从对话挖）。`agent/` 是**素材不是规则来源**——规则只由生成者描述。

### 3.6 确认生成（按钮 → 内联审阅 → 确认）

- 侦测：对话工作目录顶层出现 `agent-draft.md`（岗位卡产出）→ 栏头（「沉淀技能」
  旁）出现「**确认生成智能体**」按钮；没有就不出现（与沉淀技能按钮同一模式，
  不搞置灰——没有素材时置灰按钮是一种半开的门，§9.7）。
- 点按钮 → 聊天页弹出审阅面板（Modal，尺寸 wide）：
  - **岗位卡部分**：名称 / 角色 / 指令（一段，边界在段内），**人可改**；提示
    「草稿不是合同——检查『边界』段」（提示不是校验）；
  - **配套技能部分**：每条技能一块（slug/name/description/SKILL.md 正文，来自
    工作目录 `skill/<slug>/SKILL.md`），黄条提示「未经验证——建议先让智能体干
    几轮，再用沉淀结晶正式版」（提示不是校验）；可删可改；
  - 打开时 `GET /api/conversations/:id/agent-draft` 读一次；确认成功后面板内显示
    结果（不自动关，可关）。
- 确认 = 人确认是唯一入口（`POST /api/conversations/:id/agent-commit`）：
  1. **配套技能直接沉淀**（v1 拍板：不走 skill-draft run）：生成者在聊天里按
     skill-eligibility 起草 `skill/<slug>/SKILL.md`（配套技能 = 生成产物的另一半，
     与岗位卡一起在审阅面板里确认）→ 确认时逐条过 `resolvePayloadEntry` 同一关、
     落 `skills-mine`（source `mine`，sourceRef `mine:<slug>`）+ git（共享）；
     同名 mine 已存在 ⇒ 409（与沉淀新建同一口径，不静默覆盖）；
  2. 创建智能体：name/role/instructions（岗位卡 frontmatter + 正文），`skillIds`
     = 本次沉淀的配套技能。先沉淀技能、再建智能体（skillIds 指向已存在的技能）。
  服务端重解析岗位卡与 SKILL.md（不信任客户端分开传来的字段）。

> **v1 为什么不走 skill-draft run**：配套技能是"生成者一边问一边起草"的产物，
> 与岗位卡是**同一次生成的同一份产出**——拆成"确认岗位卡 → 再起一条 skill-draft
> run 由沉淀起草者写技能"等于把一次生成切成两段多轮编排，且 skill 草稿与岗位卡
> 之间的对应要跨 run 传递。直接由生成者在聊天里起草（规则由它描述，§1），确认时
> 一起过审一起落库，是"生成智能体"这一条链最短的路径；未经验证由 §9.1 明示。

### 3.7 技能是共享资产，不是私有（平台定性，v1 不变）

配套技能落库后和所有技能一样（`skillsRoot`、mine 进 git、任何智能体可挂）。私有
技能概念 v1 不做（新存储 + 新注入通道 + git 处理，为配套技能付出整个私有面不值）；
要私有，另起设计再议。

## 4. 推荐的挂载技能（使用者点名"你给我推荐"）

智能体生成者动态安装 **3 个平台内置技能**（与 distilly 同分发机制，离线可用、
版本可控；将来使用者也可从技能市场装更多再挂上）：

| slug | 名称 | 用途（为什么重要） |
|---|---|---|
| `agent-design-norms` | 智能体设计规范 | 岗位卡五字段结构、指令 = 目标+职责+边界+输出格式一段组装（第一句话只有一个注入位，D29）、验收标准写法。保证生成者产出的岗位卡稳定可解析 |
| `boundary-checklist` | 边界自检清单 | 边界段必含项：不可逆操作（删除/覆盖/对外发送/改他人文件）、拿不准先停下、只在工作目录动手、"没有边界也要明说"。保证边界段不缺项——文章最强调"不能做什么" |
| `skill-eligibility` | 配套技能判定 | 哪些做法值得抽成配套技能（高频 / 同格式 / 跨任务可复用）、何时 0 条、输出格式与技能的关系。保证配套技能不硬凑（访谈答案是需求不是经验） |

这三条是"生成者的手则"——挂在它身上（注入），而不是写死在指令里（可独立演进、
可被使用者编辑替换、与 distilly 同一条"规范走技能不走指令"的路）。

## 5. 与「沉淀」和「沉淀 Agent」（§4.1.3）的关系

- **配套技能 = 生成产物的另一半**：生成者在聊天里起草 `skill/<slug>/SKILL.md`
  （skill-eligibility 判定哪些值得抽），确认时随岗位卡一起过 `resolvePayloadEntry`
  同一关、直接沉淀（§3.6 那条 v1 拍板）——**不复制 skill-draft 骨架、不开第二条
  run**；技能未经验证（§3.6 提示）。
- **智能体 = §4.1.3「沉淀 Agent」的落地**：从对话（run）产出智能体指令；将来沉淀
  页把「沉淀技能 / 沉淀智能体」并排时，agent-draft 机制直接复用。
- **聊天本身就是一个 run**：对话（executor run）是素材来源，与沉淀"从 run 结晶"
  同构——不另开投递通道（D29）。

## 7. 测试策略

- **单测 / e2e**（假 AgentBackend，不烧真实 CLI）：
  - `POST /api/conversations` 接受 `agent-maker`，仍拒绝 `reviewer`/`drafter`/
    `memory-tidy`（不回归）；`executorChoices` 包含 `agent-maker`（`chat.test.ts` 钉住）；
  - **内置对账**：生成者启动建出来、可恢复默认、历史版本冻结、不进业务选择
    （补进 `agents-create` 判据）；**挂载技能动态安装**（3 条平台技能 ensure 进
    skillsRoot，幂等）；
  - **整链**：fake 生成者聊天产出岗位卡（写 agent-draft.md + `skill/<slug>/SKILL.md`）→
    按钮出现（`hasAgentDraft`）→ 审阅（改边界、删一条技能）→ 确认 → 断言配套技能
    落 `skills-mine` + git、`GET /api/agents` 新智能体 skillIds 指向已沉淀技能；
  - **规则由生成者描述**：fake 生成者的对话轮次里包含"我建议的边界是……"，
    用户只确认（e2e 断言岗位卡边界段来自生成者描述，不是用户输入原文）；
  - **边界缺省**：用户没说边界时岗位卡含最小权限缺省段；
  - **配套技能为 0 条**时只建智能体。
- **探针**（`probe:layout`）：聊天下拉有「智能体生成者」；工作目录有 agent-draft.md
  时按钮出现；审阅面板两段渲染。

## 8. 协议草案（实现时定细节）

| 端点 | 说明 |
|---|---|
| `GET /api/conversations/:id` | 详情带 `hasAgentDraft`（工作目录顶层有 agent-draft.md 的侦测） |
| `GET /api/conversations/:id/agent-draft` | 生成产物：`{agentDraft: string|null, skills: [{slug,name,description,body}]}`（agent-draft.md + `skill/<slug>/SKILL.md` 解析） |
| `POST /api/conversations/:id/agent-commit` `{agentDraft, skills:[{slug,body}]}` | 人确认：岗位卡重解析校验 → 配套技能逐条 `resolvePayloadEntry` 落 `skills-mine` + git → 创建智能体（skillIds = 本次配套技能）。非 `agent-maker` 对话 ⇒ 400 `agent_commit_not_maker` |

创建动作仍走现有端点（智能体 `POST /api/agents` 同批字段、技能沉淀 commit 同
`resolvePayloadEntry`），新接口只负责"岗位卡 → 配套技能 → 确认"这一段，不复制
创建逻辑。

## 9. 边界与风险

1. **配套技能未经验证（拍板取舍）**：AI 起草的技能草稿没有真实 run 背书。审阅时
   明示"未经验证"（提示不是校验）；正式版走沉淀。
2. **规则由生成者描述 ≠ 生成者自作主张**：它提出、用户确认；边界段是必审项。
   岗位卡是草稿不是合同，确认（commit）是唯一入口。
3. **token 成本**：一次生成 = 一场对话 + 按需的 skill-draft runs，与"聊一场 +
   沉淀一次"同量级。
4. **内置角色纪律**：`agent-maker` 不进业务选择（等值判断天然排除）；聊天放行只
   改那两处、各带 WHY 注释；配套技能由生成者直接起草（§3.6 v1 拍板），不新开 run。
5. **技能是共享资产**：配套技能落库后任何智能体可挂；私有技能概念 v1 不做（§3.7）。
6. **挂载技能动态安装**：与 distilly 同机制（启动对账 ensure，幂等）；安装失败
   不阻塞聊天（降级为"无规范注入"，但生成者指令本身仍含五字段/边界要点——技能
   是强化不是唯一来源）。
7. **agent/ 目录是素材不是规则来源**：规则只由生成者描述；素材目录缺失不影响
   生成（生成者从对话挖）。
