# 生成智能体 + 访谈官（requirement-to-agent + interviewer）设计

> 状态：**设计稿，未实作**。配套决策记录：实现时补 D 号（`docs/srs/requirements.md` §16）。
> 需求来源：使用者 2026-11-09 读完《把 AI 当员工：Lauren Tan 的七条工作法》后提出
> 「先设计 招聘官访谈」。文章的七条之一（原文第 1 条）：**第一个 AI 不干活，先当
> "招聘官"**——先问清"你是谁、你要什么、边界在哪"，再生成一张**岗位卡**（目标 /
> 职责 / 工具 / 边界 / 输出格式）；岗位卡是**草稿不是合同**，尤其要审"不能做什么"
> 那一栏。
> 使用者三轮定稿（2026-11-09）：
> ① 两步走、两步无连接；
> ② 第 2 步必须有 AI 起草（"还会通过智能体动态生成智能体吗——我的理解要"）；
> ③ **第 2 步与第 1 步彻底解耦、栏位最少**："我其实不想第 1 步和第 2 步接起来，
>    甚至用户可以直接做第 2 步，在第 2 步提要求去生成智能体"。

## 1. 背景与目标

现状：新建智能体是**填表**（`NewAgentForm`：名称 / 角色 / 指令 / 挂技能 / 审核标准）。
表单把所有"组织上下文"压回使用者自己脑子里——它不问"你最烦哪些活、绝不许它碰什么"，
于是建出来的智能体只有两种下场：指令太泛（万能助手）、或边界没说（什么都接）。

文章给的解法：先访谈、后建卡；岗位卡是**给人看、可审、可改**的草稿。

**最终形态（两个独立功能，互不连接）**：

```
┌─ 功能 A：生成智能体（第 2 步，独立可用）───────────────┐
│  提要求（一段话） → AI 起草 → 简单审阅 → 确认创建        │
│  用户可以直接用它：想好要求就写，不用先访谈              │
└──────────────────────────────────────────────────────┘
┌─ 功能 B：访谈官（可选，独立）─────────────────────────┐
│  聊天页与访谈官对话，理清"目标/职责/边界/输出格式"       │
│  想理清方向才聊；聊出的「岗位卡方向」给用户参考          │
│  （想用就抄进功能 A 的要求框，不想用就不抄）             │
└──────────────────────────────────────────────────────┘
```

**不连接的确切含义**（使用者拍板）：功能 A 不需要先访谈，也不从访谈对话自动取素材；
功能 B 聊出的东西只是**给用户看的参考**。A 的素材只有用户自己提的那段要求。

## 2. 为什么放弃「两段式连接」方案（2026-11 使用者第三轮定稿）

上一版把第 2 步做成"对访谈对话点「生成智能体」→ 素材（方向总结 + 对话轮次）→
起草 → 六栏审阅表单"。使用者拍板再简化：

1. **第 1 步和第 2 步不该接起来**：访谈是"想清楚"的辅助，生成是"动手"的事——中间
   的素材收集、方向总结传递都是连接成本，而使用者明确不要连接。
2. **用户可以直接做第 2 步**：想好了要求的人不需要先聊一场。生成智能体要能
   **独立**用——提要求 → 生成。
3. **栏位最少**：六栏审阅表单（目标/职责/边界/输出格式/技能建议/验收标准）太重。
   草稿就是"名称 + 角色 + 一段指令"（边界/输出格式都在指令段里），人审一段文本
   就够了。

**因此本版不做**：访谈对话上的「生成智能体」按钮、方向总结当素材、对话轮次收集。
**本版保留**：素材纪律（要求文本落盘）、起草 run（`agent-draft`）、AI 起草 +
  人审阅 + 确认创建。

## 3. 功能 A：生成智能体（提要求 → AI 起草 → 简单审阅 → 创建）

### 3.1 入口与交互

智能体页「新建智能体」表单顶部加一块「**先写要求，让 AI 起草**」：

```
[ 一段话写这个岗位要什么：做什么、输出长什么样、绝不能碰什么……  ]
[ 由 AI 起草 ]
        ↓ 起草 run（岗位卡起草者）
[ 名称 ] [ 角色 ▾ ] [ 指令（一段，含边界段，可改）] [ 技能建议（可选勾选）]
[ 保存智能体 ]  ← 仍是现有 POST /api/agents
```

- 要求框是**纯文本**，一两句到一段都行（"会议纪要：分 decisions/owners/deadlines
  三段；不替人做决定；缺信息先问"）。
- 点「由 AI 起草」→ 起草 run → 表单的 名称/角色/指令/技能建议 被草稿填上。
- 人改一改 → 「保存智能体」——**保存是现有动作**，草稿只是预填。
- 不满意草稿 → 改要求再起草（可重来，与沉淀同规矩）。

### 3.2 素材（一条纪律：起草者唯一依据 = 要求文本）

```
agent-requirement-<id>/
  material/
    meta.json     ← 来源（agent-requirement）、创建时间
    00-要求.md    ← 用户在要求框里写的那段话（原样落盘）
```

起草者**只读 00-要求.md**，不许编。要求里没说清的部分，草稿相应处留"待补"并
写清缺什么——与沉淀"不结晶清单"同一纪律。

### 3.3 起草 run（AI 动态起草智能体）

- **subject**：`{ type: 'agent-draft', id: <requirementId> }`（`entities.ts` 枚举
  加 `'agent-draft'` 值，§4.1.3 已预留）。不在闭环、不挂 issue、不进任务列表。
- **执行者**：内置「岗位卡起草者」，角色 `card-drafter`。为什么不是沉淀的起草者
  （三条证据，早前已定稿）：
  1. 沉淀起草者身份在第 191 批**有意**收窄成"只干一件事"（"把素材写成一条可复用
     的 skill"）——复用它写智能体 = 身份与任务书打架（第 51 批教训）；
  2. 沉淀起草者**挂 `distilly`**（SKILL 写作规范）——对智能体草稿是错误注入，而
     注入不能按 subject 分叉（第二份真相）；
  3. 仓库内置模式 = "一个岗位一条内置 + 专属 role + 不进业务选择"（memory-tidy
     先例）。
- **产出**：智能体草稿 = **名称 + 角色 + 指令（一段 Markdown）**，指令内**必须有
  边界段**（要求没提边界时，写最小权限缺省段——"没有边界"是默认最小权限，不是
  漏填）。产出落成 `agent-draft.md`（frontmatter: name/role + 正文: instructions）。

### 3.4 审阅：栏位最少

表单只有：

| 栏位 | 说明 |
|---|---|
| 名称 | 草稿给出，可改 |
| 角色 | executor / reviewer，草稿给出，可改 |
| 指令（一段） | **边界/输出格式都在这一段里**；下方一行提示「草稿不是合同——检查『边界』段」（悬停提示文章原话），提示不是校验 |
| 技能建议 | **可选**，草稿建议的技能勾选（默认不勾也行，之后手动挂） |

砍掉的：目标/职责/输出格式/验收标准独立栏——它们进指令段（第一句话只有
`{{instructions}}` 一个注入位，本来就该是一段）。验收标准（reviewer 时）进指令
或之后由用户填审核标准栏（现有表单本来就有）。

### 3.5 创建

「保存智能体」= 现有 `POST /api/agents`（指令组装规则唯一一处：frontmatter 的
name/role + 正文 instructions）。动作权限不落智能体（属于组）。**人确认是唯一
入口**——AI 起草只是预填表单，没有自动保存。

## 4. 功能 B：访谈官（可选，独立，聊天页找方向）

### 4.1 是什么

平台内置智能体「访谈官（内置）」，角色 `interviewer`。聊天页「新对话」下拉可直接
选它开对话。**独立功能**：聊出来的「岗位卡方向」只是给用户看的参考——想用就抄进
功能 A 的要求框，不想用就自己写要求。没有按钮、没有传递、没有连接。

### 4.2 角色放行（两处小改，都有测试钉住）

聊天目前只接受 `role === 'executor'`。放行 `interviewer` 两处：

| 位置 | 改动 | 钉住 |
|---|---|---|
| `apps/daemon/src/server.ts` conversations POST | 角色判据放行 `interviewer`，WHY 注释："访谈官只访谈不干活，聊天的产出是方向不是判决" | `chat.test.ts` 加一条 |
| `apps/web/src/lib/chat.ts` `executorChoices` | 同款放行 | `chat.test.ts` 对应判据 |

新角色天然被业务选择的等值判断排除（不进组、不进任务），只有聊天这一处放行——
否则它能被选去干业务活，而它的指令是"只问不干"。

### 4.3 内置纪律（与 memory-tidy 同一套）

启动对账建出来、幂等/自愈/不许删、智能体页可见可编辑可恢复默认、历史版本逐字
冻结升级（第 248/249 批教训）、通用守则（`withConduct`）共用。

### 4.4 指令要点（只问不干）

1. 你是访谈官：帮人把"一个岗位"说清楚，**不干活**；用户派活引导回岗位本身。
2. 按岗位卡五字段追问：目标 → 职责（"每天最烦的活"）→ 输出格式（给例子）→
   **边界（必问，追问到说清为止，"没有"也要明说）** → 背景。
3. 边界为空时给最小权限缺省段（不主动触发不可逆操作 / 拿不准先停下 / 只在工作
   目录里动手），写进方向总结。
4. 问完输出「岗位卡方向」总结（§4.5）——用户表示聊够了之后才给，不主动结束。
5. 方向总结里注明"草稿——建之前尤其要审『边界』"。

不用技能、记忆默认关（上一场访谈不污染下一场）。

### 4.5 「岗位卡方向」总结（给用户看的参考）

```markdown
## 岗位卡方向（草稿）
- 岗位名称：会议纪要助理
- 角色：executor
- 目标/职责：…… / 边界（不能碰，必审）：…… / 输出格式：……
- 验收标准：……
- 建议挂载技能：meeting-notes（已有）
```

用户抄进功能 A 的要求框时，可以原样粘贴或挑重点写——功能 A 只认要求框里的文本。

## 5. 与「沉淀 Agent」（§4.1.3）的关系

功能 A 是 §4.1.3「沉淀 Agent」的**简化落地**：把"素材来源"从对话/任务收窄成
"一段要求文本"，产出从更新现有智能体收窄成"创建新智能体"。将来沉淀页把
「沉淀技能」与「沉淀智能体」并排时（§4.1.3 已设计），功能 A 的起草 run
（subject `agent-draft` + card-drafter）直接复用。

## 6. 界面改动

- 智能体页：新建表单顶部加「先写要求，让 AI 起草」块（§3.1）；列表出现
  「访谈官（内置）」与「岗位卡起草者（内置）」两条（可查看/编辑/恢复默认）。
- 聊天页：「新对话」下拉出现「访谈官（内置）」。
- 无新页面、无新端点族（要求 → 起草可走沉淀接口族的 draft 机制，见 §8 备选）。

## 7. 测试策略

- **单测 / e2e**（假 AgentBackend，不烧真实 CLI）：
  - `POST /api/conversations` 接受 `interviewer`，仍拒绝 `reviewer`/`drafter`/
    `memory-tidy`（不回归）；
  - `executorChoices` 包含 `interviewer`（`chat.test.ts` 钉住）；
  - 生成整链：要求文本 → 素材落盘（原样）→ 起草 run（fake card-drafter 产出
    agent-draft.md）→ 表单预填 → 改边界 → 保存 → 断言 `GET /api/agents` 字段
    与草稿一致；
  - **要求没提边界时**草稿含最小权限缺省段；
  - **独立性**：不用访谈也能生成（无前置依赖）；访谈对话不会自动触发生成
    （没有按钮/钩子）；
  - 内置对账（两条新内置）：启动建出来、可恢复默认、历史版本冻结、不进业务
    选择（补进 `agents-create` 判据）。
- **探针**（`probe:layout`）：新建表单的「先写要求，让 AI 起草」块；聊天下拉有
  「访谈官」；审阅提示"检查边界段"。

## 8. 协议草案（要求 → 起草，两条路二选一，实现时定）

| 路 | 端点 | 说明 |
|---|---|---|
| A（独立接口族） | `POST /api/agent-requirements`（要求文本 → 建素材 + 发起 agent-draft run）、`GET /api/agent-requirements/:id`（草稿）、`PATCH …/draft`（审阅修改） | 与早前"接口独立"拍板一致 |
| B（沉淀接口族） | 复用 `/api/crystallize/*` 的 draft 机制 + 产出类型 = agent（§4.1.3 方向） | 骨架现成，但产出类型参数是新增面 |

创建本身始终是现有 `POST /api/agents`，两条路都不改它。

## 9. 边界与风险

1. **token 成本**：一次生成 = 一次起草 run；访谈另算（可选）。与沉淀同量级。
2. **草稿不是合同**：AI 只预填表单，保存是唯一入口；"检查边界段"是提示不是校验。
3. **内置角色纪律**：`interviewer` / `card-drafter` 不进业务选择（等值判断天然
   排除）；聊天放行只改 `interviewer` 那两处、各带 WHY 注释。
4. **两个功能独立是拍板行为**：不加任何"访谈 → 生成"的传递（按钮/素材/自动触发
   都不做）；将来若要自动，那是沉淀 Agent 的入口问题。
5. **技能生成不是主线**：要求是"需求"不是"经验"，要技能走现有沉淀。
