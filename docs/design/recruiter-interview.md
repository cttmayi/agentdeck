# 招聘官访谈（interviewer-in-chat → agent）设计

> 状态：**设计稿，未实作**。配套决策记录：实现时补 D 号（`docs/srs/requirements.md` §16）。
> 需求来源：使用者 2026-11-09 读完《把 AI 当员工：Lauren Tan 的七条工作法》后提出
> 「先设计 招聘官访谈」。文章的七条之一（原文第 1 条）：**第一个 AI 不干活，先当
> "招聘官"**——先问清"你是谁、你要什么、边界在哪"，再生成一张**岗位卡**（目标 /
> 职责 / 工具 / 边界 / 输出格式）；岗位卡是**草稿不是合同**，尤其要审"不能做什么"
> 那一栏。
> 使用者 2026-11-09 两轮定稿：
> ① 两步走、两步**无操作连接**——① 访谈官智能体在**聊天页**和用户找方向；
>    ② 有方向后**用户手动触发**「生成智能体」，由**智能体动态起草**岗位卡草稿，
>    审阅后确认创建。原「问卷面板四步流水线」方案（问卷 → 素材 → 起草 → 审阅 →
>    commit 一体）**放弃**：放弃的是**固定问卷面板**，不是"AI 起草"这一步。
> ② "第 2 步还会通过智能体动态生成智能体吗，我的理解要"——**要**。第 2 步 =
>    沉淀 Agent 从访谈对话生成智能体（§4.1.3 的落地），AI 起草、人审阅确认。

## 1. 背景与目标

现状：新建智能体是**填表**（`NewAgentForm`：名称 / 角色 / 指令 / 挂技能 / 审核标准）。
表单把所有"组织上下文"压回使用者自己脑子里——它不问"你最烦哪些活、绝不许它碰什么"，
于是建出来的智能体只有两种下场：指令太泛（万能助手）、或边界没说（什么都接）。

文章给的解法是**反过来的**：先访谈、后建卡。招聘官的价值不在"生成"，在**挖掘**——
"每天最烦哪些活"这类问题逼使用者说出高频、低价值、可交接的任务。岗位卡的五个字段
不是给模型的 prompt，是**给人看、可审、可改**的草稿。

**目标（两段式，使用者定稿）**：

```
① 聊天页找方向              ② 用户手动点「生成智能体」（无自动连接）
   用户 ↔ 访谈官（内置）         ↓
   自适应追问，挖五字段          平台收集素材（对话轮次 + 方向总结）
   结尾给「岗位卡方向」           → 起草 run：岗位卡起草者（智能体）动态写岗位卡草稿
                                  → 分节审阅（边界必审）→ 确认 → 创建智能体
        │                          ▲
        └──── 不自动连接 ────────────┘
```

**"无连接"的确切含义**（使用者拍板）：聊天**不会自动触发**第 2 步——没有"聊完自动建
智能体"的钩子，也没有"把对话接到面板"的通道。第 2 步是用户对这段对话**手动点一下**
「生成智能体」开始的（像现在对话上的「沉淀技能」按钮一样，本来就要求用户动手）。
但第 2 步**内部**是完整的"AI 起草 + 人审阅"——智能体动态生成智能体，不是用户抄表单。

## 2. 为什么放弃「问卷面板」方案（2026-11 使用者定稿）

上一版设计是智能体页的「访谈生成」面板：固定问卷六问 → 答案落素材 → 一次起草 run
产岗位卡 → 分节审阅 → commit。使用者拍板放弃，**但放弃的是"面板 + 固定问卷"**：

1. **绕**：找方向本来是"坐下来问几句"，被做成面板 + 问卷，还要先填表才能起草。
2. **追问才是招聘官的价值**：固定问卷砍掉了追问，而文章的招聘官恰恰靠追问挖边界。
   放在聊天页，追问是**天然的**。
3. **两步独立，连接手动**：访谈（聊天）与生成（沉淀）之间不需要自动通道；用户
   自己动手点——但**第 2 步的起草必须是 AI 干的**（使用者 2026-11-09 第二轮明确）。

**因此本版不做**：问卷表单、智能体页的访谈面板。**本版保留**：素材目录、起草 run
（`agent-draft`）、分节审阅、commit——它们全部收进第 2 步（§5），与沉淀同一骨架。

## 3. ① 访谈官（内置智能体，聊天页找方向）

### 3.1 是什么

平台内置智能体「访谈官（内置）」，角色 `interviewer`。在聊天页**可以直接选它开对话**
（和普通执行者一样出现在「新对话」下拉里），然后像聊天一样回答它的问题。

### 3.2 角色放行（两处小改，都有测试钉住）

聊天目前只接受 `role === 'executor'`（daemon 门 `POST /api/conversations` 的
`agent_role_mismatch` + web 选择器 `executorChoices`）。访谈官要能进聊天，放行两处：

| 位置 | 改动 | 钉住 |
|---|---|---|
| `apps/daemon/src/server.ts` conversations POST | 角色判据放行 `interviewer`，WHY 注释说明"访谈官只访谈不干活，聊天的产出是方向不是判决" | 现有 `chat.test.ts` 加一条 |
| `apps/web/src/lib/chat.ts` `executorChoices` | 同款放行 | `chat.test.ts` 对应判据 |

⚠️ 为什么要新角色而不是直接给 `role: 'executor'`：仓库纪律是**内置智能体绝不进业务
选择**（各处判据是 `role === 'executor'` / `'reviewer'` 等值判断）。给访谈官
`executor` 会让它能被选进智能体组去干业务活——它的指令是"只问不干"，派去干活就是
静默坏掉。新角色 `interviewer` 天然被等值判断排除（业务选择、组、任务都不认它），
只有**聊天**这一处显式放行。

### 3.3 内置纪律（与 `memory-tidy` 同一套）

- 启动对账建出来（`ensureBuiltinInterviewer`），幂等 / 自愈 / 不许删；
- 「智能体」页可见、可编辑、可「恢复成默认值」；
- 默认指令的历史版本**逐字冻结**（升级判据 = 存着的 === 已知历史），防"规矩改了
  却没到老工作区"（第 248/249 批的教训）；
- 通用工作守则（`withConduct` / `agent-conduct.ts`）与其他内置共用，不留第二份。

### 3.4 指令要点（只问不干）

身份（`withConduct` 包裹）里写死的规矩：

1. **你是访谈官：帮人把"一个岗位"说清楚，不干活**。用户派活 / 求产出时，引导回
   到岗位本身，不做任务。
2. **按岗位卡五字段追问**：目标（做什么，一句话 + 2–3 件事）→ 职责（最常被叫去
   干的活，"每天最烦的活"）→ 输出格式（长什么样，给例子）→ **边界（绝不能碰
   什么——必问，追问到用户说清为止）** → 背景（黑话 / 历史决策 / 审美偏好）。
   允许用户说"没有"，但**"没有边界"也要明说**，不许跳过。
3. **边界为空时给最小权限缺省段**，写进方向总结（与平台"判过才动、不可逆操作前
   停"同口径）：
   - 不主动触发任何不可逆操作（删除、覆盖、对外发送、修改他人文件）。
   - 拿不准的事先停下、说明、等确认，不猜着执行。
   - 只在本次工作目录里动手。
4. **问完输出「岗位卡方向」**（§4 的格式）——这是它唯一的"产出"，也是第 2 步的
   **素材**。用户没说要结束时**不主动结束**；方向总结在用户表示聊够了之后给出。
5. 岗位卡是草稿：方向总结里明确"这里是草稿，建智能体之前尤其要审『边界』那一栏"。

### 3.5 不用技能、不用记忆

访谈官不挂技能（它的"手段"就是提问）；记忆功能默认关（它不积累偏好，每次访谈
都该从一张白纸开始——上一场访谈的结论不该污染下一场）。

## 4. 「岗位卡方向」总结（第 2 步的素材，不再是"被抄的对象"）

访谈结尾输出一段固定结构。**它在第 2 步里是素材的一部分**（§5.2 的
`方向总结.md`，起草者读它比读全部对话更准——它就是"使用者的要求"，与沉淀里
`user-requirements.md` 同一地位），不需要用户复制：

```markdown
## 岗位卡方向（草稿）
- 岗位名称：会议纪要助理
- 角色：executor              # executor | reviewer
- 目标/职责：把妙记链接变成一页会议纪要；转写 → 提炼 → 分节 → 交付；缺信息先停下
- 边界（不能碰，必审）：
  - 不替参会人做决定（decisions 只列不判）
  - 不对外发送；只在工作目录里写文件
  - 缺关键信息时不猜，先问
- 输出格式：decisions / owners / deadlines 三段，每段一行一个；来源链接附末尾
- 验收标准：decisions 逐条有 owner + deadline；无主条目不许出现
- 建议挂载技能：meeting-notes（已有）
```

## 5. ② 从访谈对话生成智能体（用户手动触发，AI 起草）

### 5.1 触发：对话上的「生成智能体」动作（手动，无自动连接）

聊天页对话栏头加一个「生成智能体」按钮（与「沉淀技能」并列）。**它不会自动出现
在访谈结尾**——访谈官说"聊够了"不等于自动开始起草；用户觉得方向对了，自己点
这个按钮。这就是"两步无操作连接"的落点：没有自动通道，只有用户的手。

按钮可用条件：这段对话有**方向总结**（即对话里出现过访谈官的岗位卡方向输出）。
没有方向总结的普通对话点了要说明原因（"这段对话还没聊出方向"），不悄悄开工——
与"判过才动"同一口径：拿不准就明说。

### 5.2 素材（复用沉淀的素材纪律）

`agent-interview-<id>/material/`：

```
material/
  meta.json          ← 来源（interviews）、问卷版本 n/a、创建时间
  00-方向总结.md     ← 访谈官的岗位卡方向（§4）——起草者的第一读件
  01-对话轮次.md     ← 访谈对话的轮次（转写/回答），供回查细节
```

与 `crystallize-material.ts` 同纪律：**起草者只读 material/，不读对话历史**——
方向总结、对话轮次都在这里，可复现、可 diff。

### 5.3 起草 run：智能体动态起草岗位卡

- **subject**：`{ type: 'agent-draft', id: <对话 runId> }`（`entities.ts` 枚举加
  `'agent-draft'` 值，§4.1.3 已预留）。不在闭环、不挂 issue、不进任务列表——
  与 `skill-draft` 同一条纪律。
- **执行者**：**新内置智能体「岗位卡起草者（内置）」，角色 `card-drafter`**。
  为什么不是沉淀的起草者（三条证据，与早前定稿一致）：
  1. 沉淀起草者的身份在第 191 批**有意**收窄成"只干一件事"——第一句是"把素材
     写成一条可复用的 **skill**"。复用它写岗位卡 = 身份与任务书打架（第 51 批
     的教训）。
  2. 沉淀起草者**挂 `distilly`**（SKILL 写作规范）——对岗位卡是错误注入，而注入
     不能按 subject 分叉（那是第二份真相）。
  3. 仓库内置智能体模式 = "一个岗位一条内置 + 专属 role + 不进业务选择"
     （memory-tidy 先例）。岗位卡起草者同理："它不写 skill，它只写岗位卡"。
  ⚠️ 与访谈官**是两个角色**：访谈官只问（聊天），岗位卡起草者只写（起草 run）。
  通用守则（`withConduct`）三者共用，不留第二份。
- **产出**：`岗位卡.md`，分节 Markdown（§5.4）。
- **素材是唯一依据**：只读 §5.2 的 material/。方向总结缺字段时，草稿相应节留
  "待补"并写清缺什么——**不许编**（与沉淀"不结晶清单"同一纪律）。

### 5.4 岗位卡草稿格式（分节，平台按节解析进审阅表单）

```markdown
---
name: 会议纪要助理
role: executor            # executor | reviewer
---

## 目标
把妙记链接变成一页会议纪要。

## 职责
转写 → 提炼 → 分节 → 交付；缺信息时先停下列出缺什么。

## 边界（不能碰）
- 不替参会人做决定（decisions 只列不判）。
- 不对外发送；只在工作目录里写文件。
- 缺关键信息时不猜，先问。

## 输出格式
- decisions / owners / deadlines 三段，每段一行一个。
- 来源链接附在末尾。

## 技能建议
- 挂 `meeting-notes`（若已有）……

## 验收标准
- decisions 必须逐条有 owner + deadline；无主条目不许出现。
```

### 5.5 审阅：分节表单，边界必审

- 草稿按 frontmatter + 分节渲染成表单（名称 / 角色 / 目标职责 / 边界 / 输出格式 /
  技能建议勾选 / 验收标准），逐项可改；「重新起草」可丢弃重来（与沉淀同规矩）。
- 边界栏带**「必审」徽标**（悬停提示文章原话："岗位卡是草稿，不是合同——尤其要
  审『不能做什么』这一栏"）。提示不是校验：删掉最小权限缺省也是合法的岗位卡，
  但删是有意的。
- 修改即生效；最后一次确认在 §5.6 的 commit。

### 5.6 commit：创建智能体

确认后 `POST /api/agents`（字段映射唯一一处）：

| 岗位卡节 | Agent 字段 |
|---|---|
| name | `name` |
| role | `role` |
| 目标 + 职责 + 边界 + 输出格式 | `instructions`（组装成一份——第一句话只有一个注入位，映射规则固定写死） |
| 技能建议（勾选结果） | `skillIds` |
| 验收标准 | `reviewStandard.body`（role = reviewer 时） |

动作权限不落智能体（属于组）——与现状一致。commit 与沉淀同规矩：**人确认是唯一
入口**，平台不自动建。技能生成不是主线：访谈答案是"需求"不是"经验"，要技能
走现有沉淀（§5.6 不默认带技能生成）。

## 6. 与「沉淀 Agent」（§4.1.3）的关系

第 2 步**就是** §4.1.3「沉淀 Agent」的落地：反向沉淀（对话 → 智能体指令），
只是"素材来源"从任意对话/任务收窄到**访谈对话**（方向总结让素材质量更高）。
将来「沉淀技能」与「沉淀智能体」在沉淀页并排（产出类型维度，§4.1.3 已设计），
本设计的第 2 步先落地对话 → 智能体这一条。

- 智能体页：列表出现「访谈官（内置）」与「岗位卡起草者（内置）」两条（可查看 /

## 8. 测试策略

- **单测 / e2e**（假 AgentBackend，不烧真实 CLI）：
  - `POST /api/conversations` 接受 `interviewer` 角色（放行），仍拒绝 `reviewer` /
    `drafter` / `memory-tidy`（现有判据不回归）；
  - `executorChoices` 包含 `interviewer`（web 选择器，`chat.test.ts` 钉住）；
  - 整链：访谈对话（fake 访谈官产出方向总结）→ 点「生成智能体」→ 素材落盘
    （含方向总结）→ 起草 run（fake 岗位卡起草者产出岗位卡）→ 审阅改边界 →
    commit → 断言 `GET /api/agents` 新智能体字段与岗位卡一致；
  - **无自动连接**：访谈对话结束不会自动建智能体（没有钩子），按钮点了才开工；
  - 内置对账（与 memory-tidy 同规矩）：两条新内置启动建出来、可恢复默认、历史
    版本冻结、**不被选去干业务活**（不进组、不进任务选择器，等值判断天然排除
    ——补进 `agents-create` 判据）。
- **探针**（`probe:layout`）：聊天页「新对话」下拉有「访谈官」；对话栏头有
  「生成智能体」按钮（有方向总结时可用、无则说明原因）；审阅表单边界栏带
  「必审」徽标。

## 9. 边界与风险

1. **token 成本**：一次完整流程 = 一场访谈对话 + 一次起草 run，与"聊一场 + 沉淀
   一次"同量级，没有额外开销。
2. **岗位卡是草稿，不是合同**：方向总结和审阅表单都明说"建之前审边界栏"；
   commit 是唯一入口，平台不自动建。
3. **内置角色纪律**：`interviewer` / `card-drafter` 必须满足"不进业务选择"（等值
   判断天然排除）；聊天放行只改 `interviewer` 那两处、各带 WHY 注释，防"顺手把
   别的内置也放进聊天"。
4. **两步无连接是拍板行为**：不加"聊完自动建"的钩子；将来若想自动，那是沉淀
   Agent 的入口问题，不是本设计的缺漏。
5. **技能生成不是第 2 步的主线**：访谈答案是"需求"不是"经验"；要技能，干过几轮
   活后走现有沉淀（与早前定稿一致）。
