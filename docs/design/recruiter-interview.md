# 招聘官访谈（interview-to-agent）设计

> 状态：**设计稿，未实作**。配套决策记录：实现时补 D 号（`docs/srs/requirements.md` §16）。
> 使用者已拍板（2026-11-09）：**接口独立**（§9）、**岗位卡不进 Git**（§8.1）、
> **不用沉淀的起草者**（§5，新开内置智能体）、**v1 不做技能生成主线、不做
> 「内置/私有技能」概念**（§7.2，输出格式进指令；真要技能走现有沉淀）。
> 需求来源：使用者 2026-11-09 读完《把 AI 当员工：Lauren Tan 的七条工作法》后提出
> 「先设计 招聘官访谈」。文章的七条之一（原文第 1 条）：**第一个 AI 不干活，先当
> "招聘官"**——先问清"你是谁、你要什么、边界在哪"，再生成一张**岗位卡**（目标 /
> 职责 / 工具 / 边界 / 输出格式）；岗位卡是**草稿不是合同**，尤其要审"不能做什么"
> 那一栏。
> 与 `docs/design/skill-crystallization.md` §4.1.3「沉淀 Agent」的关系见 §8（同一
> `agent-draft` 起草链路，两个不同入口）。

## 1. 背景与目标

现状：新建智能体是**填表**（`NewAgentForm`：名称 / 角色 / 指令 / 挂技能 / 审核标准）。
表单把所有"组织上下文"压回使用者自己脑子里——它不问"你最烦哪些活、绝不许它碰什么"，
于是建出来的智能体只有两种下场：指令太泛（万能助手）、或边界没说（什么都接）。

文章给的解法是**反过来的**：先访谈、后建卡。招聘官的价值不在"生成"，在**挖掘**——
"每天最烦哪些活"这类问题逼使用者说出高频、低价值、可交接的任务，那才是适合自动化的
岗位。岗位卡的五个字段（目标 / 职责 / 工具 / 边界 / 输出格式）不是给模型的 prompt，
是**给人看、可审、可改**的草稿。

**目标**：在智能体页提供一条「访谈生成」路径——填一份**固定问卷**（不烧 token），
答案落盘为素材，平台发起**一次起草 run** 产出**岗位卡草稿**，人工逐栏审阅后
**入库成为智能体**。全程复用沉淀的「素材 → 起草 run → 审阅 → 入库」骨架，
只换产出类型（skill → agent），不留第二套流程。

### 1.1 为什么产出是"智能体"，不是技能

文章的岗位卡 = "AI 员工"，对应 AgentDeck 的**智能体**（`Agent`：角色 / 指令 / 技能 /
审核标准）。技能（SKILL.md）是"怎么做一件事"的操作手册，是**员工的手段**，不是员工
本身——岗位卡里"用什么工具、输出什么格式"这两栏会进一步沉淀成技能（§7.2 可选），
但**卡本身落成智能体**。

### 1.2 新建智能体到底包括什么（2026-11 使用者问）

`POST /api/agents` 建的智能体只有：名称、角色（executor / reviewer）、指令、挂载的
技能（`skillIds`，**引用**）、审核标准（reviewer 用）、工作目录、记忆开关、model。
**技能不是"新建智能体"的一部分**——技能是独立实体（在技能根、git 化），建智能体时
从库里**选挂**；岗位卡的「技能建议」栏 = 选挂结果。要新造一条技能（比如输出格式
模板）是**可选的另一次沉淀**（§7.2），不是建智能体的内容。动作权限 / 工具包也不在
智能体上（动作只属于组；工具包能力已整体撤掉）。

### 1.3 为什么 v1 不引入"招聘官对话"（LLM 追问 run）

文章的招聘官是**会追问的**（"问的问题越多，返工越少"）。v1 **不做追问 run**，理由：

1. **成本与确定性**：每次追问 = 一次 run = 一次 token。问卷是固定的，追问的边际
   价值集中在"挖边界"——而边界这栏 v1 用**必答 + 默认值**兜住（§4.3）。
2. **审阅即追问**：岗位卡是草稿。起草者写的卡缺信息时，**审阅表单就是追问现场**——
   人看到哪栏空着、哪栏可疑，当场改。这比"多问两轮再出卡"更省，且更接近文章
   "卡片是草稿，不是合同"的本意。
3. **仓库纪律**：素材是起草者唯一依据（沉淀同款）。问卷答案落盘成素材，起草者读
   素材写卡——比"招聘官在会话里问、答案只活在对话里"可复现、可测试。

**v2 追加**（本设计预留口子，见 §8.2）：起草 run 结束后若岗位卡缺关键信息，可发起
一次**追问 run**（用同一条「岗位卡起草者」内置，遵守"内置角色不进业务选择"纪律）列出
2–3 个待确认问题，人在审阅表单里回答后再入库。v1 不做，接口不堵死。

## 3. 流水线总览（四步）

```
① 访谈问卷 ──► ② 起草 run（agent-draft）──► ③ 审阅表单 ──► ④ 入库建智能体
   人填 6 问       内置起草者读素材写岗位卡      人逐栏改，            确认 →
   答案落素材       （subject agent-draft）      边界栏必审             POST /api/agents
                                                                    （可选）沉淀输出格式成技能
```

- ① **访谈**：固定问卷，答案由平台落成"岗位卡素材"（`material/` 目录）。
- ② **起草**：一次 run（内置起草者，`agent-draft` subject），读素材，产出
  `岗位卡.md`（分节 Markdown，§5）。
- ③ **审阅**：分节表单渲染草稿，人逐栏改；**边界栏**（"不能做什么"）在界面上
  单独强调（§6.2）。
- ④ **入库**：确认 → 创建智能体（字段映射 §7）；输出格式/流程部分可选
  同时沉淀成技能（§7.2）。

## 4. ① 访谈问卷

### 4.1 入口

智能体页「新建智能体」按钮旁新增「访谈生成」。面板 = 沉淀页同款骨架：
步骤条（① 定目标 → ② 起草 → ③ 审阅入库）+ 素材摘要 + RunLog 常驻 + 恢复进行中。

### 4.2 问题集（六问，与文章岗位卡五字段一一对应）

| # | 问题 | 对应字段 | 必答 |
|---|---|---|---|
| 1 | 这个岗位**做什么**？一句话目标 + 日常负责的 2–3 件事 | 目标 / 职责 | ✅ |
| 2 | 它**最常被叫去干的**活是什么？（"每天最烦的活"） | 职责（触发场景） | ✅ |
| 3 | 产出**长什么样**？给个例子或格式（"输出分 decisions / owners / deadlines 三段"这种） | 输出格式 | ✅ |
| 4 | 哪些事**绝不许它碰**？（删库、发群、改配置、越界目录……） | 边界 | ✅（可写"没有"，见 §4.3） |
| 5 | 它**要懂哪些背景**？（项目黑话、历史决策、审美偏好——像带新人交代的那些） | 指令里的上下文段 | 可空 |
| 6 | 这活儿**多久重复一次**？换个人能用吗？ | 复用性 → 是否连技能一起沉淀（§7.2） | 可空 |

问题集**固定**（v1 不追答）：它保证素材有结构，起草者不必猜。第 4 问单独列出、
必答——文章原话："一个没有边界的岗位，最后一定会长成一个什么都接、什么都做不深的
万能助手"。

### 4.3 边界栏的默认值（最小权限缺省段）

第 4 问写"没有"（或空）时，素材里**预置一段最小权限边界**，起草者必须采纳：

```
## 边界（不能碰）
- 不主动触发任何不可逆操作（删除、覆盖、对外发送、修改他人文件）。
- 拿不准的事先停下、说明、等确认，不猜着执行。
- 只在本次工作目录里动手；不读、不写工作目录之外的内容。
```

为什么预置而不是让起草者自由发挥：**"没有边界"是一种边界**，它不该是"空着"，而是
"默认最小权限"——和平台"判过才动、不可逆操作前停"的口径一致。这符合文章"岗位卡是
草稿"的精神：使用者可以删掉这条默认值，但删是**有意的**，不是漏填。

### 4.4 素材落盘

```
interview-<id>/
  material/
    meta.json        ← 来源（interviews）、创建时间、问卷版本
    00-回答.md       ← 六问的原文回答（起草者唯一依据）
    01-边界缺省.md   ← 第 4 问为空时的最小权限缺省段（§4.3）
```

与 `crystallize-material.ts` 的素材纪律一致：**起草者只读 material/，不读对话历史**
——回答原文、边界缺省都在这里，可复现、可 diff。

## 5. ② 起草 run（subject `agent-draft`）

- **subject**：`{ type: 'agent-draft', id: interviewId }`（`entities.ts` 枚举加
  `'agent-draft'` 值，§4.1.3 已预留）。不在闭环、不挂 issue、不进任务列表——
  与 `skill-draft` 同一条纪律。
- **执行者**：**新开一条内置智能体**（新角色 `card-drafter`，名字「岗位卡起草者
  （内置）」），**不用沉淀的起草者**。为什么不是同一个（2026-11 使用者问，三条证据）：
  1. 沉淀起草者的身份在分批第 191 批**有意**收窄成"只干一件事"——第一句是"把素材
     写成一条可复用的 **skill**"，当时特意删掉了"也可能是一条智能体的指令"那半句
     （"留着它会让它去找一个不存在的产出契约"）。复用它写岗位卡 = 身份与任务书
     打架（第 51 批的教训：自相矛盾的交代下模型行为随机），或把身份改回"对象无关"
     = 翻 191 批的案。
  2. 沉淀起草者**挂 `distilly`**（SKILL 写作规范：frontmatter / When to Use /
     Procedure）——对岗位卡是**错误注入**；而 `skillIds` 是智能体上固定挂载，
     按 subject 分叉注入就是第二份真相。
  3. 仓库的内置智能体模式本来就是"一个岗位一条内置 + 专属 role + 不进业务选择"
     （`memory-tidy` 是先例："它不闲聊，它只整理"）。岗位卡起草者同理："它不写
     skill，它只写岗位卡"。共享的通用守则（`withConduct` / `agent-conduct.ts`）
     两案共用，不留第二份。
  ⚠️ 新角色必须满足"**不进业务选择**"（各处判据是 `role === 'executor'` /
  `'reviewer'` 等值判断，新成员天然被排除），并补上"启动对账建出来 / 可恢复默认 /
  历史版本冻结升级"那套（`ensureBuiltin*` + 历史指令清单，与 `memory-tidy` 同一
  规矩）。v2 的追问 run 也用这一条（§8.2）。
- **产出**：`岗位卡.md`，分节 Markdown（平台按节解析进审阅表单）：

```markdown
---
name: 会议纪要助理
role: executor            # executor | reviewer
---

## 目标
把妙记链接变成一页会议纪要。

## 职责
转写 → 提炼 → 分节 → 交付；缺信息时先停下列出缺什么。

## 边界（不能碰）
- 不替参会人做决定（decisions 只列不判）。
- 不对外发送；只在工作目录里写文件。
- 缺关键信息时不猜，先问。

## 输出格式
- decisions / owners / deadlines 三段，每段一行一个。
- 来源链接附在末尾。

## 技能建议
- 挂 `meeting-notes`（若已有）……
- 建议沉淀一条新技能「会议纪要模板」（§7.2）。

## 验收标准
- decisions 必须逐条有 owner + deadline；无主条目不许出现。
```

- **素材是唯一依据**：起草者只读 §4.4 的 material/。问卷答案不足时，草稿里
  相应节留"待补"并写清缺什么——**不许编**（与沉淀"不结晶清单"同一纪律）。

## 6. ③ 审阅表单

### 6.1 分节渲染

草稿按 frontmatter + 分节渲染成表单：

| 草稿节 | 控件 |
|---|---|
| name / role | 文本 + 角色选择（executor / reviewer） |
| 目标 / 职责 | 文本域（可改） |
| 边界 | 文本域 + **徽标提示**（见 §6.2） |
| 输出格式 | 文本域（可改） |
| 技能建议 | 勾选（从现有技能里挑）+ 提示"可一并沉淀新技能" |
| 验收标准 | 文本域；role=reviewer 时此栏落 `reviewStandard.body`（§7.1） |

### 6.2 边界栏单独强调

审阅表单里边界栏带**视觉徽标**（如「必审」），悬停提示文章原话：
"岗位卡是草稿，不是合同——尤其要审『不能做什么』这一栏"。这是**提示不是校验**：
边界栏不强制非空（使用者明确删掉最小权限缺省也是合法的岗位卡），只是让"审这一栏"
这件事看得见。与分批第 263 批"置灰 + 说明，不隐藏"同一教训：不出现的提示不会
告诉你它为什么不在。

### 6.3 修改即生效

人改的字段直接成为最终值（草稿被改后，`PATCH` 落回 draft 记录；再点「重新起草」
可丢弃修改重来——与沉淀页同一规矩）。**岗位卡不是合同**：入库前的最后一次确认
发生在 §7 的 commit。

## 7. ④ 入库

### 7.1 岗位卡 → 智能体字段映射（唯一映射处）

| 岗位卡节 | Agent 字段 | 说明 |
|---|---|---|
| name | `name` | 直接 |
| role | `role` | executor / reviewer |
| 目标 + 职责 + 边界 + 输出格式 | `instructions` | **组装成一份指令**——第一句话只有 `{{instructions}}` 一个注入位，映射规则固定写死，不留"岗位卡"与"指令"两份真相 |
| 技能建议（勾选结果） | `skillIds` | 只落使用者勾中的 |
| 验收标准 | `reviewStandard.body`（role=reviewer 时） | 执行者的验收走**组**（见 §7.1 下面那段口径），不入 Agent |
| （无对应） | `workDir` / `model` / `memoryEnabled` | 用默认值，审阅表单不带这两栏 |

**动作权限（能用哪些工具/触发什么动作）不落智能体**——仓库已定"动作只属于组"
（`AgentGroup.allowedActions`）。岗位卡不产生组；想配动作，入库后去智能体组页。
这是刻意的口径：进不了组，就进不了动作。

### 7.2 可选：把输出格式沉淀成技能（2026-11 使用者讨论后定稿）

审阅时勾了「一并沉淀」才做：commit 顺带发起一次**技能沉淀**（复用 `skill-draft`
全流程，素材 = 岗位卡的输出格式/职责节 + 访谈答案），产出**普通技能**（mine +
git，别的智能体可以挂）。

**为什么技能生成不是访谈的主线、也没有"内置/私有技能"概念**（使用者问"必要时
可不可以包括 SKILL"，定稿如下）：

1. **访谈答案是"需求"，不是"经验"**——沉淀纪律是"素材不足以支撑就如实说，不要
   硬凑"。六问答案只说"要什么"，没干过真实的一次活，拿它生成的技能是**没验证的
   硬凑**。文章第 4 条（轨迹转技能）沉淀的是**真实成功的那次对话**，和访谈是
   两条独立流程。
2. **输出格式属于这个岗位，先进指令**（§7.1 组装进 `instructions`，唯一真相）。
   同一份内容再生成一条技能 = 两份真相。
3. **技能是共享资产**——mine 进 git、谁都能挂（文章原话："岗位卡可以交给另一个
   Agent"）。"这条技能只能给某个智能体用"的那部分，本来就该是指令的一部分，
   不是技能。私有化要新增归属标记 / 挂载过滤 / 级联删除 / 注入分叉一整套新面，
   换来的东西仓库里不存在。
4. **"安装 SKILL"已经覆盖**：§7.1 的「技能建议」栏就是从技能库勾选挂载，commit
   时一起挂进新智能体，无需新机制。

真要复用了再沉淀：智能体干过几轮活、格式被证明有用，走**现有沉淀流程**把经验
转技能——那才是技能该出生的时刻。

### 7.3 commit

确认后 `POST /api/agents`（创建智能体，含 §7.1 勾选的技能挂载；勾了 §7.2 则
先跑技能沉淀再挂）。commit 与沉淀同规矩：**人确认是唯一入口**，平台不自动建。

## 8. 与「沉淀 Agent」（§4.1.3）的关系

| | 招聘官访谈（本文） | 沉淀 Agent（§4.1.3，未来） |
|---|---|---|
| 方向 | **前向**：从需求建新智能体 | **反向**：从对话/任务经验更新现有智能体 |
| 入口 | 智能体页「访谈生成」 | 沉淀页（产出类型 = agent） |
| 素材 | 访谈问卷答案 | 对话/任务 events + 判决 |
| 起草 run | subject `agent-draft` | subject `agent-draft`（同一枚举值） |
| 审阅 | 岗位卡分节 | 指令文本 |
| 入库 | 创建 Agent | 更新 `Agent.instructions` |

**共用**：`agent-draft` subject、起草 run 机制、审阅骨架。谁先实作谁先建立
`agent-draft`，另一方直接复用——本设计若先落地，§4.1.3 的反向沉淀只剩
"素材来源"与"入库方向"两处差异。

### 8.1 岗位卡要不要进 Git

文章说岗位卡"可以进 Git"。**v1 不进**：智能体在 append-only store（不在 git），
岗位卡随智能体记录落地，可回看；将来与沉淀 Agent 一起解决"agent prompt 版本管理"
（§4.1.3 已记"将来单独定的点"）。进 Git 前先把"智能体指令要不要 git 根"想清楚，
不要在 v1 给一个半套 git 方案。

### 8.2 v2 追问 run（预留，不做）

用**同一条**「岗位卡起草者」内置智能体（追问与起草是一个 persona，不再开角色）+
追问 run（subject `agent-draft-followup` 或复用 `agent-draft`）：起草完成后列出
2–3 个待确认问题，人在审阅表单回答后再 commit。接口上不堵死：素材 meta 里预留
`followups` 数组位（v1 恒为空）。

## 9. 协议草案（独立接口族，2026-11 使用者拍板）

使用者定：**接口独立**（不挂沉淀接口族），**岗位卡不进 Git**（§8.1）。

| 端点 | 作用 |
|---|---|
| `POST /api/agent-interviews` | 提交问卷答案 → 建 `interview-<id>` 素材目录 → 发起 `agent-draft` 起草 run → 返回 interviewId + runId |
| `GET /api/agent-interviews/:id` | 进度 + 岗位卡草稿 + 素材摘要（恢复进行中） |
| `PATCH /api/agent-interviews/:id` | 审阅修改（分节字段） |
| `POST /api/agent-interviews/:id/commit` | 入库：建智能体（body 含勾选技能、是否一并沉淀技能） |

> 接口独立 ≠ 骨架独立：流程页骨架（步骤条 / 素材摘要 / RunLog / 恢复进行中）
> 仍复用沉淀那套，只是**端点**不开在 `/api/crystallize/*` 下面。

## 10. 测试策略

- **单测**：
  - 问卷 → 素材组装（回答原文 + 边界缺省预置，第 4 问空/非空两分支）；
  - 岗位卡 → Agent 字段映射（指令组装规则、reviewStandard 只在 reviewer 落、
    动作权限不进 Agent）；
  - 草稿缺节时的"待补"标记（不许编）。
- **e2e**（假 AgentBackend，不烧真实 CLI）：
  - 整链：访谈 → 起草（fake 岗位卡起草者产出岗位卡）→ 审阅改边界 → commit →
    断言 `GET /api/agents` 里新智能体的字段与岗位卡一致；
  - 缺边界时素材里带最小权限缺省段（§4.3）；
  - commit 前草稿可重来、可放弃（与沉淀同规矩）；
  - **新内置智能体对账**（与 `memory-tidy` 同规矩）：启动建出来、可「恢复成默认
    值」、历史版本冻结升级、**不被选去干业务活**（`role === 'executor'` 等值
    判断天然排除，补进 `agents-create` 判据）。
- **探针**（`probe:layout`）：访谈面板布局（步骤条 / 问卷表单 / 审阅分节 /
  边界「必审」徽标）。

## 11. 边界与风险

1. **token 成本**：v1 每访谈一次 = 一次起草 run，与沉淀同量级；问卷本身零成本。
2. **岗位卡不是合同**：入库前必须人确认（commit 唯一入口）；边界栏有提示无强制。
3. **不留第二份真相**：岗位卡 → 指令的组装规则只有一处（§7.1），问卷版本记在
   素材 meta（§4.4），防止"改了几轮问卷、旧答案还在"。
4. **内置角色纪律**：新角色 `card-drafter` 必须满足"不进业务选择"（等值判断
   天然排除），并补进既有 `agents-create` 判据（§10 已列）。
5. **与沉淀的关系**：访谈的"一并沉淀技能"（§7.2）是**另一个**流程（skill-draft），
   不是岗位卡的组成部分——别把两者焊在一起。
