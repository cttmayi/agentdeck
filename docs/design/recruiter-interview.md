# 从要求生成(智能体/技能)+ 访谈官 设计（requirement-to-agent-or-skill）

> 状态：**设计稿，未实作**。配套决策记录：实现时补 D 号（`docs/srs/requirements.md` §16）。
> 需求来源：使用者 2026-11-09 读完《把 AI 当员工：Lauren Tan 的七条工作法》后提出
> 「先设计 招聘官访谈」。文章的七条之一（原文第 1 条）：**第一个 AI 不干活，先当
> "招聘官"**——先问清"你是谁、你要什么、边界在哪"，再生成一张**岗位卡**（目标 /
> 职责 / 工具 / 边界 / 输出格式）；岗位卡是**草稿不是合同**，尤其要审"不能做什么"
> 那一栏。
> 使用者四轮定稿（2026-11-09）：
> ① 两步走、两步无连接；
> ② 第 2 步必须有 AI 起草（"还会通过智能体动态生成智能体吗——我的理解要"）；
> ③ 第 2 步与第 1 步解耦、栏位最少、用户可以直接做第 2 步（"提要求去生成智能体"）；
> ④ **功能 A 独立**（"如果需求，我觉得不应该复用现有表单"→ 选「选项 2：独立」）：
>   独立「从要求生成」面板，产出类型**智能体 / 技能 二选一**，不复用新建表单。

## 1. 背景与目标

现状：新建智能体 / 新建技能都是**填表**，所有"组织上下文"压回使用者自己脑子里——
表单不问"你最烦哪些活、绝不许它碰什么"。文章给的解法：**先访谈/先写清楚要求，
再生成草稿**；草稿是**给人看、可审、可改**的，不是合同。

**最终形态（两个独立功能，互不连接）**：

```
┌─ 功能 A：从要求生成（独立面板）──────────────────────────┐
│  写一段要求 → 选产出类型（智能体 / 技能）→ AI 起草 →      │
│  审阅 → 确认 → 创建（智能体）或沉淀（技能→mine+git）      │
│  独立入口、独立接口族、不复用新建表单                      │
└──────────────────────────────────────────────────────────┘
┌─ 功能 B：访谈官（可选，独立）───────────────────────────┐
│  聊天页与访谈官对话，理清"目标/职责/边界/输出格式"         │
│  产出「岗位卡方向」仅作参考（想用就抄进功能 A 的要求框）   │
└──────────────────────────────────────────────────────────┘
```

功能 A 的产出类型二选一是使用者第四轮拍板（"起草不需要支持新生成 SKILL 吗"）。
**代价是明说的**：技能分支从"要求文本"生成技能草稿——技能**未经验证**（沉淀纪律
是"干成功之后结晶"）。取舍：规格优先于经验，验证推迟到使用中；审阅时给提示，
不强制（§3.5）。

## 2. 为什么功能 A 独立、不复用新建表单（2026-11 使用者定稿）

上一版把功能 A 做进「新建智能体」表单（要求块 + AI 预填）。使用者第四轮拍板独立：

1. **产出类型不止智能体**：要求可以生成技能。技能落点是 `skillsRoot` + `skills-mine`
   git，智能体落点是 agents 表——**两个目的地**，共用一个表单就拧巴。
2. **表单是"保存目的地"，不是"生成器"**：复用表单意味着 AI 预填只对智能体有意义，
   技能分支无处安放（或硬塞一个"保存成技能"按钮，把表单搞成四不像）。
3. **独立面板 + 独立接口族**（与早前"接口独立"拍板一致）：面板只管"要求 → 草稿 →
   审阅 → 确认"，创建动作仍走现有端点（智能体 `POST /api/agents`、技能沉淀 commit），
   不复制逻辑。

## 3. 功能 A：从要求生成（独立面板）

### 3.1 入口与交互

智能体页「新建智能体」旁加「**从要求生成**」入口 → 打开独立面板（页面内弹层即可，
不是新导航页）：

```
[ 一段话写你要什么：做什么 / 输出长什么样 / 绝不能碰什么……       ]
[ 产出类型： (o) 智能体   ( ) 技能 ]   [ 由 AI 起草 ]
        ↓ 起草 run（按类型走不同的起草者）
[ 草稿审阅区（按类型渲染）]  [ 素材摘要 / RunLog 常驻 ]
[ 确认生成 ]
```

- 要求框是纯文本，一两句到一段都行。
- **产出类型二选一**（起草前选，不搞"AI 猜类型"——那要多一次 run）。
- 不满意 → 改要求 → 再「由 AI 起草」：素材更新为新要求，旧草稿覆盖（与沉淀
  "重新起草"同规矩）；起草 run 失败 → RunLog 报错、可重试、不预填草稿。

### 3.2 产出类型：智能体 / 技能

| | 智能体 | 技能 |
|---|---|---|
| subject | `agent-draft`（`entities.ts` 枚举加值，§4.1.3 已预留） | `skill-draft`（**现有**，不新增） |
| 起草者 | 内置「岗位卡起草者」`card-drafter`（§3.4） | **现有沉淀起草者**（挂 distilly，身份就是"把素材写成 skill"——正好对口，不用新开） |
| 素材 | `00-要求.md`（唯一依据） | 同左（沉淀素材源从 run 扩展到要求文本，§5） |
| 草稿 | `agent-draft.md`（name/role + 一段指令） | `SKILL.md`（slug/name/description/body，同沉淀） |
| 确认 | `POST /api/agents` | 复用沉淀 commit → `skills-mine` + git（共享） |

### 3.3 素材（一条纪律：起草者唯一依据 = 要求文本）

```
requirement-<id>/
  material/
    meta.json     ← 来源（requirement）、kind（agent|skill）、创建时间
    00-要求.md    ← 要求框里的那段话（原样落盘）
```

起草者**只读 00-要求.md**，不许编。要求没说清的部分，草稿相应处标「待补：xxx」并
写清缺什么——与沉淀"不结晶清单"同一纪律。

### 3.4 智能体分支：起草者 = 内置「岗位卡起草者」

为什么不是沉淀的起草者（三条证据，早前已定稿）：

1. 沉淀起草者身份在第 191 批**有意**收窄成"只干一件事"（"把素材写成一条可复用的
   skill"）——写智能体 = 身份与任务书打架（第 51 批教训）；
2. 沉淀起草者**挂 `distilly`**（SKILL 写作规范）——对智能体草稿是错误注入，而注入
   不能按 subject 分叉（第二份真相）；
3. 仓库内置模式 = "一个岗位一条内置 + 专属 role + 不进业务选择"（memory-tidy 先例）。

产出 `agent-draft.md`：frontmatter（name/role）+ 正文一段指令，**必须有边界段**
（要求没提边界时写最小权限缺省段：不触发不可逆操作 / 拿不准先停下 / 只在工作目录
动手）——"没有边界"是默认最小权限，不是漏填。

### 3.5 审阅（按类型渲染，栏位最少）

- **智能体草稿**：名称 / 角色 / 指令（一段，边界在段内）/ 技能建议（可选勾选已有
  技能）。指令栏下提示「草稿不是合同——检查『边界』段」（提示不是校验）。
- **技能草稿**：复用沉淀的 SKILL 草稿审阅（slug / name / description / body + 素材
  摘要）。审阅区一行提示：「此技能草稿来自要求，**未经验证**——建议先让智能体干
  几轮，再用沉淀结晶正式版」（提示不是校验，接受与否用户定）。

### 3.6 确认生成（人确认是唯一入口）

- 智能体：`POST /api/agents`（name/role/instructions/skillIds，现有端点，面板只是
  不借它的表单 UI）。动作权限不落智能体（属于组）。
- 技能：复用沉淀 commit 逻辑 → 落 `skills-mine` + git（可共享）。
- requirement / 草稿记录存着可复查，不自动删，不关联（不加死字段）。

## 4. 功能 B：访谈官（可选，独立，聊天页找方向）

### 4.1 是什么

平台内置智能体「访谈官（内置）」，角色 `interviewer`。聊天页「新对话」下拉可直接
选它开对话。**独立功能**：聊出的「岗位卡方向」只是参考——想用就抄进功能 A 的要求
框，不想就自己写。没有按钮、没有传递、没有连接。

### 4.2 角色放行（两处小改，都有测试钉住）

聊天目前只接受 `role === 'executor'`。放行 `interviewer` 两处：

| 位置 | 改动 | 钉住 |
|---|---|---|
| `apps/daemon/src/server.ts` conversations POST | 角色判据放行 `interviewer`，WHY 注释："访谈官只访谈不干活，聊天的产出是方向不是判决" | `chat.test.ts` 加一条 |
| `apps/web/src/lib/chat.ts` `executorChoices` | 同款放行 | `chat.test.ts` 对应判据 |

新角色天然被业务选择的等值判断排除（不进组、不进任务），只有聊天这一处放行。

### 4.3 内置纪律（与 memory-tidy 同一套）

启动对账建出来、幂等/自愈/不许删、智能体页可见可编辑可恢复默认、历史版本逐字
冻结升级（第 248/249 批教训）、通用守则（`withConduct`）共用。

### 4.4 指令要点（只问不干）

1. 你是访谈官：帮人把"一个岗位"说清楚，**不干活**；用户派活引导回岗位本身。
2. 按岗位卡五字段追问：目标 → 职责（"每天最烦的活"）→ 输出格式（给例子）→
   **边界（必问，追问到说清为止，"没有"也要明说）** → 背景。
3. 边界为空时给最小权限缺省段，写进方向总结。
4. 问完输出「岗位卡方向」总结（§4.5）——用户表示聊够了之后才给，不主动结束。
5. 方向总结注明"草稿——建之前尤其要审『边界』"。

不用技能、记忆默认关（上一场访谈不污染下一场）。

### 4.5 「岗位卡方向」总结（给用户看的参考）

```markdown
## 岗位卡方向（草稿）
- 岗位名称：会议纪要助理
- 角色：executor
- 目标/职责：…… / 边界（不能碰，必审）：…… / 输出格式：……
- 验收标准：……
- 建议挂载技能：meeting-notes（已有）
```

用户抄进功能 A 的要求框时，原样粘贴或挑重点写——功能 A 只认要求框里的文本。

## 5. 与「沉淀」和「沉淀 Agent」（§4.1.3）的关系

- **技能分支 = 沉淀的"素材源扩展"**：沉淀现在从真实 run 收集素材；功能 A 的技能
  分支把素材源扩成"要求文本"（`00-要求.md`），起草/审阅/commit 全部复用 skill-draft
  骨架，**不复制逻辑**。代价是技能未经验证（§1 明说的取舍，§3.5 审阅时提示）。
- **智能体分支 = §4.1.3「沉淀 Agent」的简化落地**：素材源是要求文本而不是对话，
  产出是新建智能体而不是更新现有智能体；将来沉淀页把「沉淀技能 / 沉淀智能体」
  并排时（§4.1.3），智能体分支的起草 run（agent-draft + card-drafter）直接复用。

## 6. 界面改动

- 智能体页：「新建智能体」旁加「从要求生成」入口 → 独立面板（§3.1）。
- 聊天页：「新对话」下拉出现「访谈官（内置）」。
- 智能体页列表：出现「访谈官（内置）」与「岗位卡起草者（内置）」两条（可查看 /
  编辑 / 恢复默认，同 memory-tidy）。
- 审阅区复用沉淀页的草稿审阅骨架（素材摘要 + RunLog 常驻 + 恢复进行中）。

## 7. 测试策略

- **单测 / e2e**（假 AgentBackend，不烧真实 CLI）：
  - `POST /api/conversations` 接受 `interviewer`，仍拒绝 `reviewer`/`drafter`/
    `memory-tidy`（不回归）；
  - `executorChoices` 包含 `interviewer`（`chat.test.ts` 钉住）；
  - **智能体分支整链**：要求文本 → 素材落盘（原样）→ 起草 run（fake card-drafter
    产出 agent-draft.md）→ 审阅改边界 → 确认 → 断言 `GET /api/agents` 字段与草稿
    一致；
  - **技能分支整链**：要求文本 → 素材落盘 → 起草 run（现有 skill-draft 骨架）→
    审阅（含"未经验证"提示文案）→ 确认 → 断言技能落 `skills-mine` + git；
  - **要求没提边界时**智能体草稿含最小权限缺省段；
  - **独立性**：不用访谈也能生成（无前置依赖）；访谈对话不会自动触发生成；
  - 内置对账（两条新内置）：启动建出来、可恢复默认、历史版本冻结、不进业务
    选择（补进 `agents-create` 判据）。
- **探针**（`probe:layout`）：独立面板（产出类型切换、要求块、起草、审阅区）；
  聊天下拉有「访谈官」。

## 8. 协议草案（独立接口族，实现时定细节）

| 端点 | 说明 |
|---|---|
| `POST /api/requirements` `{text, kind}` | 建 requirement 记录 + 素材落盘 + 发起起草 run（按 kind 走 agent-draft / skill-draft），返回 runId |
| `GET /api/requirements/:id` | 要求 + 草稿状态 + 草稿内容 + RunLog |
| `PATCH /api/requirements/:id/draft` | 审阅修改（草稿修订） |
| `POST /api/requirements/:id/commit` `{finalDraft}` | 人确认：智能体 → 调 `POST /api/agents`；技能 → 复用沉淀 commit（mine+git） |

创建动作仍走现有端点（智能体 `POST /api/agents`、技能沉淀 commit），独立接口族只
负责"要求 → 草稿 → 审阅 → 确认"这一段，不复制创建逻辑。

## 9. 边界与风险

1. **技能未经验证（拍板取舍）**：从要求生成的技能草稿没有真实 run 背书。审阅区
   明示"未经验证"（提示不是校验）；要正式版走沉淀。这是使用者第四轮选择的代价，
   写进这里防将来有人忘了为什么。
2. **token 成本**：一次生成 = 一次起草 run；访谈另算（可选）。与沉淀同量级。
3. **草稿不是合同**：AI 只起草，确认（commit）是唯一入口；"检查边界段 / 未经验证"
   是提示不是校验。
4. **内置角色纪律**：`interviewer` / `card-drafter` 不进业务选择（等值判断天然
   排除）；聊天放行只改 `interviewer` 那两处、各带 WHY 注释。
5. **两个功能独立是拍板行为**：不加任何"访谈 → 生成"的传递；将来若要自动，是
   沉淀 Agent 的入口问题，不是本设计的缺漏。
6. **技能分支不复制沉淀逻辑**：素材源扩展是唯一新增面；起草/审阅/commit 全复用。
