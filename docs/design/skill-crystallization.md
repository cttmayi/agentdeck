## 1. 背景与目标

使用者在 AgentDeck 的聊天（conversation run）里和 agent 协作，经常完成**可复用**的事——
修了一个流程、跑通了一段部署、整理出一套检查步骤。这些"做法"当前只活在对话历史里，
下次要再用就得重讲一遍，或者翻聊天记录。

**目标**：把"这段聊天做了什么、怎么做的"提炼成标准的 `SKILL.md`，进**提炼专用根
`~/.agentdeck/skills-mine/`**（与安装根 `~/.agentdeck/skills/` **物理分离**，理由见 §1.1），
以后挂到 agent 上复用；用多了发现不够 → 在旧版基础上**进化**（覆盖 + git 版本管理）。

### 1.1 为什么提炼的与安装的必须分根（2026-10-18 使用者提出）

使用者："**不应该把安装的 skill 和我自己提炼的 skill 混在一起（混在 `~/.agentdeck/skills/`）**"。
两者语义完全不同，混在一个根里有真实的损害：

| | 安装的（外部） | 提炼的（自己的） |
|---|---|---|
| 来源 | 远端服务 / GitHub / 本地清单 / localdir | 自己的聊天沉淀 |
| 更新语义 | **重新安装覆盖**是正常行为 | 自己的进化被"重装"覆盖 = **资产丢失** |
| 版本管理 | 外部内容，重新装就行 | 自己的资产，要 git 历史 / 回退 / 备份 |
| 信任 | 别人写的（可能有许可证 / 更新） | 自己的做法（可能含工作上下文） |

**落地方案（两个根）**：

```
~/.agentdeck/skills/          ← 安装的（现状不变：install API 落这）
                                   不 git 化，重装覆盖语义不变
~/.agentdeck/skills-mine/     ← 提炼的（新根，git 化 + 平台自动 commit）
                                   平台永不自动覆盖——进化 = 起草→确认→覆盖+commit
```

- **store 索引**：`Skill.source` 标记 `mine`，界面按「安装 / 我提炼的」分组。
- **注入**：零改动——注入走 store 的 `skill.body`（`syncInjectedSkills(workDir, skillDir, skills)`
  的 payload 来自 store 记录，不从磁盘根读）。
- **slug 冲突**（同 slug 两个根都有）：**提炼的优先**——运行期用提炼的 body，自己的版本
  遮蔽安装的；列表里被遮蔽的安装项标注「被你的版本遮蔽」。
- **git 化范围**：只 `skills-mine` 一个根——平台自动 commit 的语义正好是"你沉淀的东西"，
  安装的外部内容平台不碰（要备份安装的，使用者自己 git 整个 `~/.agentdeck` 即可）。

**为什么值得做（调研共识）**：skilldistill 说得最直接——"Agents repeatedly discover useful
procedures, but most of that knowledge stays trapped in the conversation"（知识困在对话里）。
业界对"从对话提炼 skill"的共识是：**审阅是必要环节**（不自动入库），且 SKILL.md 遵循统一结构
（Anthropic 官方博客的「渐进式披露」：frontmatter 的 `name`/`description` 只够判断"何时用"，
正文是第二层细节，认为相关才全文读入）。

## 3. 流水线总览

```
两个场景，同一套流水线：
  聊天（conversation）——Chat 标题栏「沉淀成 skill」按钮（§4.1）
  任务（task / review）——任务详情页「优化 skill」按钮（§4.3，素材带用户/审核反馈）

①触发（用户主动按钮）→ ②沉淀目标面板（新建 / 更新本次加载的 skill；新建必填作用描述）
→ ③提炼（skill 起草 run：素材 + 作用描述 + 模板 + 不结晶清单 + 现有 skill 列表）
→ ④审阅（界面预览/编辑 → 用户确认，平台不自动入库）
→ ⑤入库（~/.agentdeck/skills-mine/<slug>/，source:'mine'）
→ ⑥进化（起草修订版 → 确认 → 覆盖 + git 自动 commit，可回退）
```

## 4. 触发（调研后定稿；信号建议暂缓，见 §4.2）

### 4.1 用户主动（主触发）——会话级按钮（整体提炼，不做细节选择）

**2026-10-18 简化**：初版设计过"轮次级按钮 + 选起点轮 + 范围摘要"的精细交互，
使用者试想场景后定了更简单的形态："**就整体聊天结果来提炼，不用去选择对话细节**"。
理由：选起点/调范围是精细控制，但实际使用成本高、收益低——**素材给整体，筛选交给
起草 run 自己**（§5 的不结晶清单 + 提炼本身就是筛选：从整段对话里挑出可复用的步骤）。

**按钮形态与位置**
- **会话（conversation）级按钮**「沉淀成 skill」，放在 Chat 视图的会话标题栏
  （与「停止」等会话级操作同层级）。
- 会话里**至少有一轮已结束**即可用（素材 = 已落库的部分）。
- 不放在消息行/气泡上——沉淀的单位是整个聊天，不是某一轮。

**点击后：先选沉淀目标（新建 or 更新本次对话加载的 skill），再起草**
1. 点按钮 → 弹出「**沉淀目标**」选择面板：
   - 「**新建 skill**」——起草全新技能（素材 = 整段会话）。选中后出现「**作用描述**」
     输入框（2026-10-18 使用者补——**担心 agent 自己总结会偏离**）：
     - **必填**，placeholder 引导："这个 skill 是做什么的？什么时候用？一句话或几行
       都行"（触发条件导向，如"用来审核 xx 类报告的步骤"）。
     - **双重用途**：① 进起草 run 的 prompt，锚定提炼方向（防抓错重点/步骤幻觉）；
       ② **直接作为草稿 frontmatter `description` 的基底**——"这个 skill 干什么用"
       这一层是用户自己的话、不可能偏（渐进式披露第一层，§4.4），agent 只负责补正文
       （When to Use / Procedure / Pitfalls / Verification），审阅时可微调措辞。
   - 「**更新本次对话加载的 skill**」（2026-10-18 两次修正定稿）——列表列出**当前对话
     实际注入的 skill**（不是全库）：
     - **为什么只列被加载的**：对话的前提往往是"**某个 skill 不好用，这次对话就是在矫正
       它**"——更新目标天然是**正在用的那几个**；让用户从全库挑既慢又不符合心智模型。
       当前对话没挂 skill（注入为空）时此选项**置灰**，提示"本次对话没有加载 skill，
       只能新建"。
     - **提炼的**（`skills-mine`，标注"你的"）——选中 = 进化（§7）：素材 = 整段会话 +
       该 skill 现有 SKILL.md，起草"修订版"，确认后覆盖 + git commit。**作用描述可选**
       （有旧 SKILL.md 作基线 + 对话本身在矫正它，偏离风险小；填了同样进 prompt + 作为
       description 修订基底）。
     - **安装的**（`~/.agentdeck/skills/`，标注"安装的"）——选中 = 基于它创建你的版本：
       素材 = 整段会话 + 安装版 SKILL.md，确认后存为 `skills-mine/<slug>/`
       （`source: 'mine'`）并**遮蔽安装版**（§1.1），安装根原文件不动。
   - 选择面板同时显示会话素材摘要（N 轮 / M 次工具调用），用户确认目标后进入起草。
2. 起「skill 起草 run」（kind `skill-draft`，§5；更新/基于安装 = 素材里带现有 SKILL.md）。
   **素材硬要求**：无论新建还是更新，素材都含**整个会话的 run events**（全部 turn：
   消息 + 工具调用 + 输入输出），且**必须保留工具调用及其结果**——提炼"怎么做"依赖
   真实的命令/脚本，只给对话文本会写出幻觉步骤。
3. 界面进入"**起草中**"状态：**复用 RunLog 显示起草 run 的实时日志**（现成能力），
   可「停止」（现成按钮），失败可看日志。
4. 起草完成 → 进入**草稿审阅**（§6，交互同前）：
   - **预览**：SKILL.md 渲染预览（现成 markdown 渲染器 `apps/web/src/lib/markdown.ts`）。
   - **编辑**：`name`（kebab-case）、`description`（校验必须含触发条件）、正文
     （When to Use / Procedure / Pitfalls / Verification）都可改。
   - **支持文件**：草稿带脚本/模板（`scripts/`、`templates/`）时，文件列表 + 逐个预览。
   - **撞 slug 校验**（只对"新建"有意义——"更新"已在第 1 步明确目标）：提炼根已有同 slug
     → 提示"已有你提炼的同名 skill（vN）"，选「**覆盖（进化）**」走 §7 或「**改名**」；
     安装根已有同 slug → 提示"已有安装的同名 skill，你的版本将**遮蔽**它"（§1.1），确认即入
     或改名。
   - 「**确认入库**」→ 写 `~/.agentdeck/skills-mine/<slug>/` + store `source: 'mine'`
     + git commit → 完成提示"已沉淀 skill <name>，可在技能库查看/挂到 agent"。
   - 「**取消**」→ 丢弃草稿，回到聊天，聊天内容不受影响。

**边界情况**
- **当前对话没加载任何 skill** → 沉淀目标面板的「更新本次对话加载的 skill」**置灰**，
  提示"本次对话没有加载 skill，只能新建"。
- 会话很长（轮数多）→ 提示"素材较大（N 轮），起草 run 上下文有限，可能截断"——**不阻断**；
  起草 run 会从素材里挑核心步骤，截断的影响有限。
- 起草 run 失败 → 提示失败原因 + 「查看日志」「重试」（素材原样重发，不重复打包）。
- 对话还在进行（run 未终态）→ 素材只取已落库的部分，提示说明。

#### 4.1.1 界面改版（2026-10-19 使用者定稿）：任务详情式全页，替换抽屉

> ⚠️ **本节取代上面 4.1 的"弹出沉淀目标选择面板（抽屉）"的呈现方式**——目标选择、
> 素材摘要、起草日志、草稿审阅这些**内容与流程语义不变**（§4.1 / §5 / §6 仍是权威），
> 变的只是**载体与组织**：从"设置式抽屉"改成"任务详情式全页"。

**动机（使用者反馈）**：抽屉是"填表单 → 提交 → 看结果"的**设定感**；沉淀的本质是
"发起一条 run → 看它跑 → 审阅收口"，应该是任务详情页那种**执行感**——固定栏头
（返回/标题/状态/操作）+ 正文分节堆叠 + run 徽标实时状态 + RunLog 常驻。

**载体：右主区切换成沉淀流程页（MainArea 壳），不再弹抽屉**
- 点「沉淀 skill / 优化 skill」→ 右主区换成沉淀流程页；栏头 = 返回键 + 标题「沉淀 skill」
  + 副题（**来源上下文**：哪个对话/任务、源 run id、轮数/工具调用数）+ 随流程变的操作。
- 返回键回到来源视图（对话消息流 / 任务详情），栏头副题始终标着"来自哪个 run"兜底上下文。
- 权衡（使用者已确认接受）：全页意味着点按钮**暂时离开**来源视图，返回键 + 副题补回上下文；
  抽屉"不离开现场"的便利让位给执行感。

**页面结构：步骤条 + 分节渐进展开（不是 phase 互相替换）**

```
┌──────────────────────────────────────────────────────────┐
│ ‹ 返回      沉淀 skill                    [开始起草]         │ ← 栏头（固定，操作随流程变）
│   来源：对话「…」· run 01M5… · 3 轮 · 25 次工具调用          │
├──────────────────────────────────────────────────────────┤
│    ① 沉淀目标       ② 起草 run        ③ 审阅入库            │ ← 流程步骤条（当前步高亮）
├──────────────────────────────────────────────────────────┤
│ ▸ 素材摘要（折叠，起草前就可见）                            │
│    打包自本次对话/任务：3 轮 · 25 次工具调用 · 有审核判决      │
│    · 无用户反馈                                            │
├──────────────────────────────────────────────────────────┤
│ ▸ 沉淀目标（当前步，可编辑）                               │
│    (•) 新建 skill —— 作用描述 [……必填……]                  │
│    ( ) 更新本次加载的 —— [技能单选列表（你的/安装的徽标）]     │
│    [开始起草]                                             │
├──────────────────────────────────────────────────────────┤
│ ▸ 起草 run 01M5…（徽标:起草中，实时）        [停止]          │ ← 起草后才出现
│    ┌──────────────────────────────────────────┐           │
│    │ RunLog 实时日志（SSE）                     │           │
│    └──────────────────────────────────────────┘           │
├──────────────────────────────────────────────────────────┤
│ ▸ 草稿审阅（起草完成后解锁，徽标:已完成）                   │
│    slug / name / description / 正文编辑 + 预览折叠          │
│    [确认入库]  [放弃]                                     │
├──────────────────────────────────────────────────────────┤
│ 完成态：已沉淀 skill <name>（skills-mine · git 已提交）      │
│    [查看技能]  [返回]                                      │
└──────────────────────────────────────────────────────────┘
```

**与旧抽屉形态的核心差别**

| | 旧（抽屉） | 新（任务详情式全页） |
|---|---|---|
| 载体 | 右侧滑入抽屉，覆盖在页面上 | **全页 MainArea**，与任务详情同壳 |
| 流程呈现 | 三个 phase 在抽屉内互相替换 | **步骤条 + 分节渐进展开**，全程一览 |
| 起草日志 | phase 跳走就看不见 | RunLog **常驻**在审阅下方 |
| run 状态 | 只有一行小字 | 步骤②带实时徽标（起草中/已完成/失败） |
| 失败 | 弹回目标面板 + 一行错误 | 步骤②失败态：徽标红 + failureReason + [重新起草] |
| 完成 | toast 一下 + 关抽屉 | **完成态**：已沉淀 + git 状态 + [查看技能] |
| 素材 | 起草后才有数字 | **起草前**就显示素材摘要 |

**任务感从哪来（四条硬规则）**
1. **栏头操作随流程变**：目标态 → [开始起草]；起草中 → [停止]；审阅态 → [确认入库]；
   完成态 → [查看技能]。与任务详情栏头的「优化 skill」按钮同一位置、同一交互习惯。
2. **步骤条 = 任务的 stage 感觉**：①→②→③ 编号 + 连线；当前步 accent 高亮、已过步 ok 色、
   失败步 bad 色。起草 run 的 `status` 直接驱动步骤②徽标（复用 `RUN_STATUS_CLASS`）。
3. **渐进展开而不是跳转**：开始起草后目标分节收成只读摘要；起草完成审阅分节解锁并滚到审阅；
   **日志永远可见**——与任务详情"看完 verdict 还能翻 run 日志"同一道理。
4. **冲突/遮蔽交互不变**：新建撞提炼根 slug → 审阅分节顶部 notice + [改成更新它（进化）]；
   更新安装的 → 同 slug 落你的版本并遮蔽（§1.1）。

**后端小改动（界面改版实作，2026-10-19）**
- `GET /api/crystallize/targets` 增加 `materialStats: { turns, toolCalls } | null`：
  buildMaterial 是现成读操作，空素材返回 `null`，前端在目标态就禁用 [开始起草] 并提示
  （**早失败**，而不是起草完才发现 400 empty_material）。
- `POST /api/crystallize/draft`：起草 run 带 `crystallizeTarget`（新建 / 更新哪条）随 run
  落库——恢复进行中的起草进审阅/入库时按它还原目标（commit 需要目标：更新 = 复用原 id
  进化；不能凭用户这次又选啥猜）。`purpose` 不落库（只影响起草 prompt）。
- `POST /api/crystallize/commit`：入库成功后把起草 run 标 `crystallized: true`——targets 的
  `activeDraft` 据此跳过已入库的草稿（否则每次重开都会把沉淀完的草稿再"继续"一遍）。

**归属：沉淀不是任务（2026-10-19 使用者定）**
- 起草 run 仍是 **run**（`kind: execute`、`subject: {type: 'skill-draft'}`），**不挂 issue**、
  **不进任务列表**——它是从对话/任务发起的"工具动作"，不是"工作项"；也不进任务的审核
  闭环（`reviewerAgentId: null`、无返工）。任务列表里不会出现沉淀条目。
- 进度/历史只能从来源（对话 / 任务）再进流程页看——这是该方案的既定代价（使用者已接受）。

**恢复进行中的起草（补"关页面丢进度"缺口，2026-10-19 使用者定 A 方案附带）**
- 现状缺口：起草 run 在后台真实地跑，但关闭流程页后 UI 不知道它的 id，重开会另起一条
  → 重复起草。
- 修法：
  1. 起草 run 上**记 source**（`subject.sourceRunId` = 源 run id）——现在 subject 里没有
     这条链接，加上是恢复的前提。
  2. `GET /api/crystallize/targets` 顺带返回 `activeDraft: { runId, status, target } | null` =
     该源 run 最近的、**未入库**的 skill-draft run（起草中 / 已完成待审阅都算；
     `target` = 起草时落库的沉淀目标，恢复时按它还原）。
  3. 流程页打开时：有 `activeDraft` → 顶部提示"有进行中的起草（起草中/待审阅）"，
     「继续」挂回那条（RunLog 接着看、审阅接续），或「新起草」（放弃旧的）；
     没有 → 正常从目标态开始。

**状态**：设计已定（2026-10-19），**已实作**（§8.1 的 9，2026-10-19）——含上面提到的
随 run 落库沉淀目标与对话按全部轮次匹配两处实作补充。

#### 4.1.2 三轮：沉淀成为独立一页（导航列「工具」之下）

> ⚠️ **本节取代 4.1.1 里"流程页住在聊天/任务右栏"的载体**——流程的**内容与语义**
> （目标 / 起草 / 审阅 / 入库、步骤条 + 分节、素材摘要、恢复进行中）全部不变，
> 变的只是它**在哪儿**：从一个视图的右栏，变成一个自己的页面。

**动机（使用者原话）**："在导航列，工具下，增加一下流程页（TAB），沉淀的过程在此页
进行，它有类似任务页一样的列表，可用于切换沉淀任务。"（二轮之后使用者仍觉得切走回不来、
且沉淀混在聊天/任务里不像一件独立的活。）

**页面形态：与任务页同构的一页**
- 侧栏第 7 项「沉淀」，排在「工具」之下；顶栏页名同一个词条（`crystallize.navTitle`）。
- **左栏 = 沉淀任务列表**（`GET /api/crystallize/drafts`）：未入库的起草 run，
  每行 = 来源（对话/任务 + 标题）· 状态徽标 · 目标（新建 / 更新 <skill>）· 时间。
  使用者定稿：**已入库的不显示**（列表永远干净），失败的仍然显示（还要重试）。
  列表每 6 秒轻刷新一次（起草中的 run 完成/失败时徽标跟着动）。
- **右栏 = 流程页**（复用 §4.1.1 的 MainArea 壳与分节），未选中时是空态 +
  「新建沉淀」提示。
- **切换沉淀任务** = 点列表行（同一页换 runId，不跳走）。

**地址**：`#/crystallize`（列表空态）/ `#/crystallize/<runId>`（选中某条）。
二轮的 `#/chat/crystallize/<runId>`、`#/tasks/crystallize/<runId>` **保留并重定向**
到 `#/<crystallize>/<runId>`（书签与分享链接不作废，`syncRoute` 用 `location.replace`
只换当前这一格，不污染后退栈）。

**入口（三条，都落到这一页）**
1. 聊天页「沉淀成 skill」→ `#/crystallize/<源 runId>`；
2. 任务页「优化 skill」→ `#/crystallize/<任务执行 runId>`；
3. 本页「新建沉淀」→ 来源选择器（`GET /api/crystallize/sources`）→ 选中即进目标步骤。

**来源选择器（本页新建）**
- **对话**：有轮次带 runId 且最后一轮没报错（与聊天页按钮同一判据），带轮数预览。
- **任务**：有**终态**执行 run 且**审核过**（§4.3；`hasUserFeedback` 当前恒 false）——
  未达门槛的任务**不列出**（列出来是一条点了进不去的死路）。
- 一次算齐源 runId（不依赖 `GET /api/runs` 的 100 条上限，也不让前端 N 次拉取）。

**门槛三处拦（§4.3）**
1. 来源选择器只列达标任务（服务端筛）；
2. 流程页 `canStart` 拦（`scope==='task'` 且 `reviewed || hasUserFeedback` 才可开始，
   置灰时 title 说明原因）；
3. `POST /api/crystallize/draft` 返回 400 `task_gate`（界面画对了而忘了带时的兜底）。
   e2e 夹具因此要**先有一条 completed 审核 run** 再过门——测试的是机制，不是门槛本身。

**草稿 run 归一（`resolveSourceRun`）**
左栏列的是**起草 run**，点一条进来的地址里带的就是草稿 id。起草 run 自己的事件
是产出的 SKILL.md——拿它当素材就成了"用草稿沉淀草稿"。所以 `crystallizeTargets` 与
起草路由入口都先归一：`subject.type === 'skill-draft'` → 换回 `subject.sourceRunId`
指向的源 run；源 run 已被清理时原样返回（走"素材为空"的正常分支）。归一之后
`activeDraft` 正好找回这条草稿 → 流程页直接进「继续」。

**归属不变**：沉淀仍然**不是任务**（起草 run 不挂 issue、不进任务列表）；这一页的列表
是沉淀自己的列表，与任务列表互不影响。

**状态语义：待审阅 ≠ 已完成（2026-10-19 使用者："很多沉淀任务标注'已完成'，实际没有完成"）**

初版左栏直接把**起草 run 的 status** 当任务状态显示，于是 run 一跑完列表就写「已完成」。
可 run 完成只意味着**草稿写出来了**——沉淀的完成线是**入库**（写 skills-mine + git commit）。
真实数据核对：当时 5 条草稿里 3 条显示「已完成」，而 `~/.agentdeck/skills-mine` **一条都没有**
（仓库都没建），也就是说这 3 条一条都没沉淀完。**标签在撒谎。**

现在中间加一层任务状态（`apps/web/src/lib/crystallize-state.ts`）：

| 起草 run | 列表徽标 | 颜色档 |
|---|---|---|
| queued / dispatched / deferred / waiting_local_directory / running | 起草中 | `in_progress` |
| completed（未入库） | **待审阅** | `in_review` |
| failed | 起草失败 | `failed` |
| cancelled | 已停止 | `cancelled` |
| crystallized: true / discarded: true | 不进列表 | — |

流程页「完成态」（绿框 + 已沉淀 + git 状态）**只在 commit 成功之后**出现，所以那才是"真完成"。
恢复提示里的状态词也用任务状态（"有一条草稿还没收尾（待审阅）"），不再说「已完成」。

**放弃：给没入库的草稿一个出口（同一次返工）**

发现的问题：旧版流程页的「放弃」只重置本地界面状态，草稿仍在库里、仍在左栏——于是
"很多沉淀任务"永远停在那儿，列表只增不减（`abandonReview` 的注释都写着"回目标态重新来过"，
可它什么也没删）。现在：

- `POST /api/crystallize/discard { draftRunId }`：校验是起草 run 且属于本工作区；还在跑就先
  `cancel`；然后打 `discarded: true`。已入库的返回 409 `already_crystallized`（那是已发生的事实，
  该去技能页删）。幂等：再放弃一次仍是 200。
- `listCrystallizeDrafts` 与 `findActiveDraft` 都跳过 `discarded`——列表干净了，
  重开流程页也不会再把放弃的草稿"继续"一遍。
- 入口两处：左栏行右侧的「×」（与聊天/任务列表的删除钮同一格同一款，带确认框）、
  流程页审阅步的「放弃」（同样是真删除，完成后回列表并刷新）。

**控件纪律（2026-10-19 使用者指出"UI 风格和任务差很多"之后的返工）**

使用者原话："UI 风格和任务差很多，怀疑你没有用同一控件，请确认。"——确认结果是**确实没用**：
初版左栏是手写的 `li > button` + 一整套行样式，状态徽标自造 `.status-tag`，来源选择器是
手搓的遮罩浮层，"新建沉淀"还在列表顶上自插了一条按钮。任务页/聊天页的行、浮层、主操作位置
都不是那样。返工按"同一控件"逐项收口：

| 位置 | 别处用什么 | 本页改用 |
|---|---|---|
| 列表行壳 | `ListRow`（`list-row` 骨架：hover / 选中框 / `--list-row-min-h`） | `ListRow`（`rowClass="crystal-row"`） |
| 状态徽标 | 全局 `.badge {status}` + `lib/run-status.ts` 的 `RUN_STATUS_CLASS` 映射 | 同一份（映射从任务页搬到那个 lib，**不再两处各一份**） |
| 来源选择器 | `@agentdeck/ui/components` 的 `Modal`（遮罩 / Esc / 关闭钮做一次） | `Modal`（行也复用 `ListRow`） |
| 主操作位置 | 顶栏 `setPageActions`（聊天「新对话」、任务「新建任务」） | 顶栏 primary + `plus` 图标 |

`margin-bottom` / 边框 / 底色 / `h3` 字号与边距完全相同。**"同一控件"不能靠眼看，
要拿计算样式对齐。**

#### 4.1.3 未来扩展：沉淀 Agent（同流程页，产出类型维度，2026-10-19 使用者提出）

> 使用者："类似沉淀 skill 一样，通过对话或者任务来更新 Agent 的 prompt。"
> ——**反向沉淀**：把对话/任务里的经验结晶回**智能体指令**（`Agent.instructions`），
> 与沉淀 skill（SKILL.md）并列的第二种产出类型。**未来需求，未实作**，这里只记
> 流程页的复用口子，保证将来加它不改页面骨架。

**复用结论**：流程页骨架（① 定目标 → ② 起草 run → ③ 审阅入库）与"产出类型"解耦，
沉淀 Agent = 同一流程页 + 产出类型 = agent prompt。三处差异、其余照用：

| | 沉淀 Skill | 沉淀 Agent（未来） |
|---|---|---|
| ① 目标 | 新建 / 更新**本次加载的 skill** | 新建 / 更新**本次对话/任务实际涉及的 agent**（执行者、审核者） |
| ② 起草 run | 产出 SKILL.md 草稿（subject `skill-draft`） | 产出指令草稿（subject `agent-draft` 变体）；素材不变（events + 反馈 + 判决） |
| ③ 审阅入库 | frontmatter + 正文 → `skills-mine` + git | 指令文本 → 更新 `Agent.instructions`（无 frontmatter） |

**共享**：步骤条、素材摘要、RunLog 常驻、失败/完成态、恢复进行中的起草
（`activeDraft` 按 sourceRunId 泛化，不区分产出类型）。

**复用口子（设计上现在就成立，成本极低）**
1. subject 类型已是独立枚举——`skill-draft` 旁加 `agent-draft` 变体；起草 run 机制
   （executor 复用、reviewerAgentId:null、不挂 issue）一字不动。
2. draft 接口支持显式 `agentId`（缺省 = 源 agent）——agent 沉淀的起草者/目标者都明确，
   接口天然兼容。
3. 审阅分节按产出类型渲染——skill 版是 slug/name/description/正文；agent 版是纯指令文本。

**将来单独定的点**：agent prompt 的版本管理——skill 有 `skills-mine` git 根，agent 指令
没有对应 git 根；将来更新 agent prompt 要么在 agent 记录留历史/审计，要么也 git 化。
不影响流程页复用。

### 4.2 信号建议（辅触发）——⏸️ 暂缓，首版不做（2026-10-18 使用者定）

使用者："**4.2 信号建议（辅触发）先不做，这部分还没考虑清楚**"。设计方向（借
dsh-skill-evolution 的信号模型）记录在案，等考虑清楚再捡起：

| 信号 | 条件 | 含义 |
|---|---|---|
| `complex` | 成功 turn 且 ≥5 次工具调用 | 完成了一件复杂事 |
| `recovered` | 有失败步骤但 turn 仍成功 | 绕过了死路、找到了可行路径 |
| `repeated` | 相同工具序列重复 ≥N 次且成功率高 | 反复验证过的流程 |

思路：命中时 agent 在回复里**只问一句**"这段值得沉淀成 skill 吗？"——**不自动做**。
（AgentDeck 的 NG 原则是"平台不替使用者决定"；自动结晶会把使用者没有主动要的东西写进
他的技能库，噪音大于收益。信号只用来**降低使用者发现"这段可沉淀"的成本**。）

**为什么暂缓**（没考虑清楚的点，捡起时先回答这些）：
- 信号定义本身：`complex` 单独命中太弱（任何长 turn 都符合），要不要佐证门槛
  （dsh-skill-evolution 要求 complex 被 recovered/repeated 佐证）？
- 噪音控制：run 结束时多一句"要沉淀吗？"——频繁出现就是打扰，什么频率可接受？
- 触发时机与渠道：信号在 run 结束（而不是聊天中）检测，与用户主动按钮怎么衔接？

首版**只有用户主动**两条触发（§4.1 聊天 + §4.3 任务），信号建议不做。相关开放问题见 §9。

### 4.3 任务场景：优化当前 skill（用户 / 审核反馈）——2026-10-18 使用者新增

使用者："**任务可能也合适这样的提炼（通过用户的反馈或者审核的反馈，可以优化当前的 skill）**"。
任务才是 skill 的"生产环境"：挂载的 skill 在实际任务里被验证，**用户纠正 / 审核打回 =
最真实的进化信号**（skill 哪一步错了、缺什么、边界在哪）——比聊天更接近"越用越准"。

**入口**：任务详情页（Tasks detail，RunLog 所在页）——任务 run 终态后，标题栏
「**优化 skill**」按钮（与 Chat 标题栏的「沉淀成 skill」并列，同一套面板与流程）。

**触发前置（2026-10-18 使用者补充：必须检查，否则按钮置灰）**：
- 按钮**可用** ⟺ 任务 run 终态 **且**（**有用户反馈** 或 **审核过**）。
  - "有用户反馈" = 任务已存在用户评价/反馈记录（不是即将填的——那是点进去后补充的）。
  - "审核过" = 存在审核 run 的判决。
- **否则按钮置灰**，提示"该任务没有反馈、也未审核，无法据此优化 skill"
  （提示路径：先给任务加反馈，或让它走完审核——AgentDeck 任务本就有执行→审核链路）。
- 为什么**必须**有反馈或审核：任务沉淀的价值就是**反馈驱动进化**——没有进化信号的任务，
  光凭执行过程沉淀没有"矫正"意义（执行记录不是进化素材）；置灰把这条语义钉死。

**素材**（与聊天版的差异——多了反馈）：
- 任务 run 的 events（执行全流程：消息 + 工具调用 + 输入输出）。
- **审核反馈**（有则自动带）：审核 run 的**判决**（结论 / 理由码 / 严重度 / 证据 / 动作）——
  起草 run 从中看出"skill 的哪一步导致审核不过"。
- **用户反馈**（有则自动带已有的；点进去后可再补充一段："哪里不对 / 该怎么改"）。
- 素材硬要求同 §4.1：保留工具调用及其结果。

**沉淀目标**：与聊天版**共用**沉淀目标面板（§4.1 第 1 步）——新建 / 更新本次任务加载的
skill（更新目标 = 任务 run 实际注入的 skill；反馈指向的 skill 通常就是它）。

**作用描述**：新建必填（同聊天版）；更新**可选**——用户反馈 / 审核反馈本身就是方向锚定，
比聊天版更不需要额外描述。

## 5. 提炼——「skill 起草 run」

> ⚠️ **机制部分已由 §5.0 取代**（2026-10-19 四轮）：素材不再内联进第一句话、起草不再只靠
> 一段散文指令、产出不再是单个 SKILL.md。§5 余下的**语义**（不结晶清单、SKILL.md 结构、
> 支持文件与本库一致）仍然有效，且**搬进了内置 skill**（§5.0.2）——一处维护。

### 5.0 生成流程重设计（2026-10-19 四轮，使用者提的五点 + 补充）

使用者的原话与要求：

1. 对话素材是保存在文件中的，让 Agent 去读取。
2. "沉淀 skill"用一个优秀的 skill 去生成。
3. 生成的 skill 可能是多个文件，呈现上需要优化。
4. 审阅草稿时，SKILL.md 明明有 name 和 description，应该不需要填空。
5. 有可能是新建或者是更新，是否可能有对比的形式去显示，考虑 git 历史 list，选中看文件对比。
（并明确"不限于这几项"。）

#### 5.0.1 现状的五个病灶（逐条对应）

| # | 现在怎么做的 | 为什么不行 |
|---|---|---|
| 1 | `buildMaterial` 把全部轮次的消息 + 工具调用 + 判决拼成**一整块文本**，塞进第一句话 | 长对话直接撑爆 prompt；agent 只能"通读一遍"，不能按需回查某一步；证据也无法在界面里核对 |
| 2 | 起草要求写在 `buildDraftPrompt` 的一段散文里，且起草 run 的 `skills: []`（注释还写着"注入会干扰"） | 不可迭代、不可评估、不可复用；每个细节都要改代码 |
| 3 | 产出契约是单文件 SKILL.md + 末尾 `===== FILE: scripts/xxx.sh =====` 尾巴 | 前端**只解析 frontmatter，从不解析 files**——多文件产物被塞进正文丢掉；界面没有文件树 |
| 4 | 审阅把 slug / name / description / body 摆成四个输入框 | 与 SKILL.md 的 frontmatter 重复，容易改出一份"框里是 A、文件里是 B" |
| 5 | 更新场景只显示最终正文；skills-mine 的 git 历史没有入口 | 看不出"改了什么"，进化等于盲签；已有 git 历史白白浪费 |

顺带发现的两个能力现状（决定改造成本）：`Skill.files`（相对路径 → 文本）与
`resolvePayloadEntry`（安装/入库共用的规范化与限额）**本来就支持多文件**，只是没人喂它；
`synchronizeInjectedSkills` 会把 `skills:` 传进来的技能**写成工作目录里的真文件**
（`.claude/skills/<slug>/`），所以"用一个 skill 去生成"零新机制。

#### 5.0.2 (1) 素材落盘：material/ 目录，agent 自己去读

起草 run 的工作目录里分两块：

```
<workRoot>/skill-draft-<draftRunId>/
├── material/                 ← 平台写，agent 只读
│   ├── 00-README.md            索引：来源、轮数、工具调用数、每轮一句话摘要、
│   │                           "怎么用这些文件"、"别照抄素材原话"的提醒
│   ├── meta.json               结构化元信息（scope / turns / toolCalls / source / target）
│   ├── turns/001.md …          每轮一个文件：使用者原话 + 该轮 text / tool_use / tool_result
│   ├── task-run.md             （任务场景）执行 run 的完整消息
│   ├── verdict.md              （有则）审核判决
│   ├── feedback.md             （有则）使用者反馈
│   ├── skills-index.md         现有技能清单（slug / name / description）——判重与 FOLD_INTO
│   └── existing-skill/         （更新场景）现有 SKILL.md + 支持文件原样
└── skill/                    ← agent 写，平台校验后读（产出）
```

- **为什么必须在 workDir 里**：claude run 有 PreToolUse 隔离 hook，越界路径直接 deny
  （`executor.ts` 那段注释记着实测）。素材放在 dataDir 别处 agent 根本读不到——
  所以这不是风格选择，是硬约束。
- 第一句话只给**指针 + 契约**：素材在 `material/`（先读 `00-README.md`）、产出写到
  `skill/`、以及本次特有约束。全文不再内联。
- 素材同时是**审计料**：这份 skill 是根据什么生成的，事后能翻；界面里可预览
  （§6.1 的「素材」分节）。
- 保留：**永久保留，不自动清理**（2026-10-19 使用者定稿，见 §5.0.9 第 1 条）——素材是
  "这份 skill 依据什么生成"的唯一证据。代价是磁盘没有上限，界面上标明目录位置、由使用者
  自己清理，不做自动过期。

#### 5.0.3 (2) 用一套"写 skill 的 skill"来生成

新增**平台内置 skill**（随代码走，不落 store、不进使用者技能列表）：

```
apps/daemon/assets/builtin-skills/writing-skills/
├── SKILL.md            ← 渐进式披露第一层：何时用、怎么写
├── references/structure.md    章节模板 + 好坏对照示例
├── references/files.md        什么时候拆支持文件、目录布局与命名
└── references/checklist.md    交付前自检清单
```

`SKILL.md` 里承载的全部是原来散文里的知识，且更细：frontmatter 规则（name kebab、
description 必须含触发条件）、`## When to Use / Procedure / Pitfalls / Verification` 的写法、
"步骤里的命令必须原样可复制"、多文件拆分门槛、不结晶清单（§5.1 原文搬入）、
反模式（环境失败 / 工具吐槽 / 一次性叙述 / 幻觉命令）。

起草 run 改为 `skills: [writing-skills]`——注入后它成为草稿工作目录里的真技能，agent 用
自己的技能发现机制加载（渐进式披露：先只看 frontmatter+描述，需要时再读 references）。
`buildDraftPrompt` 随之瘦身成**任务块**：来源与目标、素材指针、产出契约、本次两条特有约束
（作用描述 / 更新基线），不再教"怎么写 skill"。

#### 5.0.4 (3) 多文件产物：写目录，读目录，树形呈现

产出契约（写进内置 skill 与任务块）：

- `skill/SKILL.md` **必须存在**，frontmatter 含 `name` 与 `description`；
- 允许并鼓励 `skill/references/*.md`、`skill/scripts/*`、`skill/templates/*`；
- 只写文本（UTF-8）；单文件与总量受限额（复用 `resolvePayloadEntry` 那一套），
  建议上限：单文件 256 KB、总量 1 MB、文件数 64；
- 不写 `.git`、隐藏文件、`..` 或绝对路径（与安装同一关）。

平台读取：递归读 `skill/`（跳过隐藏文件）→ `files: Record<relPath, text>`，
`SKILL.md` 单独解析 frontmatter。**兜底**（2026-10-19 定稿，§5.0.9 第 3 条）：目录为空
（generic 等没有写文件能力的 runtime）→ 回退旧口径（解析最后一条 text 消息），并在审阅界面
明说"这条是文本产物，没有支持文件"。

界面（§6.1）：文件树 + 选中文件内容；SKILL.md 排第一；每个文件带 新增 / 修改 / 删除
徽标；顶部显示文件数、总大小、校验结果。

#### 5.0.5 (4) 审阅不再手填 name / description

- `name` / `description` / `slug` 全部**从 SKILL.md frontmatter 解析**，界面只读展示
  （slug 默认 = name 的 kebab 化）；要改就改 SKILL.md 本身——**一处真相**。
- 唯一的人填项是**作用描述（purpose）**，它是给起草者的定位输入、不是产物字段；
  且**改为可选**（2026-10-19 定稿，§5.0.9 第 4 条）：留空则由 skill 从素材推断，审阅时把
  推断出的 description 摆在最上面让使用者一眼否定或接受。
- 校验（frontmatter 合法 / description 含触发条件 / 正文有 When to Use / slug 合法）失败
  → 审阅顶部红条 + 定位到文件；不允许"仍要入库"，先改。
- 入库请求不再传 `name` / `description` / `body`，只传 `files` + 确认过的 `slug`，
  服务端按 SKILL.md 复算一遍（客户端说的不算）。

#### 5.0.6 (5) 新建 / 更新：对比视图 + git 历史

- **新建**：对比 = 对着空目录全部新增（树里标 `+`）。
- **更新（mine / installed）**：草稿 vs 当前版本（installed = 安装根那份；mine = skills-mine
  最新提交）逐文件 unified diff，可切换"只看改动 / 看全文"；草稿里没有的文件标删除
  （更新 = 整目录替换，面板必须把删除列出来）。
- **git 历史（仅 `source: mine` 且 git 可用）**：右栏「历史」分节，`git log --follow -- <slug>/`
  的列表（时间 / 短 hash / 提交消息）；选中一条 → 该提交相对上一版的 diff（文件树 + 逐文件）。
- diff 在后端算（`git diff`/`git show` 或单文件 LCS），前端只渲染——两边各写一套必然漂。
- git 不可用：`history` 返回 `available:false` + 原因，界面照既有降级叙事显示"版本管理未启用"
  （沉淀与历史回退都不是核心功能，§7.3.1）。

#### 5.0.9 使用者定稿（2026-10-19 逐条确认）

| # | 问题 | 定稿 |
|---|---|---|
| 1 | 素材保留多久 | **永久保留，不自动清理**——素材是"这份 skill 依据什么生成"的唯一证据，宁可占盘。界面给入口打开目录；要删由使用者自己删（不做自动过期） |
| 2 | 更新时草稿里没出现的旧文件 | **按 `git status` 的方式罗列变更**（新增 A / 修改 M / 删除 D），可直接看 git diff；更新语义 = **整目录替换**，D 的文件随本次入库一并删除，入库前逐条可见 |
| 3 | 不能写文件的 runtime | **目录优先，读不到再回退文本**（单文件 SKILL.md），界面明确提示"这条是文本产物，没有支持文件" |
| 4 | 作用描述（purpose） | **改为可选**：留空则由 skill 从素材推断，审阅时把推断出的 description 摆在最上面供确认/否定 |
| 5 | 「按意见改一版」 | **放进 P1**（与 diff 一起做）：审阅页写一句意见 → 用同一份 `material/` 再起草一轮，新旧两版并列对比后选 |

由此确定的两条实作细节：

- **变更集的呈现直接借 git 的说法**：`A` / `M` / `D` + 每个文件的 `+n −m`，选中看 unified diff
  （后端 `git diff` 算，前端只渲染）。新建 = 全部 `A`（对着空目录）；更新 = 对着当前版本
  （mine 取 skills-mine HEAD，installed 取安装根那份）。
- **素材不清理 ⇒ 磁盘无上限**：`skill-draft-<id>/` 会一直留着。要求：① `GET
  /api/crystallize/material` 能列出并预览；② 界面上标明目录位置便于使用者自己清理；
  ③ 文档里把这条写成已知代价（不是遗漏）。


平台起一个**专门的 run（kind 建议 `skill-draft`）**，runtime 用当前 workspace 默认的
claude/codex，复用现有执行管道（第一句话投递、日志、审核收口——全部现成，零新机制）。

prompt = 拼装：
1. **沉淀素材**（§4.1 打包的消息 + 工具调用 + 结果）。
2. **用户作用描述**（§4.1 第 1 步，新建必填 / 更新可选）——锚定提炼方向；草稿的
   frontmatter `description` 以它为基底（用户的话，防偏离）。
3. **SKILL.md 模板指引**（§4.4 的结构约束）。
4. **现有 skill 列表**（name + description）——让起草者判断是否该 `FOLD_INTO`（合并进已有
   skill）而不是新建重复项。

产出 = SKILL.md 草稿（文本，落成一个临时候选文件，不进任何工作目录）。

### 5.1 不结晶清单（质量门）

以下情况**不许沉淀**（来自 dsh-skill-evolution 的硬性门，防垃圾技能冻结成长期错误行为）：

- 环境依赖失败（缺二进制、未配凭证、没装的包）——换个环境就废
- 对工具的负面评价（"工具 X 坏了"——会冻结成长期拒绝用某工具）
- 瞬时错误靠重试治好的（教训是"重试"这个模式，不是原始错误本身）
- 一次性任务叙事、没解决的失败

### 5.2 SKILL.md 草稿结构

```
---
name: <kebab-case 技能名>
description: <一句话，必须含触发条件——"当用户想……时用"——这是渐进式披露的第一层>
---

# <Title>

## When to Use   ← 触发条件展开
## Procedure     ← 可操作步骤（步骤里引用的命令/脚本要原样可复制）
## Pitfalls      ← 注意事项与边界（含"别在什么情况下用"）
## Verification  ← 怎么验证这步做对了
```

支持多文件（脚本/模板放同目录，如 `scripts/`、`templates/`），与现库 skill 结构一致
（如 `browser-use/` 是 `SKILL.md + LICENSE.txt + templates/`）。

#### 5.0.10 P0 实作（2026-10-19，含实作中发现的三个坑）

**新增模块**

| 文件 | 职责 |
|---|---|
| `apps/daemon/src/crystallize-material.ts` | `collectMaterial`（一轮一文件）+ `writeMaterial`（索引 / meta / 技能清单 / 更新基线）+ `draftRoot` |
| `apps/daemon/src/crystallize-artifacts.ts` | 读 `skill/` 目录、拆 frontmatter、校验（含限额与路径安全）、三种形态（files / text / refused） |
| `apps/daemon/src/builtin-skills.ts` | 读内置技能（`apps/daemon/assets/builtin-skills/<slug>/`）→ `SkillPayload` |
| `apps/daemon/src/run-text.ts` | 消息渲染（`formatRunMessages` / `lastTextOf`）——从 `crystallize.ts` 抽出，避免与素材模块成环 |
| `apps/daemon/assets/builtin-skills/writing-skills/` | 内置「写 skill 的 skill」：`SKILL.md` + `references/{structure,files,checklist}.md` |

**接口**：`POST /api/crystallize/draft` 改为先落盘素材、注入内置技能、`workDir` = 草稿目录；
新增 `GET /api/crystallize/artifacts`、`GET /api/crystallize/material`；`POST /api/crystallize/commit`
入参改成 `{draftRunId, target, slug?, files}`，name/description 一律由服务端从 frontmatter 解析。
`buildMaterial` / `CrystallizeMaterial` 删除（文本内联时代结束，留着就是死接口）。

**界面**：审阅 = 校验结论 + slug（默认取 name）+ 只读 frontmatter 摘要 + 文件树（A/M/D 徽标）+
选中文件编辑（**没有** Markdown 预览了——见 §10.17）；起草者拒绝沉淀时显示原因并只给
「重新起草 / 放弃」。

**实作中发现的三个坑（都修了，测试钉住）**

1. **文本兜底 + 更新会删文件**：`writeSkillFiles` 是"清空目录再写"，所以提交一份只有
   SKILL.md 的文件集合 = 把目标技能的支持文件全删掉。产出形态改用**磁盘**判（`skill/`
   目录在不在），文本模式的更新**合并**现有支持文件；界面也只在 files 模式才标「删除」。
   （e2e「文本兜底草稿更新时不删支持文件」）
2. **旧草稿的 frontmatter 不在第一行**：老 prompt 让 agent 在开头写「应并入：xxx」，
   于是真实数据里有草稿的首行不是 `---`。校验消息改成**引出当前首行**，使用者一眼知道
   删哪一行（不是只丢一句"缺少 frontmatter"）。
3. **素材必须在 workDir 里**：claude 的 PreToolUse 隔离 hook 会 deny 越界路径——素材
   落到别处 agent 根本读不到。这条写进了模块头注释，防止以后有人"顺手"挪走。

#### 5.0.11 P1 实作（2026-10-19）

| 文件 | 职责 |
|---|---|
| `apps/daemon/src/text-diff.ts` | 行级 diff（LCS + hunk 上下文 + 大文件退化）+ `diffFileSets`（A/M/D/same） |
| `apps/daemon/src/crystallize-material.ts` | 新增 `copyMaterial`（改版时复制上一版素材，跳过 `previous-draft/`、`feedback.md`） |
| `Run.revisedFrom` / `SubmitRunRequest.revisedFrom` | 改版草稿指向上一版 run（对比上一版靠它找回产出） |

**接口**

- `POST /api/crystallize/diff {draftRunId, files?, against?}`
  · `files` = **当次编辑后的内容**（人在审阅里改了一行，diff 就得反映改完的样子；不传则读磁盘）；
  · `against` = `current`（对已入库版本，即"入库会改什么"）| `previous`（对上一版草稿）；
  · 返回 `{against, baselineLabel, files:[{rel,change,added,removed,hunks,coarse}], totals}`。
- `POST /api/crystallize/revise {draftRunId, feedback}` → `202 {draftRunId, revisedFrom}`
  · 新 run 的 `material/` = 上一版素材**复制**（同一份证据）＋ `previous-draft/`（上一版产出）
    ＋ `feedback.md`（意见，优先级最高）＋ 索引页追加"这一版是按意见改一版"；
  · 为什么复制而不是共用目录：起草 run 的素材在它自己的 workDir 里（隔离 hook 只放行 workDir），
    跨 run 指过去 agent 读不到；而且直接改旧目录会把上一版的证据篡改掉。
  · 跳过上一版自己的 `feedback.md` / `previous-draft/`：不跳的话改到第五版会层层嵌套。

**界面**：文件树的「新增/修改/删除」与 `+n −m` **都来自 diff**（一处判据）；改版草稿默认
对比上一版，可切回对比当前版本；「素材」分节列目录 + 文件清单 + 预览（起草中也能看）；
审阅底部一句意见 + 「重新起草」。

**实作中发现的坑**

1. **同一行两个说法**：文件树徽标原本对"入库基线"算、旁边的 `+n −m` 来自 diff——切到
   "对比上一版"时同一行显示「新增 +1 −1」。现在徽标也走 diff；只有 diff 还没到（未拉/拉失败）
   才退回入库基线。
2. **两版草稿共用来源 run** 时，"继续"永远挂到新的那条（按来源找 activeDraft）——断言与冒烟
   夹具要分别喂不同的来源 run，否则看到的是另一版。
3. 末尾换行 / CRLF：行内容一样但文本不同，LCS 会说"没变"，而入库写下去的字节确实变了——
   显式记成"改了一行"（宁可多一行噪音，不要一份内容两个说法）。

**排版重排（2026-10-19，P1 之后）**：审阅页原来是一条 2030px 长的单列——参考信息
（素材摘要 68 + 沉淀目标 68 + 素材 345 + 日志 129 = 610px）压在"唯一要动手的地方"上面，
审阅起点在 y=932；编辑器只有 509px 宽，diff 在它下方 519px 处；素材清单还另造了一套
`.material-pane`。现在按 §6.1 的三条规矩重排（结论条 + 主区 + 折叠），并复测了数字。

⚠️ 重排的两条纪律：**不放宽正文列**（任务页/智能体页共用 `split-layout` 的 785px，
单独加宽就与它们不一致）；**不自造折叠控件**（用既有 `FoldSection`，它已被
`probe.html` 的探针钉着类名与 `aria-expanded`）。

**探针覆盖（2026-10-19）**：审阅页的排版进了布局探针（`pnpm run probe:layout` 的 `[沉淀]` 那 23 条，
`tools/layout-probe/`）。夹具是**直接写进 store** 的一条已完成起草 run（走接口会 spawn 真 CLI，
NFR-T-01 禁止；而 store 是带锁的单写者 ⇒ 探针为此**起停 daemon 两次**：首启把工作区与 agent 播种出来，
停掉、写夹具、再起）。三个踩过的坑写在那两处代码旁边：
① 两条草稿的 `queuedAt` **必须不同**（`findActiveDraft` 按它降序取最新，相等时退化成插入序 ⇒
界面「继续」挂到旧的那条，改版草稿的判据全量到上一版的数字）；
② 两条草稿**各挂一个源 run**（共用一个源时旧的那条永远挂不上——这是对的行为，
但探针"量第一版"的那段会静默量到第二版）；
③ 换草稿要**整页离开沉淀视图再回来**（在视图内部换 `runId` 时"结论条在不在"的等待立刻成立 ⇒ 量到别人的现场）。

**验证**（真浏览器冒烟，临时 data 副本 + 夹具草稿，跑完即清理）：
多文件草稿 → 文件树 2 项都标「新增」、frontmatter 摘要只读显示、只有 slug 一个输入框、
两栏布局实测 `260px 409px`、切换文件编辑区跟着换；文本兜底草稿（更新目标）→ 校验红条
点名首行、文件树只有 SKILL.md「修改」（**没有**假的「删除 LICENSE.txt」）、入库按钮禁用。
`pnpm run check` 1942 全绿（新增 20 条：素材落盘 / 产出读取与校验 / 内置技能 / e2e 五条）。

## 6. 审阅 → 入库（提炼根 `~/.agentdeck/skills-mine/`）

- 校验：frontmatter 合法（name/description 存在、description 含触发条件）、slug 唯一

## 7. 进化（覆盖 + git 版本管理）

### 7.1 触发

- **主入口（2026-10-18 定为显式选择）**：沉淀面板第 1 步选「更新本次对话加载的 skill」→
  选中其中提炼根的目标 → 进化（§4.1 第 1 步）。这是进化现在**唯一的前置入口**——
  "想更新哪个"在起草之前就定，而不是起草完撞 slug 才转弯；且目标限定为**本次对话实际
  注入的 skill**（对话=矫正它的不足）。
- 次级入口：新建时撞 slug 校验提示"已有同名 skill（vN），是否进化它？"（§4.1 第 4 步）——
  从这里也可以切到"更新本次对话加载的"。
- skill 挂载的 run 中 agent 发现问题（"这个 skill 缺了 X/过时了"）→ 建议使用者进化
  （语音提示，行动仍走沉淀面板）。

### 7.2 起草与覆盖

素材 = **现有 SKILL.md 全文 + 新经验** → 起草修订版 → 用户确认 → **覆盖旧文件**。

### 7.3 git 版本管理（使用者定的语义：覆盖 + git 类似版本管理）

- `~/.agentdeck/skills-mine/` **做成 git 仓库**：首次开做时 `git init`（实测安装根
  `~/.agentdeck/skills/` 当前不是 git 仓库；全局 git 身份已配置，平台自动 commit
  有身份可用）。**只 git 化提炼根**——安装根是外部内容，
  平台不自动 commit（§1.1）。
- 每次入库/进化后平台**自动 `git add` + `commit`**，commit message 带版本说明，如
  `skill <slug> v2：新增 X 边界`。
- 收益：`git log`/`git diff`/`git checkout` 回退/远程同步（推到私有仓库备份、换机器拉取）全免费，
  不用平台自己造版本表。

#### 7.3.1 git 可用性保护（2026-10-18 使用者要求：依赖的是**用户环境的 git**，不捆绑平台）

版本管理依赖系统 `git`——**用户环境可能没有 git，这是正常状态，不是错误**。
设计分两层（对比：早期兜底只有"失败不失败 run"，把 git 缺失当**异常**报——每次沉淀都
尝试 `git init`+`commit`、撞失败、产出一条"commit 失败"note，看着像出错；使用者要求
把它升级为**功能开关**：没有 git 就不需要版本管理）：

| 层 | 触发 | 行为 |
|---|---|---|
| **可用性开关** | 探测：daemon 启动时 + 每次沉淀/进化前 `git --version`（spawn 探测，超时/非零/找不到 → 不可用） | **git 不可用 → 版本管理关闭**：跳过 init 与 commit，沉淀/进化**照常写盘 + store 索引**（功能完全不受影响，只少历史回退）；note 一条说明"版本管理未启用（系统无 git），沉淀照常、无历史回退"——**不是错误** |
| **降级兜底** | git 可用但操作失败（`git init`/`add`/`commit` 非零、`.git` 损坏、权限不足） | note 降级，run 照常（保留早期兜底的语义——这层针对"有 git 但坏了"） |

- **自动恢复**：git 可用性每次沉淀前都探测 → 用户中途装了 git，下次沉淀自动恢复版本管理
  （幂等 `git init` + 首次 commit 把已有沉淀收进历史）。
- **半途状态**：git 不可用期间沉淀的进化没有历史——装 git 后**不补造历史**（没有基线，
  造出来是假的），从恢复那一刻起记录；note 里说明这一点。
- 另在 skills-mine 仓库配 **per-repo 兜底身份**（`agentdeck <agentdeck@localhost>`），
  防"有 git 但没全局身份"时 commit 挂掉（这是降级兜底层的一部分）。

### 7.4 历史与版本对比（2026-10-19 四轮，对应 §5.0.6）

- `skills-mine` 已经是 git 仓库（每次沉淀/进化一条 commit），历史**不需要新造**，只是没有入口。
- 新增三个只读接口（§5.0.7）：`history` / `revision` / `compare`。都走
  `run-hooks/skill-mine.ts` 现有的 `runGit`（`gitPath` 可注入 → 测试不依赖真 git，
  与 NFR-T-01 同一理由）。
- `git log --follow -- <slug>/` 取该技能目录的历史；`git show <rev>:<slug>/<file>` 取某版
  文件；`git diff <rev1> <rev2> -- <slug>/` 算逐文件差异。
- 界面：技能页/审阅页的「历史」分节，选一条看那一版的文件树与 diff；安装的 skill
  （非 mine）没有 git 历史，只有"草稿 vs 安装版本"的对比。
- git 不可用 = 正常状态（§7.3.1）：`available:false` + 原因，界面显示"版本管理未启用"，
  其余功能不受影响。

## 9. 沉淀的内置起草者（2026-10-20 定稿，**已实作**，决策编号 **D81**）

现状：起草 run 借**来源那条 run 的执行者**的身份（`agentRef.instructions = sourceAgent.instructions`），
而且哪些技能注入随 runtime 而变（claude 落 `.claude/skills/`、codex 落 `.codex/skills/`、generic 未必有通道）。
后果：**起草质量是随机的**——换个执行者起草出来的 skill 结构就变了；同一件事从聊天发起与从任务发起也可能不同。

使用者定稿（2026-10-20 逐条确认）：把它做成**一个内置智能体**（可在「智能体」页查看与编辑）。

| # | 决定 |
|---|---|
| ① | **独立角色**（起草者）：**不出现在任何"选执行者 / 选审核者"的地方**（新建任务、智能体组成员槽），智能体页上看得见、能编辑 |
| ② | **不许删**，只能「恢复成默认值」——沉淀这条路必须永远有起草者，不留"删了之后怎么办"的静默分支 |
| ③ | **不注入技能**：写作规范正文（现在 `writing-skills` 那份）**放进起草 prompt** ⇒ 不再依赖 runtime 有没有技能通道；顺带消掉 `builtin_skill_missing` 那条 500 |
| ④ | **它像普通智能体一样有自己的 CLI 设定**（使用者可选） |
| ⑤ | 规范与身份**合成一份**交给使用者编辑 |
| ⑥ | 平台升级**只更新"默认值"那一侧**，使用者改过的那份**不动**（「恢复成默认值」随时能拿到最新默认） |
| ⑦ | **全局设定新增一项：runtime 默认值**（默认取**侦测到的第一个**可用的）；**各个 agent 的 runtime 默认值一律是 `default`**（跟随全局），需要时就地覆盖 |

### 9.1 谁保证什么（三层，不要混成一层）

```
身份 + 写法规范   ← 合成一份，使用者可编辑、可恢复默认（⑥ 升级不覆盖）
产出契约          ← 平台任务块 buildDraftPrompt，随代码走（③ 之后：规范也走 prompt，不走技能注入）
硬结构            ← 入库校验兜底（已有：缺 `## When to Use` / `## Procedure` 直接 400）
素材 / 草稿小屋   ← 平台写，不变（§5.0.7 的 material/ 与 outputDir）
评审判定          ← **仍然是人**：`reviewerAgentId: null` 不动，审阅界面仍是唯一大门
```

### 9.2 实作清单（顺序）

1. **store + 播种**：智能体加"内置"标记与新角色（起草者）；首启**幂等播种**（已有就不覆盖——使用者改过的那份必须活过升级）；被改名/损坏时能自愈到默认。
2. **默认指令常量**（随代码走）+ `GET/POST`「恢复成默认值」接口（只在"与默认不同"时可点/可调）。
3. **全局 runtime 默认值设定**（⑦）：设定项 + 侦测（取第一个可用的）+ 各 agent 的 `runtime` 允许 `'default'`；解析顺序 = agent 的值 ⇒ 全局默认 ⇒ 侦测第一个可用。
4. **起草 prompt 改造**：`writing-skills` 正文从"注入技能"改为"进 prompt"；起草 run 用这条内置智能体的 `instructions`；技能集合不再靠注入。
5. **智能体页**：内置徽标 + 指令可编辑 + 「恢复成默认值」+ **不给挂载技能/删除入口** + CLI 可设。
6. **过滤与判据**：所有"选执行者/审核者"的地方排除它。

### 9.3 必须避开的坑（都踩过一次同类）

- **给它的 CLI 不可用时不许静默回退**到别的 CLI —— 那正是"没人知道为什么写不好"的死法；要报一条可照做的错（"内置起草者选的 CLI 不可用，去智能体页改"）。
- **升级不许覆盖使用者改过的那份指令**（⑥）；只更新"默认值"，并把「恢复成默认值」点亮。
- **合成一份 ⇒ 使用者能把硬结构改坏**：接受它，因为服务端入库校验会当场报出来（不会静默产出坏 skill），且有一键恢复。界面上要有一句提示。
- **播种必须幂等**，否则每次启动都把使用者的改动冲掉（与 `ensureMineRepo` 同一纪律）。
- **角色要真的被过滤**：它只要出现在"选执行者"的下拉里，就会被拿去跑业务任务（指令是"你是 skill 作者"）——故障表现是"这个任务干得很怪"，查起来很远。

### 9.4 判据（做完要能量到）

它不出现在任何选执行者/审核者的地方；删不掉；改了之后能恢复、恢复后与默认**一字不差**；平台升级后使用者的改动**还在**；起草 run 的第一句话里是**它的**指令且含规范正文；**换 CLI 也必须读到规范**（③ 的目的）；CLI 不可用时报可照做的错；全局 runtime 默认为 `default` 时新 agent 跟随全局。

决策编号 **D81**（已写入 `docs/srs/requirements.md` §16；D80 是这条链的总设计）。

## 10. 起草之后的**审核步**（2026-10-20 定稿，**已实作**，决策编号 **D82**）

流程从「① 沉淀目标 → ② 起草 run → ③ 审阅入库」变成
「① 沉淀目标 → ② 起草 run → **②.5 内置审核** → ③ 审阅入库」。

### 10.1 四条决定（逐条确认过）

| # | 决定 |
|---|---|
| ① | **预筛，不替代人审**：审核结论与问题清单摆在审阅界面上，**入库仍然是人按的那一下**。所以这不是推翻「评审在人」（§5 的 `reviewerAgentId: null` 那条说的是"起草 run 不自动审"，现在多的是**另一条 run**），而是给那个人多一道证据。决策编号 **D82**（已写入 `docs/srs/requirements.md` §16） |
| ② | **不通过 ⇒ 自动返工重起草，限 N 轮**（N 待定，建议 2；每轮都要记账：轮次 / 结论 / 理由码）。N 用完仍不通过 ⇒ 停在"审核未通过"态，给人两个选择：看结论后自己重新起草、或**明知未通过仍入库**（人仍然是最后那个人） |
| ③ | **脚本真执行**（不只是静态查）：审核者可以在草稿小屋里真的把 skill 带的脚本跑一遍 |
| ④ | **新建第二个内置智能体**：`builtin`（不可删、可编辑、可恢复默认），与起草者同一套机制（§9 的 1–3 步全部复用）。⚠️ 角色**不是** `'reviewer'` 而是新增的 **`'skill-reviewer'`** —— 理由见下（实作时发现的，原稿写的是"角色 = 审核者"） |

**④ 的那个修正（实作第 1 步时发现，有代码证据）**：业务报告的路由判据是
`packages/domain/src/routing/kind.ts` 的 `a.role === 'reviewer' && hasReviewIdentity(a)`。
给内置审核者 `'reviewer'` 的话，它会**开始接收业务报告去审**（进了闭环），而它的指令是
"审 skill 的质量与脚本"——两个身份不能合并。独立角色 `'skill-reviewer'` 靠那条**等值**
判断天然落在业务路由之外（与 `'drafter'` 同一个道理）。

### 10.2 ⚠️ 第 ③ 条的安全立场（必须写在文档里，不能只活在代码里）

**"真执行 + 自动"这个组合是最需要知情的**，所以记清楚：

- 审核者跑的是**另一个 agent 刚写出来的代码**，而本仓库**明确不做沙箱隔离**（NG7 是范围决定，不是待办）⇒ 它在**目录级**被关在草稿小屋里（`skill-draft-<id>/`，与起草者同一个屋），但**没有任何进程/文件系统隔离**：它拿得到使用者的家目录、能起进程、能联网。
- 这一跑是**自动发生的**（第 ② 条：不通过要自动返工，所以审核本身不能靠人点）。**知情**因此不能靠"界面上有个按钮"。
- **✅ 已定（2026-10-20）**：使用者确认**审核者真执行草稿脚本**。所以这一条不再是开口，要实作。
- **总开关：按"给、默认开"做**（使用者没有反对我这条建议）。理由再说一遍：真执行是**在你机器上
  跑另一个 agent 刚写的代码**，没有沙箱兜着（NG7），出事时能一键关比"改代码再重启"实际得多。
  设置项名字建议 `allowReviewerScriptRun`（缺省 `true`），关掉时审核 prompt 里去掉"跑脚本"那一段，
  **而不是**让它照写不跑（那样审核者会以为自己跑过了，判决里出现没发生过的"已执行通过"）。

### 10.3 复用现成机制（成本低，别另起一套）

- **返工 = 现有的 `POST /api/crystallize/revise`**：它已经收 `feedback`、会把素材与上一版产出一起给回起草者。审核结论（理由码 + 具体问题 + 证据）直接作为 `feedback` 喂回去 ⇒ **不需要新的返工通道**。
- **审核 run 用 `kind: 'review'`**（执行/审核两次本来就同构，见 `docs/runtime/pipeline.md`）：`agentRef` = 内置审核者、`subject: { type: 'skill-draft-review', id: draftRunId }`、**不进闭环**（不进任务列表、不挂 issue）。
- **结论用现有 verdict 形状**（结论 / 理由码 / 严重度 / 证据）：审阅界面已经有渲染判决的那套东西，解析与展示都不用新写。
- **审核者也走 §9 的内置机制**：`builtin: true`、删不掉、角色/技能挂载改不了、`restore-default` 可恢复；启动对账那条 `ensureBuiltinDrafter` 推广成"确保内置的**那一对**"。

### 10.4 收口点（容易漏，漏了就是"绕过审核"）

1. **两个入口都要过审核**：首次起草**与**「按意见改一版」的产出 —— 只审前者的话，返工那一版就绕过了审核（而返工恰恰是"上一版有问题"时才走的）。
2. **返工轮次记账在 run 上**（第 ② 条），而不是靠内存计数：daemon 重启后仍要知道"这条草稿已经返工过几轮了"，否则重启就能无限返工。
3. **审核者不进业务闭环**（与起草者同一条纪律：不参与任何"选执行者/审核者"的选择）。
4. **审核失败**（CLI 挂了、超时）**不等于不通过**：前者要如实报"审核没跑成"并让人继续（人审仍在），不许静默当成通过 —— 那是这个设计最坏的失效方式。

- **不进任务列表**：与起草 run 同一条（`subject.type` 不是任务类；`reviewerAgentId: null`）。
- **收口**：`kind` 别写成报告类（那会被当成业务报告流），且审核者的 `reviewStandard` 是 null
  ——平台不会把业务产出交给它，这条已经由角色 `'skill-reviewer'` 保证（§10.1 ④ 的修正）。

### 10.7 第 3 步（自动返工）的勘察结论（2026-10-20）

读 `apps/daemon/src/review.ts` 得到的**判决落点**（比原方案准得多）：

- `ReviewCoordinator.handle(input)` 的入参是 `{ run, workspaceId, output, allowedActions,
  tools?, fixedParams?, invalidAttempts?, maxReworks?, usedReworks? }` ——
  也就是说**额度（`maxReworks` / `usedReworks`）本来就是它的参数**，D45 那套是现成的接缝。
- 解析在 domain 的 `decideReview({ output, ... })`：**判决是从 run 的产出文本里读的**，
  不是读某个文件 ⇒ 我们那条审核 run 要产出**它认识的形状**，否则会被判成不合规并
  **诚实降级**成 `conclusion='needs_human'` + `reasonCode='internal_error'`
  （`review.ts:35-39` 的注释：这样"这条判决不合规"在数据里看得见，而不是伪装成正常判决）。
- executor 在**每个 review run 收尾时**都会调它（`executor.ts:1730`）⇒ 我们那条 run
  **已经会自动拿到一条判决记录**，第 3 步要做的不是"造判决"，而是：
  1. **查 `decideReview` 期望的产出口径**，让我们给审核者的 prompt 产出它就是能认的形状
     （现在 prompt 里写的是 `review.json` —— 那是我没查就写的，很可能要改成"按判决格式回复"）；
  2. 拿到判决后**按结论分流**：`fail` ⇒ 用现成的返工额度起一条 revise（feedback = 结论 + 问题），
     额度用完或 `needs_human` ⇒ 停在"审核未通过"态交给人。
  3. ⚠️ 动作那一路**不需要也不该开**：我们这条链的 `allowedActions` 是空的（executor 的注释：
     "报告审核那条路上它是空的 ⇒ 判决只能给结论"），所以判决不会触发任何动作——这正是要的。

**一句话**：第 3 步的活落在**两处**——审核 prompt 的产出口径（对齐 `decideReview`）+ 判决后的分流
（复用额度与 revise），而不是我原来设计的 `review.json` 与自造计数器。

### 10.8 第 3 步的格式口径（勘察结果，已照它改 prompt）

判决的产出**不是**我原先写的 `review.json`，而是平台的**判决围栏块**：

- 标记：`packages/protocol/src/verdict.ts:273-274` 的 `VERDICT_FENCE_BEGIN` / `VERDICT_FENCE_END`
  （`<<<ALPHA_VERDICT>>>` / `<<<END_ALPHA_VERDICT>>>`），提取由同文件的 `extractVerdictJson` 做，
  校验由 `parseVerdict` 做，整条判定链在 `packages/domain/src/review/pipeline.ts` 的 `decideReview`。
- **产出写坏不会静默通过**：`decideReview` 会给 `invalid`（结构性缺失 ⇒ 有重试意义；非结构性 ⇒
  按 `invalidAttempts` 决定重试或降级），最终落库时是 `needs_human` + `internal_error`
  （`review.ts:35-39` 的注释解释了为什么这样"诚实降级"）。
- 已按此改掉审核 prompt：**不再重抄格式**（围栏标记唯一出处是 protocol 常量，重抄一份两边迟早分叉，
  而分叉的表现是"判决块解析不了"），改成"按第一句话里给的格式写" + 给出 `reasonCode` / `evidence`
  的填写要求。

**还差的一件（第 3 步的实质）**：判决之后的**分流**——`fail` ⇒ 用现成的返工额度
（`ReviewCoordinator.handle` 的 `maxReworks` / `usedReworks`，D45）起一条 revise（feedback = 结论 + 问题），
额度用完或 `needs_human` ⇒ 停在"审核未通过"态交给人。executor 里**没有**"等一条 run 收尾"的 API
（查过：`executor.ts` 没有 wait/settle 之类的方法），所以分流要么挂在收口那一刻（`review.ts` /
`executor.ts:1730` 那条路），要么由 server 侧有界轮询草稿与审核两条 run 的终态——**下一轮先定这一条**，
不要直接写。

### 10.9 第 3 步后半的施工方案（**已选 A**：挂在收口那一刻，窄口子）

使用者 2026-10-20 选了 A（不选 server 侧轮询）。照 A 的实作顺序，**先做前置重构再做挂点**：

1. **前置重构（无行为变化）**：`POST /api/crystallize/revise`（`server.ts:4762` 起）那段路由体
   现在**内联在路由里**（150+ 行的早返回 + `sendJson`），收口挂点没法复用它。所以要把它抽成
   `startReviseRun(input): Promise<{ok:true, runId} | {ok:false, status, code, error}>`，
   路由只做"调它 → 按结果 `sendJson`"。**判据：`crystallize-e2e` 那 28 条一个都不许变**（纯重构，
   行为一字不改）——这也是这一步唯一需要证明的事。
2. **挂点（窄口子）**：`ReviewHandlingDeps` 加一个**可选**回调
   `onSkillDraftReviewed?: (input: { run: Run; draftRunId: string; verdict: VerdictRecord }) => Promise<void>`，
   在 `review.ts` 里**只对 `run.subject.type === 'skill-draft-review'`** 调它（业务审核那条路
   一个字不动）。server 在装配 `ReviewCoordinator` 的地方（`server.ts:1985`）提供实现。
3. **分流实现**（回调里）：读判决 ⇒ `fail` 且额度未尽 ⇒ `startReviseRun({ draftRunId, feedback: 结论 + 问题清单 })`；
   额度用尽或 `needs_human` ⇒ 什么都不做（停在"审核未通过"态，交给人）。
   ⚠️ **额度用现成的**（D45：`ReviewCoordinator.handle` 的 `maxReworks` / `usedReworks`，
   住在被审的那条 run 的 `chainDepth` 上），**不要自己造计数器**。
   ⚠️ **不许静默当成通过**：审核没跑成（CLI 挂 / 超时 / 判决不合规）⇒ 只记状态，不返工、不入库。
4. **判据**（下一轮写）：假装后端产出 `fail` 判决 ⇒ 真的起了一条 revise run 且 feedback 里带结论；
   额度用尽 ⇒ **不再**起；`pass` ⇒ 不起；业务审核 run（subject 是报告/任务）⇒ 回调**不被调用**
   （这条是"窄口子"的判据，最要紧——宽了就会动业务那条路）。

⚠️ 我这一轮**没有开始写**：第 1 步那个重构要动 150+ 行早返回的路由体，第 2 步要动业务闭环的核心文件
（`review.ts`）。在余量不足时硬上，最可能的结果是留下一个半重构的路由 —— 那比"没开始"坏得多。

### 10.10 第 4 步（脚本真执行）要勘察的三件事

⚠️ 这一条**不能凭想象写**（我自己已经在这条链上连续两次被"没查的地基"打回）。动手前先查：

1. **审核那一路怎么拿到 Bash 权限**：执行与审核两侧的工具权限不是同一套（`executor.ts:432`
   `req.kind === 'review' && req.review`、以及 1121/1138/1252 那几处 review 分支）——
   要查清"审核 run 现在允许哪些工具"，以及真执行需要加什么（argv 标志？注入工具？`pre-tool-use.py` 那条钩子？）。
   查不到确切位置就不要写。
2. **脚本在哪跑、以什么身份跑**：草稿小屋（`draftRoot`）里、与审核者同一个进程 —— 也就是
   `CLAUDE.md` 说的"不做沙箱隔离 NG7"的现场。要在文档与界面上**如实说明**（不是免责声明，
   是让使用者知道这一跑会发生什么）。
3. **失败与超时的形态**：脚本挂住（等待输入 / 死循环）时审核 run 怎么办——`limits` 是
   `{maxTurns: null, timeoutMs: null}`（起草那一路就是 null），真执行之后**要给一个有界超时**，
   否则一条挂住的脚本会把审核 run 永远吊在那儿。

判据（写的时候一起写）：审核 prompt 在开关开时含"跑脚本"那一段、关时不含；开关关掉之后
**判决里不许出现"已执行通过"**（那是我们关掉的功能，判成通过就是假证据）。

### 10.11 第 4 步勘察结果（2026-10-20，三件事查到了两件半）

1. **审核那一路怎么拿到 Bash 权限** —— `allowedActions` **不是**答案：它是**平台动作**的白名单
   （判决触发什么动作），与"CLI 能不能跑脚本"无关。真正的闸门在两层：
   - **适配器 argv / 沙箱**：`packages/agent-claude/src/claude-backend.ts` 里 `buildArgv` 那一段
     （受管参数最后写、`--disallowedTools` 的用法、`planSandbox` 在沙箱不可用时**抛异常且刻意不 catch**）。
     同一文件有一条直接相关的现场记录："Claude Code 建不了 `~/.claude/session-env/` 时，
     **Bash 工具全程 EPERM**" —— 也就是说"能不能跑脚本"取决于 CLI 自己的状态目录与沙箱规划，
     不是我们这边一个开关。
   - **跑前钩子**：`apps/daemon/src/run-hooks/claude-config.ts` 明确写着"任务隔离 hook（D76）
     **只拦 Bash/Read 等路径工具**" ⇒ **Bash 是被 D76 那个钩子拦着的**。所以第 4 步的落点大概率是
     "在那条钩子里为审核 run 放行 Bash，并把可执行范围限定在草稿小屋"，**不是**在执行侧放开权限。
2. **脚本在哪跑、以什么身份跑** —— 草稿小屋（`draftRoot`）+ 审核者同一进程；沙箱取决于
   `options.sandboxMode`（缺省 `none`，即 NG7 的"不做沙箱隔离"）。要在文档与界面上如实说。
3. **失败与超时** —— 仍未查清 `limits.timeoutMs` 在审核那一路怎么落地（起草那一路是 `null` = 无限）。
   这一条**必须先查再写**：挂住的脚本会把审核 run 永远吊在那儿，而"审核永远在跑"在界面上
   与"审核还没开始"长得一样。

**结论**：第 4 步不是"加个提示词"那么轻 —— 它要动的是 **D76 的运行期钩子与 claude 的 argv/沙箱规划**，
属于安全边界那条线上的改动。所以它应当在**第 3 步收口之后**单独做，并且做完要有一条
"脚本真被执行过"的**实测证据**（不是"我们放开了权限"这句话）。

### 10.12 第 3 步后半（自动返工）实作记录（2026-10-20）

**挂点比原方案更省**：`ReviewCoordinator` 的 deps 里**本来就有**

⚠️ **踩到的第一个坑（否则这段就是死代码）**：`executor.ts` 的 `#reworkBudgetFor` 对

用"版本数"而不是新加一个计数器：重装、重启、人工多改一版，这个数都对得上。

⚠️ **踩到的第二个坑（测试 fixture）**：判决必须**完全合规**才算"不通过"。我第一版随手写了

⚠️ **踩到的第三个坑（判据选错）**：第一版用"起草 run 的**条数**"当判据，卡在"等不到第 27 条"

①判决状态 `rework_requested`（只在这条路上出现，派不出去是 `escalated`）；
②文件系统里**新的一间草稿小屋**里有 `material/feedback.md`，且内容是审核者写的理由码/条目/位置。

测试 +3（2005 通过）：fail ⇒ 派得出去且意见落进新一版素材、pass ⇒ 一版不多、判决不合规 ⇒

### 10.14 第 ③ 条（脚本真执行）实作记录（2026-10-20）

**权限本来就有**（勘察结论，不是假设）：
- claude 一律跑在 `--permission-mode bypassPermissions`（`packages/agent-core/src/runtime-table.ts`
  的 `baseArgs`，还有 `--disallowedTools AskUserQuestion`）⇒ Bash 对**每一次 run**都是通的；
- D76 的运行期钩子（`apps/daemon/src/run-hooks/pre-tool-use.py`）只拦**越界**（`..` / `~` /
  工作目录外的绝对路径），小屋内部相对路径的 `bash skill/scripts/x.sh` 是**放行**的。
  ⇒ 所以这一条**不需要改权限**，缺的只是"让它去跑"这句指令。

实作：
- 审核 prompt 里加一段【把 `skill/scripts/` 里的脚本真的跑一遍】，含三条约束：只用相对路径、
  **只在这个工作目录里活动**、**"跑不起来就说跑不起来，不要猜它能跑"**（后两条是这个功能的
  价值所在：脚本能不能执行，看是看不出来的）。
- **总开关** `Workspace.allowReviewerScriptRun`（缺省开）+ `PUT /api/workspace/reviewer-script-run`
  + identity 暴露 + 设置抽屉里的一项。⚠️ 关掉时 prompt 那一段**换成"不要执行脚本"并要求如实写
  "脚本未被执行"**，而不是删掉那一段 —— 权限还在，删掉的话它可能照跑；而如果它没跑却写下
  "已执行通过"，那份判决就是**假证据**。
- **上限**：**不单独设**。⚠️ 我第一版在这里写了 `timeoutMs: 10 分钟`，理由写的是"没有上限才是
  问题"——**那是没查就写的**：`limits.timeoutMs` 是**空闲**上限，而平台**本来就有**
  `DEFAULT_IDLE_TIMEOUT_MS` = 30 分钟（`executor.ts`，没有输出就判 `idle_timeout` 收掉，并在 run
  日志里写明"用的是平台默认"）。我那个 10 分钟比默认**更紧**，会误杀"合法但安静"的脚本
  （比如一次长时间构建）。所以撤掉，用平台默认，并把这句话写进代码注释。

测试 +4（2010 通过）：开关开的 prompt 含"真的跑一遍"+越界约束；开关关的 prompt **不含**那一句
且含"不要执行脚本/如实写未被执行"；**直接量 D76 钩子**（小屋里的 `bash skill/scripts/check.sh`
⇒ `allow`，`bash ../../etc/passwd` ⇒ `deny`）；审核 run 的日志里说出**真正生效的空闲上限**（30 分钟）。

⚠️ 两处踩坑（都写进注释了）：① 用 `promisify(execFile)` 喂 stdin —— `execFile` **没有** `input`
选项，钩子等 stdin 等到测试整个挂住（60 秒无输出）；改 `execFileSync` + `timeout`。
② 判据读"判决一出现"⇒ 读到收口**中间态** `validated`，断言 `rework_requested` 成了竞态：
单跑绿、全量跑红（我第一次就是这么写的）。改成**等收口之后的状态**（`status !== 'validated'`），
窗口也放宽。

**仍未完成**：真机上的端到端证据（一次真实 CLI 的审核 run 把草稿里的脚本跑出痕迹）。

### 10.15 真机端到端证据的施工单（第 ③ 条最后一件，下一轮照这个做）

### 10.17 界面重做：使用者 2026-10-21 的三条（实作 + 实测数字）

**这一轮探针抓出来的两个真缺陷（都修了）**：

1. **徽标一直停在「排队中」**：状态原来是"打开面板那一刻的接口快照"，点「开始审核」时 run 还是

   没结束"的一半来源。修法：`RunLog` 加 `onstatus`，把事件流里的状态变化转告调用方（**不装轮询**）。
2. **取消之后界面纹丝不动**（我在修①时改出来的）：徽标改成"优先用实时状态"之后，run 落终态时

**探针这边的三个坑（写下来防复发）**：

1. **插一条 `running` 的夹具 run 量到的是假的绿**：夹具注入在 daemon 停机那一段，而 daemon 起来时
   `reconcileInterruptedRuns`（FR-RUNTIME-11）会把非终态 run 收口成 `failed` ⇒ 那一屏其实是
   "没跑成"那一屏，而两条判据（有日志、日志有内容）**碰巧**成立。假绿比红更危险，整条删掉重做。
2. **真现场靠假 CLI**：把假 `agent-cli` 垫在 daemon 的 PATH 最前面（daemon 只在启动时读一次
   PATH），再点界面上真的「开始审核」——真 spawn、真 `running`、真日志、真取消，一个额度不花
   （NFR-T-01）。它靠"内置审核者身份里塞的记号"只服务审核那条 run，别的 run 一律 `exit 127`
   （那几条夹具本来就靠"`agent-cli` 不存在 ⇒ 立刻失败"避免真跑 CLI）。
3. **★★ SSE 开着的时候 Chrome 的虚拟时钟完全不走**：探针是 `--virtual-time-budget` + `--dump-dom`
   收结果的，页面上只要有一个没结束的 fetch（SSE 就是），**连 `setInterval` 的 tick 都是 0**，
   虚拟时间预算永不到期 ⇒ **dump 永远写不出来、整个探针挂到超时**。症状（探针超时、dump 空文件）
   离原因（一条开着的 SSE）隔了三层，花了两轮才定位。修法：那一屏的等待一律走 `untilNet()`
   ——拿一次**真网络往返**当节拍器（时钟冻结时网络照样完成），既有上界又不会挂死；等完还必须让流
   关掉（取消 ⇒ run 终态；再兜一层切路由卸载组件）。

  · `crystal.stoppedStartButtonDisabled = false`（停下来之后按钮是可按的，不是灰着让人发呆）

`pnpm run probe:layout` **528 项全绿**（第 5 批 523 + 5）。结论：那一支**不是死代码**，
而且它是使用者真会走的路（起草跑歪了 → 停下 → 回头看看素材）——所以判据留在这儿守着，
而不是把那支标记删掉。

### 10.23 真机上量出来的缺陷：`#/crystallize/<草稿id>` 里那个 id 被丢掉了（2026-10-21，分批第 7 批）

这一批不是设计改动，是**真机验证时撞出来的缺陷**——顺手修掉，因为它让使用者已经付过钱的审核结论
在界面上打不开。

**怎么发现的**：真机跑审核那条链时我在浏览器里连着打开几条草稿，发现**不同草稿的结论条一模一样**
（都是 `✗ 不通过 · logic_error · 6 个文件 · 对比上一版 +80 −25`）。一开始我还按错了标签，
以为是界面显示了错数据；量清楚之后是两个事实叠在一起：

  · 视图这边没错：它挂的是"**该来源最新那条**草稿"（`targets.activeDraft`），显示的判决与那条一致；
  · 错的是**深链语义**：`#/crystallize/<草稿id>` 里那个 id 进到后端就被 `resolveSourceRun` 解析成
    来源，然后一律取最新那条 ⇒ **URL 说哪条不算数**。

**用户可见的后果**（真机上量的数字）：同一个对话来源下有 **4 条**草稿，「沉淀」列表里是 **4 行**，
点开全是同一条（最新那条）；其余几条的判决与问题清单打不开——其中一条是 `✓ 通过 · meets_criteria`
的审核，**那一次审核花了 131 万输入 token（约 $1.32）**，结论在界面上根本看不到。

**修法**：进来的 run 本身就是草稿 ⇒ **就挂它**（`crystallizeTargets` 里的 `requested`），
来源入口的老口径不变。三条口径写清楚：

  · **已入库的草稿**：深链照样指它自己——"回看这条已入库的"要看到的就是它（含那次入库的 git 历史）；
  · **已丢弃的草稿**：**不复活**（丢弃是列表里一个明确的动作，旧 URL 不该把它拉回界面上）⇒ 回落到最新那条；
  · 形状只有一份：新抽的 `draftInfo()` 同时供"最新那条"与"指名那条"用，不许抄两份。

**验证（三层）**

  1. 单元测试 `crystallize.test.ts`「★ 深链指名的那条草稿优先」四个断言：来源入口取最近 /
     深链取指定的那条（哪怕它更旧）/ 已入库的深链仍指自己 / 已丢弃的回落到最新。
     ⚠️ 这一条第一版红在**我自己的测试写法**上：③④ 两步我传的是本地那个 run 对象，它身上没有
     刚写进 store 的 `crystallized`/`discarded` 标记 ⇒ 量到过期现场（真链路上 run 一律来自 store）。
     改成从 store 重读之后一次通过。
  2. 探针（`pnpm run probe:layout` **531 项全绿** = 第 6 批 528 + 3）：新增一对**同来源的兄妹草稿**
     （那条比本体旧、只有 1 个文件）⇒ 深链打它挂上的就是它（`["新增 SKILL.md +19 −0"]`、
     结论条 `○ 还没审核过 · 1 个文件`），而**从来源进来仍是最近那条**（3 个文件）。
     两条配对很要紧：只判前者的话，把"来源入口也变成深链"这种改坏会当成通过。
  3. **真机**（复制一份使用者的 store 起临时 daemon，`--work-root` 指到真实的
     `~/agentdeck-workspace`，只读不改）：深链 `01M5FD5VDP…` 现在显示 `✓ 通过 · 5 个文件 ·
     对比上一版 +429 −28`（就是那条 $1.32 的审核），另一条显示自己的 `✗ 不通过 · +136 −26`；
     列表 5 行**各开各的**（第 5 行还量到一个新形态：`已按上面的意见自动重新起草（第 4 版）`）。
     ⚠️ 临时 daemon 是这次真机验证的关键手法：**不动使用者正在跑的那个 daemon**，
     又能拿真实数据量（直接起第二个 daemon 指着同一个 store 是禁止的——单写者锁）。

**给使用者的提醒**：这个修复要**重启 daemon** 才生效（后端是 `.ts` 直接跑，重启才载入新代码）。

### 10.24 人改草稿要算数：写回落盘 + 结论过期 + 重新审核（2026-10-21，分批第 8 批）

使用者原话：「缺少一个可以改的地方」。查下来**编辑器一直都在**（草稿 tab 的文件树，每个文本文件
都能改），缺的是**改完算不算数**：

  · 改动只活在浏览器内存里（`onEditInput` 只写 `artifacts.files`），而**审核者读的是磁盘上的
    `skill/`** ⇒ 改了等于没改，审核看的还是老内容；
  · 「确认入库」交的却是**编辑器里的**内容 ⇒ 入库的东西与结论条上的判决可能不是一个东西，
    而界面上**一个字都不提**；
  · 有判决之后结论条上**没有「重新审核」**（那个按钮原来只在 `review === null` 时出现）
    ⇒ 同一版审完就再也审不了，连"我改完了，请再审一遍"都做不到。

**这一批补的三件事**

1. **写回**：`POST /api/crystallize/save-draft`（`{draftRunId, files}`）把编辑器的内容写回
   `<草稿小屋>/skill/`。三条纪律：
   · **只写、不删**——"删文件"该是一个明确的动作，不是"保存"的副作用。这条与入库那条路的教训
     同源（"清空目录再写"会把文本兜底草稿看不见的支持文件删掉），在保存这条路上更贵：
     人只改了 `SKILL.md`，却可能顺手删掉点文件/二进制/`readTree` 之外的东西。有单测钉着。
   · **路径三层守卫**（`isSafeDraftRelPath` + 拼出来的路径按分隔符比前缀 + `realpath` 比父目录）：
     封 `..`、绝对路径、反斜杠、空段，也封"`skill/` 下放一个指向 `/etc` 的软链"。
     教训与 `workdir-files.ts` 同源——按字符串前缀比会把 `/work-other` 当成 `/work` 的子路径。
   · **有任何一个路径不安全 ⇒ 整单拒**（一个文件都不写）：半写会让磁盘进入使用者没要求过的
     中间状态，而审核紧接着看到的就是它。
2. **结论过期**：审核路由在**起审核 run 的那一刻**把"这次审的是哪一版内容"的指纹钉下来
   （`<草稿小屋>/.audited.json`，`{reviewRunId, hash, at}`）；review 接口拿它与"此刻磁盘内容"比，
   给出 `stale: true/false/**null**`。`null` = 判不出来（旧数据没指纹）——**不编成 `false`**，
   那会让"判不出来"看起来像"没过期"，界面就会安静地把一份可能对不上的结论当成有效结论。
   指纹用**长度前缀**拼（不是分隔符）：`rel + '\n' + text` 这种拼法会让两组不同文件撞同一个串
   （内容里带换行的文件最先撞上），表现正是"改了内容却判为没过期"。有单测钉着。
3. **界面**：结论条出现「内容已改 —— 这个结论是改之前的，要它算数得重新审一轮。」+
   「保存改动」（**只在有未保存改动时出现**；没有改动时挂一个点不动的按钮比没有按钮更困惑）+
   「重新审核」（有判决就能再审；`dirty` 时禁用并说明"先保存：现在重审的是磁盘上那一版"）。
   ⚠️ 保存后**不自动重审**：真机一轮审核 ≈ $1.32，这笔钱由人决定。

**"人改不占额度"是怎么成立的**：自动返工的额度按"同一来源上起草过几版 − 1"算，而**人改不起
新 run** ⇒ 天然不吃额度（e2e 里钉着：保存前后 `versions` 不变）。这也是选"写回同一版"而不是
"人改也算一版"的原因之一。

**验证**

1. 单测（`crystallize-artifacts.test.ts` +5）：路径守卫的正反例、整单拒、**只写不删**（连点文件
   都不许动）、指纹的顺序无关/变化敏感/不许撞车、指纹与审核时间戳的读写（坏文件 ⇒ `null`）。
2. e2e（`crystallize-e2e.test.ts` §10.6，真 daemon + 假后端 + 真 git）：**人改 → 落盘 → 结论过期
   → 重审**四步都在磁盘与接口上真发生（还断了"只写不删"与"版本数不变"）；守卫四例（逃逸整单拒
   且小屋外不许出现文件、非起草 run 400、缺 id 400、**没跑完 409**）。
   ⚠️ 那个 409 需要"卡在跑完之前"的起草 run：假后端加了 `draftGate`。第一版我打算"POST 起草之后
   抢在完成前再 POST 保存"——那是把一条纪律押在调度顺序上，机器一忙就红。
**⚠️ 指纹判据的第一版错了，错在一个"判决不合规 ⇒ 自动重试"的事实上**（全量跑才红，单跑绿）：
第一版写的是 `stamp.reviewRunId === reviewRun.id`（"指纹与审核 run 一一对应"），而
**一次「开始审核」可能留下两条审核 run**——判决不合规时 daemon 会 `createRetryRun` 重试一次
（同 subject、同内容、相隔几毫秒），接口报的是**最后**那条 ⇒ 指纹那条永远不是"报出来的那条"
⇒ `stale` 变成"判不出来"。也就是说：**恰恰在审核出问题（重试）的时候，"人改过没有"反而看不见了**，
而那正是人最需要知道"结论还算不算数"的时刻。现在的口径是"拿最近一次「开始审核」钉下的指纹比"，
`stamp.reviewRunId` 只作记录。e2e 里**显式**钉住这条：先等"报出来的审核 run 换了一条"
（证明重试真的发生），再断言 `stale` 仍是一个判得出来的布尔值——只断言"不过期"会漏掉它。

**还有一个假后端的错**（也是全量跑才露出来）：假后端原来"只要工作目录是草稿小屋就往 `skill/`
写夹具文件"，而**审核 run 用的就是同一间小屋**（设计如此）⇒ 审核者一跑就把人手改的内容盖回去，
红的却是"磁盘上真的换了内容"。改成**只有起草 run 写文件**（真链路上审核者只读）。

3. 探针（`pnpm run probe:layout` **538 项全绿** = 第 7 批 531 + 7）：没改过时没有保存按钮、
   也没有过期标记；在编辑器里打字（真 `input` 事件）⇒ 出现「保存改动」；点它 ⇒ 出现过期标记与
   「重新审核」、保存按钮自己收起来；**重读 `/api/crystallize/artifacts` 能看到那句手写的改动**
   （证明真的写到了磁盘，而不是只改了内存）。夹具那侧要补一件事：夹具是直写 store 的，
   所以**没有审核路由写的指纹**——补指纹时**引 daemon 的实现**算 hash，不许在探针里抄一份算法。
