## 1. 背景与目标

使用者在 AgentDeck 的聊天（conversation run）里和 agent 协作，经常完成**可复用**的事——
修了一个流程、跑通了一段部署、整理出一套检查步骤。这些"做法"当前只活在对话历史里，
下次要再用就得重讲一遍，或者翻聊天记录。

**目标**：把"这段聊天做了什么、怎么做的"提炼成标准的 `SKILL.md`，进**提炼专用根
`~/.agentdeck/skills-mine/`**（与安装根 `~/.agentdeck/skills/` **物理分离**，理由见 §1.1），
以后挂到 agent 上复用；用多了发现不够 → 在旧版基础上**进化**（覆盖 + git 版本管理）。

### 1.1 为什么提炼的与安装的必须分根（2026-10-18 使用者提出）

使用者："**不应该把安装的 skill 和我自己提炼的 skill 混在一起（混在 `~/.agentdeck/skills/`）**"。
两者语义完全不同，混在一个根里有真实的损害：

| | 安装的（外部） | 提炼的（自己的） |
|---|---|---|
| 来源 | 远端服务 / GitHub / 本地清单 / localdir | 自己的聊天沉淀 |
| 更新语义 | **重新安装覆盖**是正常行为 | 自己的进化被"重装"覆盖 = **资产丢失** |
| 版本管理 | 外部内容，重新装就行 | 自己的资产，要 git 历史 / 回退 / 备份 |
| 信任 | 别人写的（可能有许可证 / 更新） | 自己的做法（可能含工作上下文） |

**落地方案（两个根）**：

```
~/.agentdeck/skills/          ← 安装的（现状不变：install API 落这）
                                   不 git 化，重装覆盖语义不变
~/.agentdeck/skills-mine/     ← 提炼的（新根，git 化 + 平台自动 commit）
                                   平台永不自动覆盖——进化 = 起草→确认→覆盖+commit
```

- **store 索引**：`Skill.source` 标记 `mine`，界面按「安装 / 我提炼的」分组。
- **注入**：零改动——注入走 store 的 `skill.body`（`syncInjectedSkills(workDir, skillDir, skills)`
  的 payload 来自 store 记录，不从磁盘根读）。
- **slug 冲突**（同 slug 两个根都有）：**提炼的优先**——运行期用提炼的 body，自己的版本
  遮蔽安装的；列表里被遮蔽的安装项标注「被你的版本遮蔽」。
- **git 化范围**：只 `skills-mine` 一个根——平台自动 commit 的语义正好是"你沉淀的东西"，
  安装的外部内容平台不碰（要备份安装的，使用者自己 git 整个 `~/.agentdeck` 即可）。

**为什么值得做（调研共识）**：skilldistill 说得最直接——"Agents repeatedly discover useful
procedures, but most of that knowledge stays trapped in the conversation"（知识困在对话里）。
业界对"从对话提炼 skill"的共识是：**审阅是必要环节**（不自动入库），且 SKILL.md 遵循统一结构
（Anthropic 官方博客的「渐进式披露」：frontmatter 的 `name`/`description` 只够判断"何时用"，
正文是第二层细节，认为相关才全文读入）。

## 3. 流水线总览

```
两个场景，同一套流水线：
  聊天（conversation）——Chat 标题栏「沉淀成 skill」按钮（§4.1）
  任务（task / review）——任务详情页「优化 skill」按钮（§4.3，素材带用户/审核反馈）

①触发（用户主动按钮）→ ②沉淀目标面板（新建 / 更新本次加载的 skill；新建必填作用描述）
→ ③提炼（skill 起草 run：素材 + 作用描述 + 模板 + 不结晶清单 + 现有 skill 列表）
→ ④审阅（界面预览/编辑 → 用户确认，平台不自动入库）
→ ⑤入库（~/.agentdeck/skills-mine/<slug>/，source:'mine'）
→ ⑥进化（起草修订版 → 确认 → 覆盖 + git 自动 commit，可回退）
```

## 4. 触发（调研后定稿；信号建议暂缓，见 §4.2）

### 4.1 用户主动（主触发）——会话级按钮（整体提炼，不做细节选择）

**2026-10-18 简化**：初版设计过"轮次级按钮 + 选起点轮 + 范围摘要"的精细交互，
使用者试想场景后定了更简单的形态："**就整体聊天结果来提炼，不用去选择对话细节**"。
理由：选起点/调范围是精细控制，但实际使用成本高、收益低——**素材给整体，筛选交给
起草 run 自己**（§5 的不结晶清单 + 提炼本身就是筛选：从整段对话里挑出可复用的步骤）。

**按钮形态与位置**
- **会话（conversation）级按钮**「沉淀成 skill」，放在 Chat 视图的会话标题栏
  （与「停止」等会话级操作同层级）。
- 会话里**至少有一轮已结束**即可用（素材 = 已落库的部分）。
- 不放在消息行/气泡上——沉淀的单位是整个聊天，不是某一轮。

**点击后：先选沉淀目标（新建 or 更新本次对话加载的 skill），再起草**
1. 点按钮 → 弹出「**沉淀目标**」选择面板：
   - 「**新建 skill**」——起草全新技能（素材 = 整段会话）。选中后出现「**作用描述**」
     输入框（2026-10-18 使用者补——**担心 agent 自己总结会偏离**）：
     - **必填**，placeholder 引导："这个 skill 是做什么的？什么时候用？一句话或几行
       都行"（触发条件导向，如"用来审核 xx 类报告的步骤"）。
     - **双重用途**：① 进起草 run 的 prompt，锚定提炼方向（防抓错重点/步骤幻觉）；
       ② **直接作为草稿 frontmatter `description` 的基底**——"这个 skill 干什么用"
       这一层是用户自己的话、不可能偏（渐进式披露第一层，§4.4），agent 只负责补正文
       （When to Use / Procedure / Pitfalls / Verification），审阅时可微调措辞。
   - 「**更新本次对话加载的 skill**」（2026-10-18 两次修正定稿）——列表列出**当前对话
     实际注入的 skill**（不是全库）：
     - **为什么只列被加载的**：对话的前提往往是"**某个 skill 不好用，这次对话就是在矫正
       它**"——更新目标天然是**正在用的那几个**；让用户从全库挑既慢又不符合心智模型。
       当前对话没挂 skill（注入为空）时此选项**置灰**，提示"本次对话没有加载 skill，
       只能新建"。
     - **提炼的**（`skills-mine`，标注"你的"）——选中 = 进化（§7）：素材 = 整段会话 +
       该 skill 现有 SKILL.md，起草"修订版"，确认后覆盖 + git commit。**作用描述可选**
       （有旧 SKILL.md 作基线 + 对话本身在矫正它，偏离风险小；填了同样进 prompt + 作为
       description 修订基底）。
     - **安装的**（`~/.agentdeck/skills/`，标注"安装的"）——选中 = 基于它创建你的版本：
       素材 = 整段会话 + 安装版 SKILL.md，确认后存为 `skills-mine/<slug>/`
       （`source: 'mine'`）并**遮蔽安装版**（§1.1），安装根原文件不动。
   - 选择面板同时显示会话素材摘要（N 轮 / M 次工具调用），用户确认目标后进入起草。
2. 起「skill 起草 run」（kind `skill-draft`，§5；更新/基于安装 = 素材里带现有 SKILL.md）。
   **素材硬要求**：无论新建还是更新，素材都含**整个会话的 run events**（全部 turn：
   消息 + 工具调用 + 输入输出），且**必须保留工具调用及其结果**——提炼"怎么做"依赖
   真实的命令/脚本，只给对话文本会写出幻觉步骤。
3. 界面进入"**起草中**"状态：**复用 RunLog 显示起草 run 的实时日志**（现成能力），
   可「停止」（现成按钮），失败可看日志。
4. 起草完成 → 进入**草稿审阅**（§6，交互同前）：
   - **预览**：SKILL.md 渲染预览（现成 markdown 渲染器 `apps/web/src/lib/markdown.ts`）。
   - **编辑**：`name`（kebab-case）、`description`（校验必须含触发条件）、正文
     （When to Use / Procedure / Pitfalls / Verification）都可改。
   - **支持文件**：草稿带脚本/模板（`scripts/`、`templates/`）时，文件列表 + 逐个预览。
   - **撞 slug 校验**（只对"新建"有意义——"更新"已在第 1 步明确目标）：提炼根已有同 slug
     → 提示"已有你提炼的同名 skill（vN）"，选「**覆盖（进化）**」走 §7 或「**改名**」；
     安装根已有同 slug → 提示"已有安装的同名 skill，你的版本将**遮蔽**它"（§1.1），确认即入
     或改名。
   - 「**确认入库**」→ 写 `~/.agentdeck/skills-mine/<slug>/` + store `source: 'mine'`
     + git commit → 完成提示"已沉淀 skill <name>，可在技能库查看/挂到 agent"。
   - 「**取消**」→ 丢弃草稿，回到聊天，聊天内容不受影响。

**边界情况**
- **当前对话没加载任何 skill** → 沉淀目标面板的「更新本次对话加载的 skill」**置灰**，
  提示"本次对话没有加载 skill，只能新建"。
- 会话很长（轮数多）→ 提示"素材较大（N 轮），起草 run 上下文有限，可能截断"——**不阻断**；
  起草 run 会从素材里挑核心步骤，截断的影响有限。
- 起草 run 失败 → 提示失败原因 + 「查看日志」「重试」（素材原样重发，不重复打包）。
- 对话还在进行（run 未终态）→ 素材只取已落库的部分，提示说明。

#### 4.1.1 界面改版（2026-10-19 使用者定稿）：任务详情式全页，替换抽屉

> ⚠️ **本节取代上面 4.1 的"弹出沉淀目标选择面板（抽屉）"的呈现方式**——目标选择、
> 素材摘要、起草日志、草稿审阅这些**内容与流程语义不变**（§4.1 / §5 / §6 仍是权威），
> 变的只是**载体与组织**：从"设置式抽屉"改成"任务详情式全页"。

**动机（使用者反馈）**：抽屉是"填表单 → 提交 → 看结果"的**设定感**；沉淀的本质是
"发起一条 run → 看它跑 → 审阅收口"，应该是任务详情页那种**执行感**——固定栏头
（返回/标题/状态/操作）+ 正文分节堆叠 + run 徽标实时状态 + RunLog 常驻。

**载体：右主区切换成沉淀流程页（MainArea 壳），不再弹抽屉**
- 点「沉淀 skill / 优化 skill」→ 右主区换成沉淀流程页；栏头 = 返回键 + 标题「沉淀 skill」
  + 副题（**来源上下文**：哪个对话/任务、源 run id、轮数/工具调用数）+ 随流程变的操作。
- 返回键回到来源视图（对话消息流 / 任务详情），栏头副题始终标着"来自哪个 run"兜底上下文。
- 权衡（使用者已确认接受）：全页意味着点按钮**暂时离开**来源视图，返回键 + 副题补回上下文；
  抽屉"不离开现场"的便利让位给执行感。

**页面结构：步骤条 + 分节渐进展开（不是 phase 互相替换）**

```
┌──────────────────────────────────────────────────────────┐
│ ‹ 返回      沉淀 skill                    [开始起草]         │ ← 栏头（固定，操作随流程变）
│   来源：对话「…」· run 01M5… · 3 轮 · 25 次工具调用          │
├──────────────────────────────────────────────────────────┤
│    ① 沉淀目标       ② 起草 run        ③ 审阅入库            │ ← 流程步骤条（当前步高亮）
├──────────────────────────────────────────────────────────┤
│ ▸ 素材摘要（折叠，起草前就可见）                            │
│    打包自本次对话/任务：3 轮 · 25 次工具调用 · 有审核判决      │
│    · 无用户反馈                                            │
├──────────────────────────────────────────────────────────┤
│ ▸ 沉淀目标（当前步，可编辑）                               │
│    (•) 新建 skill —— 作用描述 [……必填……]                  │
│    ( ) 更新本次加载的 —— [技能单选列表（你的/安装的徽标）]     │
│    [开始起草]                                             │
├──────────────────────────────────────────────────────────┤
│ ▸ 起草 run 01M5…（徽标:起草中，实时）        [停止]          │ ← 起草后才出现
│    ┌──────────────────────────────────────────┐           │
│    │ RunLog 实时日志（SSE）                     │           │
│    └──────────────────────────────────────────┘           │
├──────────────────────────────────────────────────────────┤
│ ▸ 草稿审阅（起草完成后解锁，徽标:已完成）                   │
│    slug / name / description / 正文编辑 + 预览折叠          │
│    [确认入库]  [放弃]                                     │
├──────────────────────────────────────────────────────────┤
│ 完成态：已沉淀 skill <name>（skills-mine · git 已提交）      │
│    [查看技能]  [返回]                                      │
└──────────────────────────────────────────────────────────┘
```

**与旧抽屉形态的核心差别**

| | 旧（抽屉） | 新（任务详情式全页） |
|---|---|---|
| 载体 | 右侧滑入抽屉，覆盖在页面上 | **全页 MainArea**，与任务详情同壳 |
| 流程呈现 | 三个 phase 在抽屉内互相替换 | **步骤条 + 分节渐进展开**，全程一览 |
| 起草日志 | phase 跳走就看不见 | RunLog **常驻**在审阅下方 |
| run 状态 | 只有一行小字 | 步骤②带实时徽标（起草中/已完成/失败） |
| 失败 | 弹回目标面板 + 一行错误 | 步骤②失败态：徽标红 + failureReason + [重新起草] |
| 完成 | toast 一下 + 关抽屉 | **完成态**：已沉淀 + git 状态 + [查看技能] |
| 素材 | 起草后才有数字 | **起草前**就显示素材摘要 |

**任务感从哪来（四条硬规则）**
1. **栏头操作随流程变**：目标态 → [开始起草]；起草中 → [停止]；审阅态 → [确认入库]；
   完成态 → [查看技能]。与任务详情栏头的「优化 skill」按钮同一位置、同一交互习惯。
2. **步骤条 = 任务的 stage 感觉**：①→②→③ 编号 + 连线；当前步 accent 高亮、已过步 ok 色、
   失败步 bad 色。起草 run 的 `status` 直接驱动步骤②徽标（复用 `RUN_STATUS_CLASS`）。
3. **渐进展开而不是跳转**：开始起草后目标分节收成只读摘要；起草完成审阅分节解锁并滚到审阅；
   **日志永远可见**——与任务详情"看完 verdict 还能翻 run 日志"同一道理。
4. **冲突/遮蔽交互不变**：新建撞提炼根 slug → 审阅分节顶部 notice + [改成更新它（进化）]；
   更新安装的 → 同 slug 落你的版本并遮蔽（§1.1）。

**后端小改动（界面改版实作，2026-10-19）**
- `GET /api/crystallize/targets` 增加 `materialStats: { turns, toolCalls } | null`：
  buildMaterial 是现成读操作，空素材返回 `null`，前端在目标态就禁用 [开始起草] 并提示
  （**早失败**，而不是起草完才发现 400 empty_material）。
- `POST /api/crystallize/draft`：起草 run 带 `crystallizeTarget`（新建 / 更新哪条）随 run
  落库——恢复进行中的起草进审阅/入库时按它还原目标（commit 需要目标：更新 = 复用原 id
  进化；不能凭用户这次又选啥猜）。`purpose` 不落库（只影响起草 prompt）。
- `POST /api/crystallize/commit`：入库成功后把起草 run 标 `crystallized: true`——targets 的
  `activeDraft` 据此跳过已入库的草稿（否则每次重开都会把沉淀完的草稿再"继续"一遍）。

**归属：沉淀不是任务（2026-10-19 使用者定）**
- 起草 run 仍是 **run**（`kind: execute`、`subject: {type: 'skill-draft'}`），**不挂 issue**、
  **不进任务列表**——它是从对话/任务发起的"工具动作"，不是"工作项"；也不进任务的审核
  闭环（`reviewerAgentId: null`、无返工）。任务列表里不会出现沉淀条目。
- 进度/历史只能从来源（对话 / 任务）再进流程页看——这是该方案的既定代价（使用者已接受）。

**恢复进行中的起草（补"关页面丢进度"缺口，2026-10-19 使用者定 A 方案附带）**
- 现状缺口：起草 run 在后台真实地跑，但关闭流程页后 UI 不知道它的 id，重开会另起一条
  → 重复起草。
- 修法：
  1. 起草 run 上**记 source**（`subject.sourceRunId` = 源 run id）——现在 subject 里没有
     这条链接，加上是恢复的前提。
  2. `GET /api/crystallize/targets` 顺带返回 `activeDraft: { runId, status, target } | null` =
     该源 run 最近的、**未入库**的 skill-draft run（起草中 / 已完成待审阅都算；
     `target` = 起草时落库的沉淀目标，恢复时按它还原）。
  3. 流程页打开时：有 `activeDraft` → 顶部提示"有进行中的起草（起草中/待审阅）"，
     「继续」挂回那条（RunLog 接着看、审阅接续），或「新起草」（放弃旧的）；
     没有 → 正常从目标态开始。

**状态**：设计已定（2026-10-19），**已实作**（§8.1 的 9，2026-10-19）——含上面提到的
随 run 落库沉淀目标与对话按全部轮次匹配两处实作补充。

#### 4.1.2 三轮：沉淀成为独立一页（导航列「工具」之下）

> ⚠️ **本节取代 4.1.1 里"流程页住在聊天/任务右栏"的载体**——流程的**内容与语义**
> （目标 / 起草 / 审阅 / 入库、步骤条 + 分节、素材摘要、恢复进行中）全部不变，
> 变的只是它**在哪儿**：从一个视图的右栏，变成一个自己的页面。

**动机（使用者原话）**："在导航列，工具下，增加一下流程页（TAB），沉淀的过程在此页
进行，它有类似任务页一样的列表，可用于切换沉淀任务。"（二轮之后使用者仍觉得切走回不来、
且沉淀混在聊天/任务里不像一件独立的活。）

**页面形态：与任务页同构的一页**
- 侧栏第 7 项「沉淀」，排在「工具」之下；顶栏页名同一个词条（`crystallize.navTitle`）。
- **左栏 = 沉淀任务列表**（`GET /api/crystallize/drafts`）：未入库的起草 run，
  每行 = 来源（对话/任务 + 标题）· 状态徽标 · 目标（新建 / 更新 <skill>）· 时间。
  使用者定稿：**已入库的不显示**（列表永远干净），失败的仍然显示（还要重试）。
  列表每 6 秒轻刷新一次（起草中的 run 完成/失败时徽标跟着动）。
- **右栏 = 流程页**（复用 §4.1.1 的 MainArea 壳与分节），未选中时是空态 +
  「新建沉淀」提示。
- **切换沉淀任务** = 点列表行（同一页换 runId，不跳走）。

**地址**：`#/crystallize`（列表空态）/ `#/crystallize/<runId>`（选中某条）。
二轮的 `#/chat/crystallize/<runId>`、`#/tasks/crystallize/<runId>` **保留并重定向**
到 `#/<crystallize>/<runId>`（书签与分享链接不作废，`syncRoute` 用 `location.replace`
只换当前这一格，不污染后退栈）。

**入口（三条，都落到这一页）**
1. 聊天页「沉淀成 skill」→ `#/crystallize/<源 runId>`；
2. 任务页「优化 skill」→ `#/crystallize/<任务执行 runId>`；
3. 本页「新建沉淀」→ 来源选择器（`GET /api/crystallize/sources`）→ 选中即进目标步骤。

**来源选择器（本页新建）**
- **对话**：有轮次带 runId 且最后一轮没报错（与聊天页按钮同一判据），带轮数预览。
- **任务**：有**终态**执行 run 且**审核过**（§4.3；`hasUserFeedback` 当前恒 false）——
  未达门槛的任务**不列出**（列出来是一条点了进不去的死路）。
- 一次算齐源 runId（不依赖 `GET /api/runs` 的 100 条上限，也不让前端 N 次拉取）。

**门槛三处拦（§4.3）**
1. 来源选择器只列达标任务（服务端筛）；
2. 流程页 `canStart` 拦（`scope==='task'` 且 `reviewed || hasUserFeedback` 才可开始，
   置灰时 title 说明原因）；
3. `POST /api/crystallize/draft` 返回 400 `task_gate`（界面画对了而忘了带时的兜底）。
   e2e 夹具因此要**先有一条 completed 审核 run** 再过门——测试的是机制，不是门槛本身。

**草稿 run 归一（`resolveSourceRun`）**
左栏列的是**起草 run**，点一条进来的地址里带的就是草稿 id。起草 run 自己的事件
是产出的 SKILL.md——拿它当素材就成了"用草稿沉淀草稿"。所以 `crystallizeTargets` 与
起草路由入口都先归一：`subject.type === 'skill-draft'` → 换回 `subject.sourceRunId`
指向的源 run；源 run 已被清理时原样返回（走"素材为空"的正常分支）。归一之后
`activeDraft` 正好找回这条草稿 → 流程页直接进「继续」。

**归属不变**：沉淀仍然**不是任务**（起草 run 不挂 issue、不进任务列表）；这一页的列表
是沉淀自己的列表，与任务列表互不影响。

**控件纪律（2026-10-19 使用者指出"UI 风格和任务差很多"之后的返工）**

#### 4.1.3 未来扩展：沉淀 Agent（同流程页，产出类型维度，2026-10-19 使用者提出）

> 使用者："类似沉淀 skill 一样，通过对话或者任务来更新 Agent 的 prompt。"
> ——**反向沉淀**：把对话/任务里的经验结晶回**智能体指令**（`Agent.instructions`），
> 与沉淀 skill（SKILL.md）并列的第二种产出类型。**未来需求，未实作**，这里只记
> 流程页的复用口子，保证将来加它不改页面骨架。

**复用结论**：流程页骨架（① 定目标 → ② 起草 run → ③ 审阅入库）与"产出类型"解耦，
沉淀 Agent = 同一流程页 + 产出类型 = agent prompt。三处差异、其余照用：

| | 沉淀 Skill | 沉淀 Agent（未来） |
|---|---|---|
| ① 目标 | 新建 / 更新**本次加载的 skill** | 新建 / 更新**本次对话/任务实际涉及的 agent**（执行者、审核者） |
| ② 起草 run | 产出 SKILL.md 草稿（subject `skill-draft`） | 产出指令草稿（subject `agent-draft` 变体）；素材不变（events + 反馈 + 判决） |
| ③ 审阅入库 | frontmatter + 正文 → `skills-mine` + git | 指令文本 → 更新 `Agent.instructions`（无 frontmatter） |

**共享**：步骤条、素材摘要、RunLog 常驻、失败/完成态、恢复进行中的起草
（`activeDraft` 按 sourceRunId 泛化，不区分产出类型）。

**复用口子（设计上现在就成立，成本极低）**
1. subject 类型已是独立枚举——`skill-draft` 旁加 `agent-draft` 变体；起草 run 机制
   （executor 复用、reviewerAgentId:null、不挂 issue）一字不动。
2. draft 接口支持显式 `agentId`（缺省 = 源 agent）——agent 沉淀的起草者/目标者都明确，
   接口天然兼容。
3. 审阅分节按产出类型渲染——skill 版是 slug/name/description/正文；agent 版是纯指令文本。

**将来单独定的点**：agent prompt 的版本管理——skill 有 `skills-mine` git 根，agent 指令
没有对应 git 根；将来更新 agent prompt 要么在 agent 记录留历史/审计，要么也 git 化。
不影响流程页复用。

### 4.2 信号建议（辅触发）——⏸️ 暂缓，首版不做（2026-10-18 使用者定）

使用者："**4.2 信号建议（辅触发）先不做，这部分还没考虑清楚**"。设计方向（借
dsh-skill-evolution 的信号模型）记录在案，等考虑清楚再捡起：

| 信号 | 条件 | 含义 |
|---|---|---|
| `complex` | 成功 turn 且 ≥5 次工具调用 | 完成了一件复杂事 |
| `recovered` | 有失败步骤但 turn 仍成功 | 绕过了死路、找到了可行路径 |
| `repeated` | 相同工具序列重复 ≥N 次且成功率高 | 反复验证过的流程 |

思路：命中时 agent 在回复里**只问一句**"这段值得沉淀成 skill 吗？"——**不自动做**。
（AgentDeck 的 NG 原则是"平台不替使用者决定"；自动结晶会把使用者没有主动要的东西写进
他的技能库，噪音大于收益。信号只用来**降低使用者发现"这段可沉淀"的成本**。）

**为什么暂缓**（没考虑清楚的点，捡起时先回答这些）：
- 信号定义本身：`complex` 单独命中太弱（任何长 turn 都符合），要不要佐证门槛
  （dsh-skill-evolution 要求 complex 被 recovered/repeated 佐证）？
- 噪音控制：run 结束时多一句"要沉淀吗？"——频繁出现就是打扰，什么频率可接受？
- 触发时机与渠道：信号在 run 结束（而不是聊天中）检测，与用户主动按钮怎么衔接？

首版**只有用户主动**两条触发（§4.1 聊天 + §4.3 任务），信号建议不做。相关开放问题见 §9。

### 4.3 任务场景：优化当前 skill（用户 / 审核反馈）——2026-10-18 使用者新增

使用者："**任务可能也合适这样的提炼（通过用户的反馈或者审核的反馈，可以优化当前的 skill）**"。
任务才是 skill 的"生产环境"：挂载的 skill 在实际任务里被验证，**用户纠正 / 审核打回 =
最真实的进化信号**（skill 哪一步错了、缺什么、边界在哪）——比聊天更接近"越用越准"。

**入口**：任务详情页（Tasks detail，RunLog 所在页）——任务 run 终态后，标题栏
「**优化 skill**」按钮（与 Chat 标题栏的「沉淀成 skill」并列，同一套面板与流程）。

**触发前置（2026-10-18 使用者补充：必须检查，否则按钮置灰）**：
- 按钮**可用** ⟺ 任务 run 终态 **且**（**有用户反馈** 或 **审核过**）。
  - "有用户反馈" = 任务已存在用户评价/反馈记录（不是即将填的——那是点进去后补充的）。
  - "审核过" = 存在审核 run 的判决。
- **否则按钮置灰**，提示"该任务没有反馈、也未审核，无法据此优化 skill"
  （提示路径：先给任务加反馈，或让它走完审核——AgentDeck 任务本就有执行→审核链路）。
- 为什么**必须**有反馈或审核：任务沉淀的价值就是**反馈驱动进化**——没有进化信号的任务，
  光凭执行过程沉淀没有"矫正"意义（执行记录不是进化素材）；置灰把这条语义钉死。

**素材**（与聊天版的差异——多了反馈）：
- 任务 run 的 events（执行全流程：消息 + 工具调用 + 输入输出）。
- **审核反馈**（有则自动带）：审核 run 的**判决**（结论 / 理由码 / 严重度 / 证据 / 动作）——
  起草 run 从中看出"skill 的哪一步导致审核不过"。
- **用户反馈**（有则自动带已有的；点进去后可再补充一段："哪里不对 / 该怎么改"）。
- 素材硬要求同 §4.1：保留工具调用及其结果。

**沉淀目标**：与聊天版**共用**沉淀目标面板（§4.1 第 1 步）——新建 / 更新本次任务加载的
skill（更新目标 = 任务 run 实际注入的 skill；反馈指向的 skill 通常就是它）。

**作用描述**：新建必填（同聊天版）；更新**可选**——用户反馈 / 审核反馈本身就是方向锚定，
比聊天版更不需要额外描述。

## 5. 提炼——「skill 起草 run」

平台起一个**专门的 run（kind 建议 `skill-draft`）**，runtime 用当前 workspace 默认的
claude/codex，复用现有执行管道（第一句话投递、日志、审核收口——全部现成，零新机制）。

prompt = 拼装：
1. **沉淀素材**（§4.1 打包的消息 + 工具调用 + 结果）。
2. **用户作用描述**（§4.1 第 1 步，新建必填 / 更新可选）——锚定提炼方向；草稿的
   frontmatter `description` 以它为基底（用户的话，防偏离）。
3. **SKILL.md 模板指引**（§4.4 的结构约束）。
4. **现有 skill 列表**（name + description）——让起草者判断是否该 `FOLD_INTO`（合并进已有
   skill）而不是新建重复项。

产出 = SKILL.md 草稿（文本，落成一个临时候选文件，不进任何工作目录）。

### 5.1 不结晶清单（质量门）

以下情况**不许沉淀**（来自 dsh-skill-evolution 的硬性门，防垃圾技能冻结成长期错误行为）：

- 环境依赖失败（缺二进制、未配凭证、没装的包）——换个环境就废
- 对工具的负面评价（"工具 X 坏了"——会冻结成长期拒绝用某工具）
- 瞬时错误靠重试治好的（教训是"重试"这个模式，不是原始错误本身）
- 一次性任务叙事、没解决的失败

### 5.2 SKILL.md 草稿结构

```
---
name: <kebab-case 技能名>
description: <一句话，必须含触发条件——"当用户想……时用"——这是渐进式披露的第一层>
---

# <Title>

## When to Use   ← 触发条件展开
## Procedure     ← 可操作步骤（步骤里引用的命令/脚本要原样可复制）
## Pitfalls      ← 注意事项与边界（含"别在什么情况下用"）
## Verification  ← 怎么验证这步做对了
```

支持多文件（脚本/模板放同目录，如 `scripts/`、`templates/`），与现库 skill 结构一致
（如 `browser-use/` 是 `SKILL.md + LICENSE.txt + templates/`）。

## 6. 审阅 → 入库（提炼根 `~/.agentdeck/skills-mine/`）

- 界面预览草稿（SKILL.md 渲染，Markdown 渲染器是现成的 `apps/web/src/lib/markdown.ts`），
  可编辑，**用户确认后才入库**——完整交互见 §4.1 第 4 步起（会话级按钮 → 起草 → 审阅）。
- 校验：frontmatter 合法（name/description 存在、description 含触发条件）、slug 唯一
  （撞车提示"已有同名 skill，是否进化它？"——从这里自然衔接进化流程）。
- 入库**不走** `POST /api/skills/install`（那是"装外部来源"的路，落安装根）——提炼走新的
  「沉淀入库」写入，落 `~/.agentdeck/skills-mine/<slug>/`，store 记录 `source: 'mine'`，
  写完 `git add` + `commit`（§7.3）。**平台永不自动覆盖安装根**。

## 7. 进化（覆盖 + git 版本管理）

### 7.1 触发

- **主入口（2026-10-18 定为显式选择）**：沉淀面板第 1 步选「更新本次对话加载的 skill」→
  选中其中提炼根的目标 → 进化（§4.1 第 1 步）。这是进化现在**唯一的前置入口**——
  "想更新哪个"在起草之前就定，而不是起草完撞 slug 才转弯；且目标限定为**本次对话实际
  注入的 skill**（对话=矫正它的不足）。
- 次级入口：新建时撞 slug 校验提示"已有同名 skill（vN），是否进化它？"（§4.1 第 4 步）——
  从这里也可以切到"更新本次对话加载的"。
- skill 挂载的 run 中 agent 发现问题（"这个 skill 缺了 X/过时了"）→ 建议使用者进化
  （语音提示，行动仍走沉淀面板）。

### 7.2 起草与覆盖

素材 = **现有 SKILL.md 全文 + 新经验** → 起草修订版 → 用户确认 → **覆盖旧文件**。

### 7.3 git 版本管理（使用者定的语义：覆盖 + git 类似版本管理）

- `~/.agentdeck/skills-mine/` **做成 git 仓库**：首次开做时 `git init`（实测安装根
  `~/.agentdeck/skills/` 当前不是 git 仓库；全局 git 身份已配置，平台自动 commit
  有身份可用）。**只 git 化提炼根**——安装根是外部内容，
  平台不自动 commit（§1.1）。
- 每次入库/进化后平台**自动 `git add` + `commit`**，commit message 带版本说明，如
  `skill <slug> v2：新增 X 边界`。
- 收益：`git log`/`git diff`/`git checkout` 回退/远程同步（推到私有仓库备份、换机器拉取）全免费，
  不用平台自己造版本表。

#### 7.3.1 git 可用性保护（2026-10-18 使用者要求：依赖的是**用户环境的 git**，不捆绑平台）

版本管理依赖系统 `git`——**用户环境可能没有 git，这是正常状态，不是错误**。
设计分两层（对比：早期兜底只有"失败不失败 run"，把 git 缺失当**异常**报——每次沉淀都
尝试 `git init`+`commit`、撞失败、产出一条"commit 失败"note，看着像出错；使用者要求
把它升级为**功能开关**：没有 git 就不需要版本管理）：

| 层 | 触发 | 行为 |
|---|---|---|
| **可用性开关** | 探测：daemon 启动时 + 每次沉淀/进化前 `git --version`（spawn 探测，超时/非零/找不到 → 不可用） | **git 不可用 → 版本管理关闭**：跳过 init 与 commit，沉淀/进化**照常写盘 + store 索引**（功能完全不受影响，只少历史回退）；note 一条说明"版本管理未启用（系统无 git），沉淀照常、无历史回退"——**不是错误** |
| **降级兜底** | git 可用但操作失败（`git init`/`add`/`commit` 非零、`.git` 损坏、权限不足） | note 降级，run 照常（保留早期兜底的语义——这层针对"有 git 但坏了"） |

- **自动恢复**：git 可用性每次沉淀前都探测 → 用户中途装了 git，下次沉淀自动恢复版本管理
  （幂等 `git init` + 首次 commit 把已有沉淀收进历史）。
- **半途状态**：git 不可用期间沉淀的进化没有历史——装 git 后**不补造历史**（没有基线，
  造出来是假的），从恢复那一刻起记录；note 里说明这一点。
- 另在 skills-mine 仓库配 **per-repo 兜底身份**（`agentdeck <agentdeck@localhost>`），
  防"有 git 但没全局身份"时 commit 挂掉（这是降级兜底层的一部分）。

## 8. 实现范围（要开做时的六项）

1. **会话级 / 任务级按钮 + 沉淀目标面板**（共用）——Chat 标题栏「沉淀成 skill」+ 任务详情页
   「优化 skill」（有用户/审核反馈时高亮提示）+ 「新建 / 更新**本次对话/任务加载的** skill」
   选择（列出实际注入的 skill，提炼的在前、安装的在后；未加载 → 置灰；新建必填作用描述，
   §4.1 第 1 步 / §4.3）。
2. **素材打包**（daemon 端）——取整个会话/任务 run 的 events（消息 + 工具调用），组
   「沉淀素材」；任务场景**附用户反馈（可选填）+ 审核判决（有则带）**（§4.3）；
   更新/基于安装 = 素材里附上现有 SKILL.md。
3. **起草 run**（新 run kind `skill-draft`）——prompt 组装（素材 + 作用描述 + 模板 +
   不结晶清单），产出候选文件。
4. **草稿审阅界面**——预览/编辑/确认入库/新建撞车时切进化。
5. **提炼根 `skills-mine` + git 化 + 自动 commit**——新根落盘（`source: 'mine'`，store 索引）、
   **git 可用性开关**（启动时 + 每次沉淀前探测 `git --version`；不可用 → 版本管理关闭、
   沉淀照常 + note，可用 → 幂等 init + 自动 commit；操作失败 → note 降级，见 §7.3.1）。
6. **列表分组 + 冲突遮蔽**——技能库按「安装 / 我提炼的」分组；同 slug 冲突时提炼的优先
   （注入用提炼的 body），被遮蔽的安装项标注。

最小闭环 = 1–6（触发→选目标→提炼→审阅→入库→git→列表/遮蔽，全部做完才是完整闭环）；
**信号建议（§4.2）不在首版**——使用者定"还没考虑清楚，先不做"；自动 FOLD_INTO 提示
**被"沉淀目标面板手动选更新"取代**（§4.1 第 1 步，2026-10-18）——人工选目标比自动建议
更可控，可二期。

### 8.1 界面改版（2026-10-19 使用者定稿，已实作）

- **7. 界面改版：任务详情式全页替换抽屉**（§4.1.1）——点按钮后右主区切换成沉淀流程页
  （MainArea 壳：返回 + 标题 + 来源副题 + 随流程变的栏头操作），不再是抽屉；

  并回普通右栏地址；带着地址回来时按源 run 的 subject（对话/任务）把来源选中，返回即
  回到那条对话/任务详情。

  空素材在目标态就禁用 [开始起草]，早失败）。draft / commit 接口不动。

  `canStart` 与 `POST /api/crystallize/draft` 三处拦。

## 9. 开放问题（本次未定）

  使用者在真实任务里用几次自会知道好不好用。

## 10. 与现有机制的关系（零冲突）

| 现有机制 | 本设计的接法 |
|---|---|
| run 执行管道（executor、第一句话、审核收口） | 起草 run 完全复用（kind 加一个 `skill-draft`） |
| `/api/runs/:id/events` | 素材打包的数据源 |
| `POST /api/skills/install` + `~/.agentdeck/skills/` | **不动**——那是"装外部来源"的路；提炼走新根 `~/.agentdeck/skills-mine/` + 新写入入口（§1.1、§6） |
| store 的 `Skill.source` | 加 `'mine'` 值；注入零改动（走 `skill.body`），冲突时提炼优先（§1.1） |
| Markdown 渲染器 `apps/web/src/lib/markdown.ts` | 草稿预览复用 |
| NG 原则（不替使用者决定） | 用户主动为唯一触发（信号建议暂缓）；审阅后才入库 |
