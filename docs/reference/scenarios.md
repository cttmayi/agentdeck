## 1. 系统里有什么

```
┌──────────── 使用者机器 ────────────┐
│                                    │
│  ★ 打开 http://127.0.0.1:<固定端口> │
│  ┌──────────────────────────────┐  │
│  │  Web UI（由 daemon 托管）      │  │
│  │   ① 本地接口（同源）→ daemon   │  │
│  │   ② 远端接口（跨源）→ 远端     │  │
│  └───────┬──────────────┬───────┘  │
│          │              │          │
│          ▼              │          │
│     ┌─────────┐         │          │
│     │ daemon  │         │          │
│     │ ★全部工作数据      │          │
│     │ ★执行            │          │
│     │ ★不发起远端请求   │          │
│     └────┬────┘         │          │
│          │ 子进程        │          │
│          ▼              │          │
│      claude             │          │
│          ▼              │          │
│   使用者指定的工作目录    │          │
└─────────────────────────┼──────────┘
                          │ HTTPS（token）
                          ▼
┌──────────────────────────────────────┐
│  远端（五项职责）                      │
│   ├ 账号与登录                        │
│   ├ 保存用户设定                      │
│   ├ 公共 SKILL / TOOL 目录             │  ← 读它自己的本地文件
│   ├ 第三方查询                        │  ← 被问时去查，不暂存
│   └ 记录与统计                        │
│  ★ 不执行、不持权威数据、不托管 UI      │
│  （可选：一个落地页）                  │
└──────────────────────────────────────┘
```

**四句话概括**：

1. **daemon 是全部**——工作数据、执行、UI 都在使用者机器上。
2. **daemon 不发起对远端的请求**——取**待处理项**（`GET /api/pending`；D19 之后远端已经没有 run 队列）、下载 skill、查第三方、上报记录，全部由本地页面代为发起。
3. **页面是唯一通路，且是唯一发起方**。
4. **远端是"账号 + 设定 + 目录 + 查询 + 记录"**——它不干活，也不持有权威数据。

## 2. 三种使用形态

| 形态 | 用法 | 关键约束 |
|---|---|---|
| **单机** | 笔记本上装 daemon，开浏览器用 | 合上笔记本就停止派发 |
| **多机** | 家里台式 + 公司笔记本各装 daemon | 两台机器的数据**各自独立**；只有"记录"在远端能合起来看 |
| **常开机器** | 一台常开机器上跑 daemon + **常驻页面会话** | 页面不常驻就只能跑完手上的活，接不到新的 |

> **常开机器必须有一个页面一直开着**。这是本架构的直接代价，已写进部署文档要求。

## 3. 端到端走查

### 3.1 第一次使用

| # | 谁 | 做什么 |
|---|---|---|
| 1 | 使用者 | `pnpm install` → `pnpm run build:web` → `pnpm run daemon`（⚠️ **npm 分发还没做**：所有包都是 `private: true`，FR-RUNTIME-05 / NFR-P-03 标注未达成） |
| 2 | 使用者 | `agentdeck daemon start` |
| 3 | daemon | 探测本机 CLI，生成设备标识，在**固定端口**上开始服务，并**自动打开浏览器** |
| 4 | 页面 | 从 daemon 加载（**同源**），无需任何跨源协商 |
| 5 | 页面 | 提示登录 → 使用者登录远端账号 |
| 6 | 页面 | 显示：设备名、探测到的 CLI 及版本 |
| 7 | 使用者 | 建 agent（或选预置模板）、建 issue、指派 |
| 8 | 页面 | 把 run 交给本地 daemon |
| 9 | daemon | 建工作目录 → 注入技能 → 组装第一句话（① 框架 / ② 身份 / ③ 任务）→ 起 `claude` |
| 10 | daemon → 页面 | SSE 流式推消息 |
| 11 | daemon | 完成，产出报告 |
| 12 | daemon | 上报记录与统计到远端（**可关闭**） |

**要点**：

| 要点 | 说明 |
|---|---|
| **没有授权 / 配对步骤** | 页面本来就从这个端口加载，不存在"连到别的服务"的问题 |
| **daemon 未启动时** | 浏览器直接显示无法连接（能打开页面就说明 daemon 在跑） |
| **离线可用** | UI 与数据都在本机，断网时完整可用（仅远端相关功能不可用） |
| **端口固定** | 被占用时明确失败并提示可配置的覆盖值，**不静默换端口** |

### 3.2 场景 S3 —— 纯执行（只产出报告）

**产出是报告，不触发 Action。** **不存在"改代码"这条线。**

1. 使用者建 issue
2. 指派给 agent
3. 页面把 run 交给 daemon；daemon 起 `claude` 执行
4. 产出一份**报告**（artifact）
5. 人看报告，决定后续

**没有自动审核，也没有 Action**——两者都只属于审核（S1 / S2）。

> **Action 只能由审核产生的 verdict 触发**（D21）。执行 run 的产出不得直接触发动作——否则"执行即动作"这条口子一开，动作边界就失控了。

### 3.2b 多 agent 分工（本项目核心用法）

同一实例可以配置**任意多个 agent**，它们各有分工：

| 维度 | 例子 |
|---|---|
| **处理不同的 issue** | 代码类 issue → 代码 agent；文档类 → 文档 agent |
| **执行不同的审核** | 代码 issue 由代码 agent 处理、由**安全 agent** 审核 |
| **不同的 skill 子集** | 执行者挂参考用的资料包（如"仓库约定""语言规范"）；审核标准**不是** skill（见下） |
| **不同的动作范围** | 动作**不再挂到 agent 上**：装好工具包之后，在**审核者的「行动权限」**里勾它声明的动作（`Agent.allowedActions`），判决通过时由平台触发（挂载能力 2026-09 已撤） |
| **不同的模型与工作目录** | 互相独立 |

关键点：

- **skill 按 agent 求解**——同一个 workspace 下，不同 agent 注入的技能目录内容**不同**（执行者挂什么就注入什么）
- **判断依据随审核 agent 而变**——verdict 的结构全局统一，但判断依据**写在审核者身上**（2026-09 起并进它的「指令」，② 身份；老数据里那份 `Agent.reviewStandard` 仍会合成进去），不再属于 skill；skill 只是执行者参考的资料包
- **动作权限也是审核者的能力**——「判完允许动什么」在 `Agent.allowedActions`（D40 收口），动作名只能是**已安装工具包**声明的 `<包 slug>.<动作名>`（D41 起平台不内置任何动作）；skill 一个字都不参与授权
- **agent 之间相互隔离**——一个 agent 的 skill / tool / 环境变量不得泄漏到另一个 agent 的 run

### 3.3 场景 S2 —— 纯审核流水线

**产物来自远端；由页面主动去问；远端按需查询第三方，不暂存。**

```
第三方                    远端                    页面                daemon
  │                        │                       │                   │
  │◀─ ① 按远端支持的查询协议完成配置（一次性）──────│                   │
  │                        │  （远端保存该配置）    │                   │
  │                        │◀─ ② 页面定期问 ───────│                   │
  │                        │  「我这台机器有东西吗」│                   │
  │◀─ ③ 远端按需查询 ───────│                       │                   │
  │── ④ 返回当前数据 ─────▶│                       │                   │
  │                        │── ⑤ 返回给页面 ──────▶│                   │
  │                        │                       │── ⑥ 转交 daemon ─▶│
  │                        │                       │                   │ 建 report
  │                        │                       │                   │ 起 review run
  │                        │                       │◀─ 判决与结果 ─────│
```

**三个关键性质**：

| 性质 | 说明 |
|---|---|
| **方向是拉取** | 页面主动问，远端**不推送** ⇒ 远端不需要知道"哪个浏览器在线" |
| **远端不暂存** | 被问时才去查第三方 ⇒ **不存在过期策略问题** |
| **水位归适配器** | 平台不管增量 —— 平台靠 `report` **去重键**保证正确性（即使适配器返回重复数据也不会重复审核） |

**完整走查**：

1. 第三方按**远端支持的查询协议**完成一次性配置
2. 页面定期向远端询问本机是否有待处理项
3. 远端按需查询第三方，取回当前数据
4. 页面转交本机 daemon
5. daemon 建 `report`（不可变快照）
6. 起 review run：交给 `role: 'reviewer'` 的 agent——判断依据来自它的**「指令」**（② 身份；老数据里那份内联标准 `reviewStandard` 会一起合成进去，D37/D38），skill 不再承载标准
7. 产出结构化判决
8. 判决触发**有界动作**
9. 结果留在本地；记录副本经页面回报远端（可选）

**浏览器没开着时**：不积压也不丢——数据留在第三方，下次页面来问时取回，重复部分被去重键挡掉。

### 3.4 场景 S1 —— 执行 + 审核闭环

1. 指派 issue 给 `Coder` → 执行 run
2. 执行完成，产出报告
3. 系统创建 review run，交给 `Reviewer`（**必须是不同的 agent**）
4. `Reviewer` 按它身上的判断依据（「指令」；老数据那份 `reviewStandard` 也合成进来）审核 → 产出结构化判决（`pass` / `fail` / `needs_human` + 原因码）
5. 判决带 `action`（且在该审核者或本次任务的「行动权限」内、包已安装）→ 平台执行；动作失败 → 卡在人手里等待处理（⚠️ D41 起没有"通过类/修正类"内置动作——动作只来自装进来的工具包）
6. 判决超出标准 → **升级给人**，带结构化原因码

### 3.5 公共 SKILL / TOOL 的获取与使用

**下载由页面中转**——daemon 不访问网络。

```
        页面                      远端                    daemon
         │                        │                       │
         │── 1. 浏览 / 检索 ─────▶│                       │
         │◀─ 目录列表 ────────────│                       │
         │── 2. 下载选定内容 ─────▶│                       │
         │◀─ 内容 ────────────────│                       │
         │── 3. 交给 daemon ─────────────────────────────▶│  落盘
         │◀─ 4. 确认 ────────────────────────────────────│
```

1. 使用者在 Skills 页（或工具页）点「安装」→ 打开安装抽屉，切到**远端目录**页签——公共目录如今**没有独立页面**，入口就是这两个安装抽屉里的「远端目录」页签
2. 浏览远端从**它自己的本地文件**里列出的内容（⚠️ D38 起目录里**不再有 skill**：`/api/catalog` 的 `skills` 恒为空，审核标准不再借 skill 发布；⚠️ D40 起列的是**工具包**——一个包 = 一组动作，装一次整组可用）
3. 点安装 → **页面从远端下载**（内容随列表一起给，没有第二次取内容的机会）
4. 页面把内容交给本地 daemon
5. daemon 落盘保存：skill 挂到 agent 上当参考（`skillIds`）；工具包只是**装进来**（它的动作由审核者的「行动权限」授权，`Agent.allowedActions`——「挂到 agent 整组可用」那个能力已撤）
6. 使用者**自己的**与下载来的**同时可用**；同名时**拒绝写入**并明确提示与谁冲突——要替换必须显式勾选「允许替换」（D38 起也有了卸载入口）

> ⚠️ **历史形态**：公共目录一度是"一个能进的地方"，里面还摆着内置的 `general-review`（一份审核标准）。D38 把它移除了——审核标准内联在审核者身上（`Agent.reviewStandard`），目录不再承担"发审核标准"这件事。

### 3.6 异常与边界

| 情况 | 行为 |
|---|---|
| 刷新页面 | run 不受影响，页面**按序号补齐**错过的消息 |
| 关掉页面，run 正在跑 | **继续跑完**，只是不再派发新 run |
| 多个标签页同时打开 | 由**本机 daemon** 保证：run 的状态机 + `runId` 幂等（D19 之后远端已经没有 run 队列，页面直接调 `POST /api/runs`） |
| 关掉 daemon | 正在跑的 run 中断，标记为失败（子进程已死） |
| 再次打开页面 | 能看到之前的历史与结果（数据在本地） |
| 换一台机器打开页面 | 看到的是**另一台机器**的数据；远端只有记录副本 |
| 第三方有新数据但页面没开 | 不积压也不丢；下次页面来问时取回，重复部分被去重键挡掉 |
| 远端不可达 | 本地功能**完整可用**；但**能力目录、第三方查询、记录上报**三项失效 |
| 远端永久关闭 | 本地功能仍完整可用；拿不到新 skill，也收不到第三方数据 |
| 未登录 | 本地功能**完整可用**；远端相关功能不可用 |

## 4. 数据在哪

| 数据 | 位置 | 权威 |
|---|---|---|
| issue / 评论 / agent / skill | 本机 daemon | ✅ |
| run 状态与消息流 | 本机 daemon | ✅ |
| verdict / action / artifact / 审计链 | 本机 daemon | ✅ |
| 工作目录与 CLI 登录凭据 | 本机 | ✅ 永不出本机 |
| 账号与用户设定 | 远端 | 远端 |
| 公共 SKILL / TOOL 目录 | 远端（读它自己的文件） | 远端 |
| 记录副本与统计 | 远端 | ❌ 仅便利副本 |
| 设备标识 | 本机生成、界面显示；**上报载荷里没有它**（`apps/web/src/lib/sync.ts` 只出 kind/digest/conclusion/occurredAt；FR-REG-15 未实现） | — |

**远端记录不是审计证据**：写入虽可鉴权（有账号），但**内容完整性取决于远端服务方**。因此合规级证据以本地为准；对外表述用"**可追溯**"，而非"完全可复现"。

## 5. 明确不做的事

| 不做 | 说明 |
|---|---|
| 团队协作 | 没有组织、成员、角色、席位、共享看板 |
| 沙箱隔离 | run 以 daemon 用户权限执行，文档如实披露 |
| 通用工作流引擎 | 只做固定线性链：执行 → 审核 → 判决 → 动作 |
| **平台管理代码仓库** | 不做检出、worktree、仓库缓存；只给工作目录 |
| **改代码** | 不存在这条线，产出都是报告 |
| MCP 工具配置 | 首版不做，留扩展位 |
| 技能**内容指纹** | 不做。⚠️ 版本比较/更新**已经实现**（远端目录给「安装 / 已安装 / 更新 / 退回」，`apps/web/src/lib/skill-catalog.ts` 的 `catalogEntryState`），这一条只剩「指纹」那半 |
| 远端上传 / 发布 | 远端只读自己的本地文件 |
| 桌面端 / 移动端 | 首版只有 Web |
| 多租户与计费 | 没有 |

### 6.1 关于插件机制（D25）

**第三方接入与登录方式都用 plugin 方式实现**，不再各自留专用扩展位。

| 项 | 结论 |
|---|---|
| 为什么 | 两者形状相似（都是"接入一种外部能力"）；各写一套 → 加第三类又要写一套 |
| 两类宿主 | **远端**（`login` / `third-party`）；**daemon**（首版无） |
| 插件从哪来 | **各自读自己的本地目录**——**不从网络拉插件** |
| 隔离靠什么 | **scope 白名单 + 未声明即拒绝**，不靠运行时沙箱 |
| 边界 | **首版只做 `login` + `third-party`**；CLI 适配层保持 daemon 内部表 |

> ⚠️ **不要把插件机制做成"什么都要插件化"**。CLI 适配层（FR-CLI-47）是编译进 daemon 的内部表，改成插件会引入版本兼容与加载时序问题。**只有当"外部第三方要自己写"时才值得做成插件。**
