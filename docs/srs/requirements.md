## 1. 项目定位

> **agentdeck 是一个本地优先的个人 AI 工作台，外加一个公共能力仓库。**
>
> 工作数据、执行、以及 **Web UI** 都在使用者自己的机器上；远端只提供账号、设定、公共能力目录、第三方查询中转与记录统计。

### 1.1 远端与本地各做什么

| | **远端** | **本地（daemon）** |
|---|---|---|
| Web UI | 不托管（可选一个落地页） | **★ 托管 UI**——与本地接口**同源** |
| 账号与登录 | **★ 提供** | 无（token 由页面持有） |
| 用户设定 | **★ 保存**（如轮询间隔、上报开关） | 保存运行相关配置 |
| 公共 SKILL / TOOL | **★ 目录与分发**（读远端自己的本地文件） | 接收、保存、使用 |
| 第三方查询 | **★ 被问时去查第三方**（不暂存） | 取回、建 report、审核 |
| 记录与统计 | **★ 接收**（便利副本） | **权威** |
| 工作数据（issue / run / verdict / 动作 / 审计） | 便利副本 | **★ 权威** |
| 执行 | 无 | **★ 全部** |
| 对远端的网络请求 | 服务被访问 | **daemon 自身不发起**——全部由本机页面代为发起 |

**没有团队协作概念**：不存在组织、成员、角色、席位、共享看板。

### 1.2 与同类产品的方向差异

| 产品 | 流程方向 |
|---|---|
| Multica / Linear / GitHub Agent HQ | agent 干活 → **人审** → 人决定 → 人操作 |
| **agentdeck** | 产物进来 → **agent 审** → agent 出判决 → 系统执行 |
| **agentdeck（完整）** | agent 既执行也把关，只在真正需要判断时升级给人 |

主流产品允许使用者替换**执行容量**（自托管 runner / orbs / 自有 VPC / 自托管沙箱），但**看板、状态机、agent 身份始终在厂商服务器上**。本项目更进一步：**这些全部在本地，远端只留"账号 + 设定 + 目录 + 触发 + 记录"**。

### 1.3 信任边界（必须写进产品表述）

| | 权威性 | 允许的表述 |
|---|---|---|
| **本地审计链** | ✅ 权威 | "合规证据"、"可追溯" |
| **远端记录** | 来源可鉴权的**副本** | "查看历史"、"统计"、"跨机器同步" |

两条限制：

- **内容完整性取决于远端服务方**（服务方管理员可改数据）⇒ **合规级证据仍以本地为准**；
- **不记录 skill 内容指纹** ⇒ 审计链能回答"用了哪个 skill"，**不能证明其内容**。

**严禁**在 UI、README 或对外材料中让使用者误以为远端记录可用于审计或合规。

### 1.4 变现假设

免费使用者可浏览、下载、贡献免费能力；付费来自**专业能力包 / 团队包 / 策展与托管**。

> 这是假设，不是已定策略，需在首版后验证。

## 2. 背景与调研结论摘要

完整证据见仓库 `ref/` 目录（上游行为分析材料）与 §18 的参考文档表。

| # | 结论 | 对需求的影响 |
|---|---|---|
| B1 | Multica 是 source-available 而非 OSI 开源（自定义许可：禁止对外托管、要求保留品牌、授权方可单方调整条款） | 必须 clean-room 实现；本项目以**不可撤销的 OSI 许可**作为差异点 |

| B3 | 该品类存在已被证实的变现失败模式（多个项目在约三个季度内退出） | 商业模式必须与产品同步设计 |

## 3. 目标与成功标准

### 3.1 目标

| ID | 目标 |
|---|---|
| G1 | 使用者在自己的机器上完整运行工作台，远端不可用时本地功能不受损 |
| G2 | agent 能审核进来的产物并产出**机器可执行**的结构化判决，自动触发有界动作 |
| G3 | 执行与审核两个阶段可独立使用，也可串联成闭环 |
| G4 | 每一次判决与动作都可追溯 |
| G5 | 在 Windows、Linux、macOS 上开箱可用 |

### 3.2 成功标准（首版）

- 三个场景（§7）端到端跑通
- 安装只需 Node，**不需要容器、不需要独立数据库服务**
- 完整审计链可导出
- 三平台 CI 全绿，且**测试不会调用使用者真实安装的 agent CLI**

## 5. 术语与词汇约定

**词汇必须在第一天定死，并用测试锁住**（调研教训：内部与界面各叫一套，最终靠专门的术语测试防止漂移）。

| 术语 | 定义 | 接口命名 |
|---|---|---|
| **Workspace** | 本地数据分组容器（**无成员概念**） | `workspace` |
| **Device** | 本机设备标识（设备名等可读信息），**不是账号、不承担鉴权** | `device` |
| **Agent** | 可复用的 AI 协作者配置（名称、指令、模型、runtime、并发上限）。**不是常驻进程** | `agent` |
| **Skill** | 可复用的能力包：给**执行者**参考的资料/方法（正文 + 支持文件）。**不携带审核标准、也不携带动作权限**（D37 把标准搬到审核者身上、D40 收口把动作权限也搬了过去） | `skill` |
| **Runtime** | 执行环境 = 一台机器 + 一个 CLI 工具 | `runtime` |
| **Daemon** | 使用者机器上的**本机服务**：托管 UI、承接操作、执行 run。**不发起对远端的请求** | `daemon` |
| **Run** | 一次具体执行记录，有 `kind`：`execute` 或 `review` | `run` |
| **Report** | 从第三方进来的**不可变快照**，审核的输入 | `report` |
| **Verdict** | 一次 `review` run 产出的**结构化判决** | `verdict` |
| **Action** | 由 verdict 触发的**有界操作**，**全部来自已安装的工具包**（D41：平台不内置任何动作），名字形如 `<包 slug>.<动作名>` | `action` |

| **Artifact** | run 的产出物（报告等）。**宽而自由**，与窄而闭合的 verdict 相对 | `artifact` |
| **Issue** | 人类发起的意图，带讨论与生命周期 | `issue` |
| **Executor / Reviewer** | 执行类 run 与审核类 run 的 agent 身份。**两者不得相同** | — |
| **界面文案 / 契约值** | **界面文案**是人读的句子，随界面语言变；**契约值**是机器读的取值（`pass`、`needs_human`、`comment.create`、`in_progress`、`claude` 等），**任何语言下都原样显示**，翻译只能加在为它配的**标签**上（D39） | — |

**命名约定**：界面与接口统一使用上述名字，**不使用同义词**。状态值一律用完整英文单词。

## 6. 用户角色

**单用户模型——有账号，但没有团队。**

| 角色 | 描述 | 核心诉求 |
|---|---|---|
| **使用者** | 在自己机器上跑 daemon，登录后用本地页面操作 | 一条命令跑起来；不要变成 review 队列管理员 |
| **能力作者** | 编写 skill / tool 并交给远端运维者上架 | 能力能被别人装走 |
| **维护者（项目方）** | 策展远端目录 | 上架内容可控 |

> 三者很可能是同一个人。**没有组织、没有席位、没有角色权限。**

## 7. 使用场景

三个场景是**两个可独立使用的阶段**（执行、审核）的不同组合。

| 编号 | 场景 | 阶段组合 | 地位 |
|---|---|---|---|
| **S1** | 执行 → 审核 → 判决 → 行动 | 执行 + 审核 | **旗舰** |
| **S2** | 审核 → 判决 → 行动 | 仅审核 | **旗舰** |
| **S3** | 执行（产出报告） | 仅执行 | 兜底 |

> **Action 的唯一来源是 verdict**，而 verdict 只由 `review` run 产出。因此 **S3 不触发 Action**（D21）。

### S1：执行后自动审核

1. 指派 issue 给 executor agent → 执行 run
2. 执行完成，产出 report / artifact
3. 系统创建 review run，交给 **reviewer agent（必须是不同 agent）**
4. reviewer 结合 skill 审核 → 产出结构化 verdict
5. verdict 合格 → 触发通过类动作；不合格 → 触发修正类动作（附原因码）
6. 超出 skill 判定标准 → **升级给人**，带结构化 reason_code

### S2：纯审核流水线

1. 第三方**按远端支持的查询协议**完成一次性配置
2. 页面定期向远端询问；远端**按需查询第三方**（不暂存）
3. 页面转交 daemon → 建 `report`（不可变快照）
4. 起 review run → 产出 verdict → 触发有界动作
5. **全程无人类参与，也没有 issue**

### S3：纯执行

1. 指派 issue 给 agent → 执行 run → 产出**报告**
2. 人看报告，决定后续

> **S3 不触发 Action。** Action 只能由**审核**产生的 verdict 触发（§9.10）。
> **不存在"改代码"这条线**——产出都是报告。

### 场景共性

| ID | 要求 |
|---|---|
| SC-1 | 三个场景**共用同一套执行原语与状态机**，不为每个场景单独设计流程 |
| SC-2 | S1 中 reviewer 与 executor 必须是**不同的 agent 身份** |
| SC-3 | verdict → action 可派生出新的 execute run ⇒ **链路可能成环**，必须有边界（§8.5） |
| SC-4 | 人在三个场景中都是**例外通道**，不是默认关卡 |

## 8. 关键约束与不变量

### 8.1 不做通用工作流引擎

链路形态固定为：`[执行?] → [审核? → 判决 → 动作?]`。仅线性串联。

### 8.2 reviewer ≠ executor（强制不变量）

| ID | 要求 |
|---|---|
| INV-1 | 系统必须**拒绝**"同一 agent 既执行又审核同一产出"的配置 |
| INV-2 | 最低要求不同 agent 身份；建议不同 skill、不同 session |
| INV-3 | 使用者强行配置自审时，必须**报错**，**不得静默降级** |

> 理由：自审没有价值。若允许，S1 的整个闭环就是假的。

### 8.3 人是例外通道，不是默认关卡

| ID | 要求 |
|---|---|
| INV-4 | verdict 默认走向**机器可执行**，而非"等待人工批准" ⚠️ **D45 收窄了它的形状**："机器可执行"不再等于"必须带一个处置动作"。`pass` ⇒ 按 `action` 处置；`fail` ⇒ **返工**（把审核意见交回执行者重做，`maxReworks` 次数内）；两者都是机器出口，所以**判决永远不会只能等人**——这条不变量守的是"不许只能等人"，而"出口只有处置一种"是它的一个实现细节，已经改了 |
| INV-5 | 需要人介入时必须携带**结构化 reason_code**，不得只给自然语言 |
| INV-6 | 升级情形必须由 skill 显式定义，不得由系统"猜" |
| INV-7 | 系统不得默认把所有产出置为"待审核" |
| INV-8 | **通知必须稀缺**：通知中心只承载"需要人做决定"类事件，不得每条 run 都响 |

> 理由：这是对该品类最尖锐批评（B4）的直接回应。

### 8.4 动作必须有界

| ID | 要求 |
|---|---|
| INV-9 | verdict 能触发的动作必须来自**显式白名单**（action registry） |
| INV-10 | 每条动作定义必须声明：**执行端（local / remote）**、参数 schema、必要权限、是否幂等、是否可回滚 |
| INV-11 | 动作必须支持 **dry-run** 与**幂等** |
| INV-12 | 可回滚的动作提供回滚路径；不可回滚的必须显式标注 |
| INV-13 | **执行端由注册表决定，不由 verdict 决定**——verdict 只写 action type，使本地动作将来可迁移到远端而不改判决结构 |

> 注意：这不是安全加固（NG7 已明确不做沙箱），而是**功能正确性**。

### 8.5 回路必须有边界

| ID | 要求 |
|---|---|
| INV-14 | 必须有**最大链路深度**限制（⚠️ D41 之后**没有调用点**：唯一会加长链路的动作 `issue.assign_agent` 随内置动作一起删了。实现与测试仍在域层，见 `docs/../design/design.md` §15.29） |
| INV-15 | 必须有**环检测**（⚠️ 同上：D41 之后没有调用点） |
| INV-16 | 由 action 派生出的 run 必须**显式打标**（⚠️ 同上：D41 之后没有动作能派生 run） |
| INV-17 | 必须防止同一 agent 对同一对象并发自竞争 |

### 8.6 词汇不漂移

| ID | 要求 |
|---|---|
| INV-18 | §5 术语表是权威定义，界面与接口命名必须一致 |
| INV-19 | 必须有自动化测试防止术语回退 |

## 9. 功能需求

优先级：**P0** = 首版必须有；**P1** = 第一阶段；**P2** = 后续。

### 9.1 FR-LOCAL 本地实例

| ID | 需求 | 优先级 |
|---|---|---|
| FR-LOCAL-01 | **单用户模型**：需要登录账号，但**无成员、无角色、无团队、无席位** | P0 |
| FR-LOCAL-02 | 以**设备标识**（设备名等可读信息）区分本机；启动时自动读取，允许覆盖。**不承担鉴权与归属职责** | P0 |
| FR-LOCAL-03 | 本地数据目录必须可配置；同一目录**只允许一个 daemon 进程打开**（锁文件） | P0 |
| FR-LOCAL-04 | 支持创建/切换**本地工作区**（仅数据分组，无成员） | P1 |
| FR-LOCAL-05 | **一台机器只支持一个账号登录**；不支持同机多账号同时使用 | P0 |

### 9.2 FR-AUTH 账号、登录与设定

| ID | 需求 | 优先级 |
|---|---|---|
| FR-AUTH-01 | 使用者必须**登录**后才能使用远端功能（账号、设定、能力目录、记录） | P0 |
| FR-AUTH-02 | 登录态由**本地页面**持有；daemon **不持有任何远端凭据**。⚠️ **必须用 token 而非 cookie**——本地页面是 `http://127.0.0.1`，`Secure` cookie 不会在 http 上发送 | P0 |
| FR-AUTH-03 | **登录方式实现为 `login` 插件**（D25）；首版至少内置一种最小形态 | P0 |
| FR-AUTH-04 | 账号是**个人身份**，不是团队成员：不得引入组织、成员、角色、席位 | P0 |
| FR-AUTH-05 | 记录与设定**归属到账号**；设备标识只表示"哪台机器" | P0 |
| FR-AUTH-06 | daemon 的本地功能在**未登录或远端不可达**时**仍须完整可用** | P0 |
| FR-AUTH-07 | 远端必须**保存用户设定**，使同一账号在任意机器/浏览器行为一致 | P0 |
| FR-AUTH-08 | 设定至少覆盖：**轮询间隔**、上报开关，以及后续同类设定 | P0 |
| FR-AUTH-09 | 设定可在页面修改并**立即生效**，不得要求重启 daemon | P1 |
| FR-AUTH-10 | 首版设定范围就限于：**轮询间隔**、**上报开关**（更多项后续按需增加） | P1 |

### 9.16 FR-PLUGIN 插件系统

> **D25**：**第三方接入与登录方式都用 plugin 方式实现**，而不是各自留一个专用扩展位。
> 理由：这两类扩展点形状相似（都是"接入一种外部能力"），用统一机制实现比各写一套更省、也更容易加第三类。

| ID | 需求 | 优先级 |
|---|---|---|
| FR-PLUGIN-01 | 必须提供**统一的插件机制**，作为扩展点的标准实现方式 | P0 |
| FR-PLUGIN-02 | 插件必须通过 **manifest 声明**：能力类型（capability）、所需 scope、`apiVersion`、以及可选的代码入口 | P0 |
| FR-PLUGIN-03 | 至少支持两类插件：**`login`**（登录方式）与 **`third-party`**（第三方接入） | P0 |
| FR-PLUGIN-04 | 必须留出**新增插件类型**的扩展位：新增一类能力时**不得改动宿主既有调用链** | P0 |
| FR-PLUGIN-05 | 插件**不从网络拉取**：daemon 从**本地目录**加载自己的插件，远端从**本地目录**加载自己的插件 | P0 |
| FR-PLUGIN-06 | **未声明即拒绝**：宿主不认识的能力或 scope 必须**拒绝加载**并给出可读原因 | P0 |
| FR-PLUGIN-07 | 宿主不得加载不认识的主 `apiVersion` 的插件 | P0 |
| FR-PLUGIN-08 | **插件加载失败不得影响宿主其他功能**——某个 login 插件坏了，邮箱登录仍须可用 | P0 |
| FR-PLUGIN-09 | 插件必须能**独立启用 / 停用**，且停用后宿主的其他插件不受影响 | P0 |
| FR-PLUGIN-10 | 必须有**插件清单视图**：显示已加载的插件、类型、版本、scope、加载状态与失败原因 | P1 ⚠️ **部分实施**：清单视图在远端「设置」抽屉（`SettingsDrawer.svelte`：插件名、capability、加载 / 启用状态、失败原因、密钥键名、启停按钮）；**版本与 scope 两列未展示** |

| FR-PLUGIN-12 | 插件的错误必须**可见**（日志 + 清单视图），不得静默失效 | P0 |

## 10. 状态机

### 10.1 Run 状态机（execute 与 review 共用）

| 状态 | 含义 | 终态 |
|---|---|---|
| `deferred` | 已排期，未到触发时刻 | 否 |
| `queued` | 已受理，等待开始执行 ⚠️ 原"等待页面把它交给本机 daemon"的说法随 D19 失效——run 现在直接提交本机 daemon（`POST /api/runs`），`queued` 只是受理后、开跑前的队列位 | 否 |
| `dispatched` | daemon 已受理，正在准备工作目录并启动 CLI | 否 |
| `waiting_local_directory` | 目标目录被其他 run 占用，等待释放 | 否 |
| `running` | CLI 正在执行 | 否 |
| `completed` | 正常完成 | 是 |
| `failed` | 出错或被中断 | 是 |
| `cancelled` | 被手动停止 | 是 |

| ID | 要求 |
|---|---|
| SM-RUN-1 | 合法转移：`queued→dispatched→running→completed\|failed`；`*→cancelled`；`dispatched→waiting_local_directory`；**`queued→failed`、`waiting_local_directory→failed`**（见下方说明） |
| SM-RUN-2 | `deferred→queued` 由调度时间驱动 |
| SM-RUN-3 | `completed` 仅表示"这次 run 结束了"，**不代表 issue 完成** |
| SM-RUN-4 | 改变 issue 的指派人或状态，**不得**停止已启动的 run |

> **关于 `queued→failed` 与 `waiting_local_directory→failed`**（v2.4 补充）：
> `failed` 的定义是"**出错或被中断**"，而"被中断"是它字面含义的一部分。
> 但原转移表只允许从 `dispatched` / `running` 进入 `failed`，那等于假设
> **run 只可能在开始执行之后出问题**。
>
> 反例是 daemon 重启：状态是持久化的，所以上次退出时还在排队的 run 会停在
> `queued` / `waiting_local_directory` 上，而它们**再也不会有结果**
> （执行所需的 prompt 与技能正文未落盘）。原来只给它们留了 `cancelled`——
> 那是"使用者主动停止"，记成这个等于**在数据里撒谎**。
>
> 因此补上这两条边，让"被重启中断"落进它本该落的地方（`failed` +
> `failureReason: daemon_restarted`）。处置见 `FR-RUNTIME-11`。

### 10.2 Verdict 生命周期

```
pending_verdict → emitted → validated → (dispatched_to_action | advisory | escalated | rework_requested)

> ★ `rework_requested` 是 D45 加的：判决 `fail` 的意思不是「处置它」，而是把审核意见交回**执行者**重做
> （任务上可选 0–5 次）。它与 `escalated` 同属终态，区别是「还有没有返工额度」。
                          ↘ invalid   → (retry | downgrade_to_advisory | escalate)
```

### 10.3 Action 生命周期

```
proposed → (auto_approved | awaiting_approval) → executing → executed | failed | rolled_back | skipped
```

| ID | 要求 |
|---|---|
| SM-ACT-1 | 默认路径是 `auto_approved`；`awaiting_approval` 是例外（INV-4） |
| SM-ACT-2 | 幂等动作重复触发时进入 `skipped`，不得重复执行 |
| SM-ACT-3 | `failed` 必须可见并通知，不得静默 |

## 12. 数据实体（概念级）

| 实体 | 说明 | 关键关系 |
|---|---|---|
| `workspace` | 本地数据分组容器（**无成员**） | 1:N 其余实体 |
| `device` | 本机设备标识，**不是账号** | — |
| `agent` | 可复用 agent 配置 | N:1 workspace |
| `skill` | 可复用的资料包（正文 + 支持文件），给执行者参考 | N:M agent |

| `run` | 一次执行记录，含 `kind` | N:1 agent；可自引用（派生关系） |
| `report` | 不可变外部产物 | N:1 workspace；1:N run（审核） |
| `verdict` | 结构化判决 | 1:1 review run；1:N action |
| `action` | 有界操作及结果；含**执行端** | N:1 verdict |
| `artifact` | run 的产出物（宽而自由） | N:1 run |
| `runtime` | 执行环境 | N:1 workspace |
| `audit` | 审计链路记录 | 关联 run / verdict / action |
| `tool` | 工具包（D40）：一个目录 = 一个包 = 一个组（`tool.json` 清单 + 入口脚本），动作名形如 `<包 slug>.<动作名>` | N:1 workspace；与 agent 的关系**不在「挂载」上**——审核者用 `Agent.allowedActions` 引用它的动作（D40 收口），「挂到 agent 整组可用」那个能力已整个撤掉 |
| `reviewStandard` | 审核标准（D37）。★ 2026-09：它**并入了 `Agent.instructions`**（② 身份），界面上不再单独设置；这个字段只剩**老数据的兼容读取**（投递时合成进 ②，详情页可一键并进「指令」） | 1:1 agent（reviewer，`Agent.reviewStandard`） |
| `comment` | issue 下的评论与活动时间线 | N:1 issue |
| `inboxItem` | 通知中心条目（类别 + 严重度，供订阅 / 静音） | N:1 workspace |
| `conversation` | 一个对话（D49）：**绑一个执行者**（中途不换）、可选自己的 `skillIds`、自己的 `workDir`；删对话**连同轮次**，但跑过的 run 原样留着 | N:1 agent（+ N:1 workspace） |
| `chatTurn` | 对话里的一轮：使用者那句话 + 它的 `runId`（**先落盘再提交**，`runId` 为空的那条拿到 run 后原地更新） | N:1 conversation |
| `assignee` | 指派对象：人（member）或 agent | 1:1 issue（`Issue.assignee`） |

| ID | 约束 |
|---|---|
| DR-1 | `report` 不可变：创建后内容不得修改 |
| DR-2 | `verdict` 必须引用其输入快照与**所用 skill 的标识与来源** |
| DR-3 | 每次 run 产生独立记录，**历史不得被覆盖** |
| DR-4 | 所有实体必须可追溯到 workspace |
