# 示例工具：通知（example-notify）

**远端目录里的范例包，专门用来测试动作参数**——特别是「平台/渠道」这一大类。

## 它演示什么

`example-notify.send` 模拟发一条通知，但**不真的发**：它把收到的**完整参数**追加写到
工作目录的 `notify.log`，还逐项写出参数类型。装好之后建一条任务、让审核者在判决里引用
这个动作，然后打开工作目录里的 `notify.log`，就能看到"这一次判决到底传了哪些参数、类型
对不对"——这就是测试参数管道的方法。

## 参数一览

| 参数 | 类型 | 平台是否要求 | 怎么填 |
|---|---|---|---|
| `channel` | **enum**（平台/渠道） | 必填 | `dingtalk` / `wecom` / `feishu` / `slack` / `email` 五选一 |
| `title` | string（≤200） | 必填 | 一句话标题 |
| `content` | string（≤2000） | 必填 | 正文 |
| `urgent` | boolean | 必填 | 是否加急 |
| `retries` | integer（0–10） | 必填 | 失败重试次数 |
| `dir` | bound（`workdir`） | 平台注入 | **模型看不见、也填不了**；平台按事实填工作目录 |
| `run-id` | bound（来源 `subject.runId`） | 平台注入 | 触发这次动作的那条 run 的 id（模型同样填不了） |

## 为什么这样设计

- **enum 演示"平台/渠道"这一类**：动作要发到哪个渠道，天然是一个**有穷枚举**，而不是
  随便一个字符串——枚举外的一个值要么是拼错、要么是还没接的渠道。契约里只把参数名列
  给模型（`你只需要给：channel、title、content、urgent、retries`），填什么由模型决定，
  但**值的合法性在判决校验时按这份清单挡住**。
- **绑定参数演示"平台按事实注入"**：`dir` 与 `runId` 不从判决来（模型写了反而判不合规），
  平台在执行前按这次 run 的事实填好——脚本拿到的这两个值**不可能被模型带偏**。

## 怎么用（端到端测一遍）

1. 「工具」页 → 从**远端目录**安装 `example-notify`。
2. 把它挂到一个**执行者**身上（执行者的能力是工具，与动作权限无关）。
3. 在**审核者**的「行动权限」里允许 `example-notify.send`（审核标准里也可以提到它）。
4. 新建任务跑一次；模型判完会写判决 `action: { type: "example-notify.send", params: { … } }`。
5. 判决通过后平台执行脚本；打开那条任务的工作目录（`~/alpha-helper-workspace/issue-<id>/…`），
   看 `notify.log` —— 每一行就是一次调用收到的参数与类型。

⚠️ 它刻意**只往工作目录写一个文件**：范例不该在你的机器上动别的东西。
