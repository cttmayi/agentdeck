# 什么时候拆支持文件、怎么放

## 拆分的三个理由（满足其一才拆）

1. **有可执行的东西**：脚本、校验器、生成器 → `scripts/`
2. **有长表格 / 长清单**：映射表、术语表、字段说明 → `references/`
3. **有可直接复制的成品**：模板、配置骨架、示例文件 → `templates/`

反面：把正文硬切成多个 md 只为"看起来有条理"——那不是拆分，是把检索成本转移给读者。

## 目录布局

```
<slug>/
├── SKILL.md            ← 必须；正文 + frontmatter
├── references/         ← 长文参考（按主题一个文件）
│   ├── fields.md
│   └── errors.md
├── scripts/            ← 可执行脚本（带 shebang 或明确调用方式）
│   └── normalize.mjs
└── templates/          ← 可直接复制走的成品
    └── config.example.json
```

- 目录名用复数、小写、固定三选（`references` / `scripts` / `templates`）——
  读者找东西靠约定，不靠猜。
- 文件名描述内容（`errors.md` 而不是 `doc2.md`）。
- **只放文本文件**：二进制（图片、字体、压缩包）不被支持，需要时改写成文本或说明来源。

## 正文里怎么引用

用**相对技能目录的路径**，并且**在正文里说明它的用途与读法**——只给路径不给理由，
读者不知道何时该打开：

```markdown
## Procedure
3. 按 `references/fields.md` 里的字段表逐列核对；表里没列出的列，先问使用者再加
4. 跑 `scripts/normalize.mjs`（参数见文件头注释），它会把不合规行写到 stderr
```

## 体积与数量

| 项 | 建议上限 | 超了怎么办 |
|---|---|---|
| 单文件 | 256 KB | 拆成多个参考文件，或删掉与大段无关的日志样例 |
| 全部文件总量 | 1 MB | 只保留"做这件事必须看"的部分；历史材料不入库 |
| 文件数 | 64 | 说明抽象层次太细，合并同主题文件 |

## 自检

- 正文里出现的每个文件路径，在目录里都真实存在（拼写、大小写、层级一致）？
- 脚本能被直接执行（有解释器声明，或正文写清 `node scripts/x.mjs`）？
- 把 `references/` 全部删掉，`SKILL.md` 还能独立看懂"做什么"吗？不能 → 正文没写清。
