# SKILL.md 的结构与不结晶清单

## 骨架

```markdown
---
name: <kebab-case 动作短语>
description: <一句话，含触发条件——"当……时用">
---

# <一句话标题：这个技能解决什么问题>

## When to Use
- <触发场景 1>
- <触发场景 2>
- <不适用的情况（防止误加载）>

## Procedure
1. **<动作名>**：<做什么> —— `<可直接复制的命令>`
   期望看到：<成功时的关键输出特征>
2. ...

## Pitfalls
- <踩过的坑 + 为什么 + 怎么绕>

## Verification
- <怎么验证做对了：命令 / 检查项 / 判据>
```

## 写好坏对照

**Procedure 的一步**

| 坏 | 好 |
|---|---|
| 运行测试并修复问题 | 跑 `pnpm test 2>&1 \| tail -40`；有 `fail` 就先修最后一条失败用例，修完重跑，直到 `fail 0` |
| 用脚本处理数据 | `node scripts/normalize.mjs --in raw.csv --out clean.csv`；输出行数必须比输入少（去重生效） |

**description**

| 坏 | 好 |
|---|---|
| 项目构建帮助 | 当需要给这个仓库出产物、或 CI 报构建失败要本地复现时用 |
| Excel 工具 | 当需要把多语言 Excel 的列名统一成英文并导出 CSV 时用 |

**When to Use**

只写"什么时候用"会把技能变成万能钥匙。**同时写清什么时候不要用**，才是能用的路由信号：

```markdown
## When to Use
- 需要在本地复现 CI 的构建失败时
- 需要出可交付的产物（dist/）时
- 不要用：只是改文档、或用例失败但与构建无关时
```

## 不结晶清单（命中即停）

| 别写进去 | 为什么 |
|---|---|
| 环境依赖失败（缺包、没凭证、无权限、网络不通） | 换台机器就消失；写进去等于把一次性的坑永久化 |
| 对工具的负面判断（"X 不好用"） | 会冻结成长期拒绝使用，除非附带明确的替代方案与判据 |
| 靠重试治好的一次性错误 | 可复用的是"无输出就重试一次并记录"，不是那个错误本身 |
| 一次性任务的叙述（"这次我做了 X"） | 那是日志，不是步骤 |
| 未解决的失败 | 没有验证过的做法不该被固化 |

判断口诀：**换一个人、换一台机器，照它做还能成吗？** 不能，就不是技能素材。

## 语言与长度

- 正文用使用者对话的语言写（本平台是中文），**结构标题保持英文**（`When to Use` /
  `Procedure` / `Pitfalls` / `Verification`）——工具与人都靠它定位。
- 单文件控制在 **400 行以内**。超了说明该拆参考文档（见 `files.md`），而不是压缩句子。
- 命令块写完整的、能复制就跑的形式；需要变量时用 `<尖括号>` 标出要替换的部分。
