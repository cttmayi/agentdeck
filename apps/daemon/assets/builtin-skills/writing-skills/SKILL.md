# 写一个能被正确加载的 skill

skill 不是文档，是**给未来的自己（或另一个模型）用的操作手册**。判断标准只有一条：
**换一个不了解上下文的人，照着它能不能把事做成。**

## When to Use

- 要把一次对话/任务里跑通的做法固定成可复用技能
- 要修订已有技能（进化），而不是新建一个重复的
- 要判断某段经验**值不值得**沉淀（见下面的不结晶清单）

## Procedure

1. **先判值不值得写**。命中不结晶清单（见 `references/structure.md`）就直接停，写一句话
   说明为什么不可沉淀——垃圾技能会冻结成长期的错误行为，比没有技能更糟。
2. **起名**：`name` 用 kebab-case 的**动作短语**（`review-report`、`extract-table`），不用
   项目名/人名/日期，不超过 63 字符。它会变成目录名与调用名。
3. **写 frontmatter**：
   ```yaml
   ---
   name: <kebab-case>
   description: <一句话：什么时候该用它——必须含触发条件>
   ---
   ```
   `description` 是渐进式披露的**第一层**：模型只看它决定要不要加载正文。所以它写的是
   **触发条件**（"当……时用"），不是功能简介（"一个用来……的工具"）。
4. **写正文四节**，顺序固定：`## When to Use` / `## Procedure` / `## Pitfalls` /
   `## Verification`。正文只写**怎么做**，不写这次做了什么。
5. **判断要不要拆支持文件**：有可执行脚本、长参考表、模板 → 拆（见 `references/files.md`）；
   只有步骤和判断 → 单文件就够，别为了"看起来专业"硬拆。
6. **过自检清单**（`references/checklist.md`），逐条打勾再交付。

## Pitfalls

- **把"这次发生了什么"写成步骤**。"这次我用了 X 工具"不是可复用步骤；"先跑
  `xxx --dry-run` 看输出里有没有 `ERROR`，有就停下改配置"才是。
- **description 写成功能简介**。"一个处理 Excel 的技能"→ 模型不知道该什么时候用；
  "当需要把多语言 Excel 的列名统一成英文并输出 CSV 时用"→ 才会有正确的加载时机。
- **步骤里省略命令参数**。`npx foo` 和 `npx foo --strict --out dist` 是两回事，写全，
  让读者能直接复制。
- **环境问题当成技能内容**。缺依赖、没配凭证、网络不通——这些换台机器就消失，写进去
  等于把一次性的坑永久化。
- **对工具下负面判断**。"X 工具不好用"会冻结成长期拒绝，除非有明确的替代方案与判据。
- **一节里塞三件事**。`Procedure` 的一步应该是一次可验证的动作，不是一段概述。
- **不留验证方式**。没有 `Verification` 的技能无法判断"做完了没"。

## Verification

交付前对每个文件问四个问题，全部为"是"才算完成：

1. `SKILL.md` 有 frontmatter，`name` 是 kebab-case，`description` 写了触发条件？
2. 正文四节齐全，`Procedure` 的每一步都能被直接执行（命令/参数完整）？
3. 正文里引用的每个支持文件都真实存在，路径与文件名一致？
4. 换一个不懂上下文的人照做，能判断出"做完了"和"做错了"？
