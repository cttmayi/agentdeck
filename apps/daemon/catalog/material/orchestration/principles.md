# 生成编排的六条原则（先读这一份）

这一份是**硬原则**，不是建议。每一条都来自一次真实的翻车现场（2026-11 的
「AI每日情报流水线」跑完，人在工作目录里**找不到文章**）。写完代码逐条对照。

> 三条平台事实（不读懂这三条，六条原则就无从谈起）：
> 1. **`main.js` 的返回值没人看**——引擎执行完就丢掉。编排的产出 = **每一步 run 的产出**。
> 2. **每次执行编排都会新建一个任务 ⇒ 新工作目录**。上次工作目录里的文件不会自己出现。
> 3. **内建智能体没有记忆**（记忆只属于智能体页里的账号智能体）。它们不会"记得上次"。

---

## 原则 1｜交付物必须落成工作目录里的文件

**规则**：这条编排的最终交付物，是工作目录里的**一份文件**（路径与文件名写死），
不是"某一步的对话文本"。

**为什么**：run 的文本只留在运行日志里（会滚走、要一层层点开才看得到），
也没法再加工。人打开工作目录找不到东西，就等于没产出。

**怎么做**：
- 最后一步安排"交付"：让某个人（可以就叫「交付员」）把终稿写到
  `终稿-<YYYY-MM-DD>.md`；或者让最后那个人自己在「输出格式」里写明"写到 `终稿-<日期>.md`"。
- 并且在**交付那一步那个人的** `instructions.md` 里**单独写一行**：

  ```
  落盘：终稿-<YYYY-MM-DD>.md
  ```

  这一行是**平台会检查的**：一条编排里没有任何人写这一行 ⇒ 候选卡片上会标「没有交付物落盘」。
  （检查的是"有没有人负责交付"，不是"每个步骤都要产出文件"。）
- 中间产物也各有名字：`资料-<日期>.md`、`草稿-<日期>.md`。**下一步读文件**，
  不靠"上一轮对话里说了什么"——`flow` 的接力只传文本，跨轮次就更靠不住。
- 文件名要能让**第二次运行不覆盖第一次**（带日期），或者相反：明确要覆盖同一份（`终稿.md`）。

## 原则 2｜不要用 `return` 交付

**规则**：`main.js` 里不要靠 `return` 把东西交给使用者。

**为什么**：返回值被丢掉（平台事实 1）。`return '⚠️ 两轮审校未通过…'` 这种写法
**不会报错**、也不会有人看到——两个分支都成了死代码，最贵的是"失败提醒"随之消失。

**怎么做**：要给人看的东西**写进文件**（原则 1）或**写成某一步的产出**；
分支判断可以留，但每个分支都要落到"某个动作"上，而不是"拼一段字然后 return"。

## 原则 3｜失败路径要看得见

**规则**：`loop` 超轮（`结果.result === 'fail'`）时，必须有一步把
「未通过 + 审校意见 + 最后一版正文」写成文件（`未通过-<日期>.md`），或交给交付员。

**为什么**：把关者说"不通过"是一次普通 run，人只看到审校那一段；
整条编排"没通过"这件事本身没有地方说。靠 `return` 说（原则 2）等于没说。

**怎么做**：

```js
const 结果 = await loop(调研, 审校, '{{task}}', { maxRounds: 2 })
if (结果.result === 'fail') {
  const 收尾 = agent('收尾员')   // 这个人必须写进 agents/
  await 收尾.run(`把这次失败写进 未通过-今天的日期.md：结论=未通过、审校意见、最后一版正文。`)
}
```

## 原则 4｜跨次累计的东西不能想当然

**规则**：需要**跨多次运行**累计的状态（已发清单、进度、去重台账）不要假设
"上次工作目录里那份还在"。

**为什么**：每次执行都是新任务、新工作目录（平台事实 2）；内建人也没有记忆（事实 3）。
这次的 `已发清单.md` 落在当次目录里，**明天再跑读到的是空清单** ⇒
"每天不重复"这个核心要求根本不可能成立。

**怎么做**（三选一，按可行性挑，并在身份/回复里写清挑了哪个）：

1. **固定目录**：需要台账的编排，运行时把「工作目录」填成**同一个固定路径**
   （运行对话框里那一格），每次执行都用它；
2. **做成技能**：把台账写成一份技能（挂在账号智能体上，运行时注入），人维护它的内容；
3. **人给**：在任务描述里由人提供"上次已收录的清单"。

三者都没用 ⇒ **不要在身份里写"每天不重复"这类要求**，改成"本次只能与任务描述里给的清单比对"。

## 原则 5｜把关者要判事实，不只判格式

**规则**：把关者的检查表里必须有**可核验的事实项**，并且打回意见要指明位置与改法：

1. 主线出处那个页面**能打开**吗？
2. 正文里每个数字 / 日期 / 人名，**能在出处页面里找到**吗？
3. 每个链接指向的是**原文**（而不是转载、二手转述）吗？

**为什么**：这次的审校第一轮只因为"『本次未采用』里没写明已核对清单"打回，
第二轮补了那一句话就通过了——而"文中的数字是否真的在原文里"没人核过
（事后核对是对的，但那是运气，不是把关）。

**怎么做**：把上面三问写进把关者的身份（「职责」或检查表），并写明
"判不了就写不通过 + 缺什么证据"。

## 原则 6｜收尾陈词不写进交付物

**规则**：交付文件里不出现"我创建了哪个文件 / 把抓取页面放进了 `.scratch/` /
本次已核对清单"这类**过程说明**。过程信息写进聊天回复，或单独的 `说明.md`。

**为什么**：这次文章的**最后一整段**就是行政说明（"工作目录内已创建 `已发清单.md`…"），
人拿去直接发，会把内部流程带出去。

## 写完自检（六问，逐条答"是"）

1. 终稿是工作目录里的文件吗？文件名在谁的身份/任务书里写明了？
2. 代码里还有 `return` 在交付东西吗？
3. 把关循环失败时，有人把"未通过"写下来吗？
4. 需要跨次累计的状态，落点在哪（固定目录 / 技能 / 人给）？还是干脆没有这种状态？
5. 把关者的检查表里有"事实三项"（能打开 / 能对上 / 是原文）吗？
6. 交付文件里有没有混进过程说明？

六条里有任何一条答不上来，就把那条的依据补上再交付；补不出来就**如实告诉用户
"这条编排做不到 X，因为平台现在没有 Y"**——不要假装做到了。
