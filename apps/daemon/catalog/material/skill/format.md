# 技能的形状

一条技能 = 一个目录，目录名与 `name` 相同：

```
<技能名>/
  SKILL.md            必须有
  references/…        可选：分主题的参考材料
  templates/…         可选：模版/骨架文件
```

起草 run 里的落点就是这块形状：`skill/<技能名>/`——写它等于写完了入库后的形状。

## `SKILL.md` 的 frontmatter

```markdown
---
name: meeting-minutes-format
description: 会议纪要的固定形状：结论三句以内、待办带人+期限、未决问题单列。给"整理会议记录"这类任务用。
---
```

| 字段 | 硬要求 |
|---|---|
| `name` | **kebab-case**（小写字母/数字/连字符，`^[a-z0-9][a-z0-9-]{0,62}$`）；与目录名一致；它是标识（引用键），不是给人看的标题 |
| `description` | **必填**。模型靠它决定"什么时候该加载这份技能"：先写它干什么，再写什么场景用它。中文可以 |

⚠️ 不再要求 `## When to Use` / `## Procedure` 这类固定小节（那是我们的口味，不是技能规范的形态）。
真正要求的是：**正文能被另一个模型在没有上下文的情况下读懂并用起来**。

## 正文怎么写

- 第一段：这份技能解决什么问题（一到两句）。
- 主体：**步骤 / 规则 / 判据**，按能被照做的顺序排；每条尽量能勾选。
- 结尾：常见坑（"看起来对但会坏"的那几条）——这是最值钱的部分。
- 写支持文件时，正文里**指路**（"见 `references/typography.md`"），不要把长材料抄进正文。

## 支持文件

| 目录 | 放什么 |
|---|---|
| `references/` | 参考材料：规范摘录、格式说明、长清单 |
| `templates/` | 可复制的模版/骨架 |

不要放：二进制、大素材（单文件 > 256 KB 会被拒）、与技能无关的临时文件。
